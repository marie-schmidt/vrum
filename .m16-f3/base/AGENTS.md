# AGENTS.md

How to work in this repository. Read `SPEC.md` first, then `PROGRESS.md`.

## Running the checks

`./check.sh` is the one check command. It runs, in order:

1. lint: `uv run ruff check .` and `uv run ruff format --check .`
2. types: `uv run mypy` (strict)
3. unit tests: `uv run pytest -m "not integration"`
4. integration tests: builds the image, starts the real database and server in a throwaway compose project (`vrum-check`, port 18000 or `VRUM_CHECK_PORT`, random database password, removed afterwards; there is no token: the tests register an account, make a project and an agent key through the board's own HTTP API, `tests/world.py`), together with the stand-ins and extras in `compose.check.yaml` (which `check.sh` adds through `COMPOSE_FILE`): a scripted embedding service, a scripted language model (its port, `VRUM_CHECK_PORT` + 2, is published so tests can script it and read what it was sent), and a second server with no language model set up (`VRUM_CHECK_PORT` + 1). It runs `uv run pytest -m integration` with a real MCP client against it. A proof stack started by hand (a clean clone, another compose project and port) needs the same `COMPOSE_FILE=compose.yaml:compose.check.yaml`, the ports `VRUM_NO_MODEL_PORT` and `VRUM_MODEL_SCRIPT_PORT`, and `VRUM_TEST_URL`, `VRUM_NO_MODEL_TEST_URL` and `VRUM_TEST_MODEL_URL` to match (plus `VRUM_RESTORE_TEST_PORT` for the tests that start a second copy), because the tests stop and start the stand-ins.

It needs Docker (with compose) and `uv`. It never touches your own stack or your `.env`. Run it before every commit; fix `ruff format` problems with `uv run ruff format .`.

`./acceptance.sh` is the other command: the shorter walk a person can read. It starts its own throwaway stack (compose project `vrum-acceptance`, port 18400 or `VRUM_ACCEPTANCE_PORT` with the next two ports for the second server and the scripted model, and the one after for the second, empty copy the board chapter makes (compose project `vrum-restore`), random password and token, the same stand-ins as the check stack; it needs `openssl` too), runs one scenario through a real MCP client, prints one line for each proof of each milestone, and removes everything afterwards, even when it fails. Name chapters to run only those (`./acceptance.sh arriving moving`; the names are in `tests/acceptance.py`). It runs in the checkout it is in, so "from a clean clone" means: clone, then run it there. Each later milestone adds its proofs to it.

## Running the stack

```
./scripts/init-env.sh      # once: writes .env with a random database password
docker compose up -d --build --wait
```

The board is at `http://127.0.0.1:8000/board` (or `VRUM_PORT`) and the MCP endpoint is `http://127.0.0.1:8000/mcp` on the same port. There is no install-wide token: open the board, create an account (email and password kept by Vrum, `src/vrum/accounts.py`), create a project (it opens at `/board/p/<id>`), and on its **Agent access** page make an agent key (`vrk_…`, shown once, only its hash is kept). Every request to the MCP endpoint needs a project's agent key, as `Authorization: Bearer <key>`, and reaches that project only; the board's own calls under `/board/api` carry a session cookie and the session's CSRF secret instead; only `GET /health` and the board's page files are open. While working on the board's pages (`src/vrum/board/static`), the server reads them once at start, so rebuild the image to see a change, or mount that folder over `/app/.venv/lib/python3.12/site-packages/vrum/board/static` in a scratch compose override and restart `app`. For a script or a client of your own, `scripts/vrum_client.py` connects with the key it reads from the `VRUM_AGENT_KEY` environment variable (`export VRUM_AGENT_KEY=...` first; the helper scripts below need it). The most one request may hold is `VRUM_MAX_REQUEST_BYTES` (4 MiB). `docker compose down` stops it; add `--volumes` to also delete the data. Logs are JSON lines (`docker compose logs app`): they never hold passwords, sessions, keys or what was written.

**Backing up and moving data.** `./scripts/backup.sh [file]` writes the whole database to one file (default `backups/vrum-<time>.dump`, git-ignored, readable only by you) while the server runs: every account and project, hashes included, so it is for whoever runs the server and not an account's to take. `./scripts/restore.sh <file>` puts it back (it creates the database role the projects run as first, since a role belongs to the server and not to a database): into a fresh database (after `docker compose down --volumes`) it just restores; into one that holds data it refuses unless you add `--replace`. For one project's data that you can read, keep or load into another project or server: `uv run python scripts/export_graph.py <url> <file.json>` writes the project as one JSON file (ids included: each project numbers its own), `scripts/import_graph.py <url> <file.json>` loads such a file into an empty project (all or nothing; as big as one request may be), and `scripts/export_markdown.py <url> <folder>` writes a read-only Markdown copy, one file per item with `[[references]]`, to read in Obsidian or keep in git. All three need `VRUM_AGENT_KEY` set (the project's key), and work from a checkout without installing anything.

Search by meaning, similar items and overlaps need an embedding service; exact-words search needs nothing. To run one on this machine, add `EMBEDDING_BASE_URL=http://ollama:11434/v1` and `EMBEDDING_MODEL=all-minilm` to `.env` and start with `docker compose --profile local-embeddings up -d --build --wait` (the first start downloads the model, about 50 MB). Any OpenAI-compatible service works instead: set the two variables to its address and model (see `.env.example`). To see what a real model does with realistic requirements, run `uv run python scripts/real_embeddings_check.py http://127.0.0.1:8000/mcp` (with `VRUM_TOKEN` set to the token in `.env`; it adds a few clearly named epics and stories). The thresholds depend on the model: measure, then set `EMBEDDING_MIN_SIMILARITY` and `EMBEDDING_OVERLAP_THRESHOLD`.

`extract_facts`, `consolidate_memory`, `find_contradictions` and `reflect` need a language model; without one they say so and everything else works. Set `LLM_BASE_URL` and `LLM_MODEL` in `.env` (any OpenAI-compatible chat service; see `.env.example`). To use Ollama installed on this machine: `LLM_BASE_URL=http://host.docker.internal:11434/v1` and `LLM_MODEL=llama3.2`. To see what a real model does with the same notes and questions every time, run `uv run python scripts/real_model_check.py http://127.0.0.1:8000/mcp` (it adds a few clearly named items); what it prints is recorded in `PROGRESS.md`.

## Layout

- `src/vrum/config.py`: settings from the environment (the only place that reads it), including the request size limit and the optional embedding and language services. There is no token setting.
- `src/vrum/accounts.py`: the one owner of accounts, sessions, projects and agent keys (the `accounts`, `sessions`, `projects` and `agent_keys` tables, which are not graph content and which a project's database role cannot reach): `Accounts.register`/`sign_in` (scrypt hashes, `hash_password`/`password_matches`; the failures of one address or one network address are counted by `src/vrum/ratelimit.py`'s `AttemptLimiter`, in memory), `session` (a cookie's value, of which only a SHA-256 is stored, plus a CSRF secret), `projects`/`create_project`/`project_of` (a project that does not exist and one that is someone else's are refused in the same words), and `create_key`/`keys`/`revoke_key`/`project_for_key` (a key is `vrk_…`, shown once, only its hash stored). Refusals are `AccessRefusal` (a `Refusal` with an HTTP status).
- `src/vrum/db.py`: besides the pool and `prepare_schema`, how work is bound to a project: `working_for(project_id)` sets the project for everything done inside it (a `ContextVar`), `Database.transaction()` is the project-scoped transaction (it does `set_config('vrum.project_id', …)` and `SET ROLE vrum_project`, so the database shows only that project's rows; with no project named it raises `NoProject` and the database shows none), and `Database.admin_transaction()` is for what is not a project's own work (accounts, projects, keys, the index job, building the schema). Never use `admin_transaction` for graph data in a tool.
- `src/vrum/schema.sql`: the whole database in one file: the account tables, then the graph tables, constraints, triggers and the `node_state`, `decision_state` and `memory_state` views. Every graph table has a `project_id` that is part of its primary key and of every foreign key, so a row cannot refer to a row of another project; each project numbers its own nodes, links, rules, facts and beliefs, decisions and events from 1 (a sequence per project and kind, made when the project is made, read with `next_id(kind)`; `continue_ids_after` sets it after an import); and row-level security with a policy `project_id = current_project()` on every graph table, for the role `vrum_project` (the server switches to it for each project transaction; it has only the rights listed at the end of the file and none on accounts, sessions, projects or keys). Views are `security_invoker`. The derived index tables made by `indexing.py` carry a `project_id` and the same policy. A new graph table needs `project_id`, composite keys, the policy and the grants.
- `src/vrum/common.py`: what the modules below share: `Refusal` (the plain-English refusals), argument checks (including `parse_day` for dates), paging, and database helpers.
- `src/vrum/graph.py`: the one owner of epics, stories and tasks (`Graph`), and of how a node is read (`node_state`, backed by the `node_state` view that decides what `ready` means).
- `src/vrum/query.py`: the one owner of the filter language (words, `field:value`, commas, `OR`, a leading `-`, `no:field`, date ranges, `is:overdue`). `compile_query(text)` returns a condition on the `node_state` view with every value passed as a parameter, or refuses in plain words; `Graph.list_nodes(query=...)` ANDs it with the other filters, so the board's filter box and the agents' `list_nodes` give one answer. The board does not parse the text: it sends it as `query` to `list_nodes` (`filterbar.js`).
- `src/vrum/links.py`: the one owner of links. `src/vrum/claims.py`: the one owner of claims, leases and the handoff note that ends one (`next_work` and `finish_work` use its helpers), and `Claims.who_is_working` (every claim in force or lapsed, the latest handoff of each agent and the server's clock, for the Activity page; read only).
- `src/vrum/rules.py`: the one owner of rules and the coverage report. `src/vrum/decisions.py`: the one owner of decisions and principles, their links and supersession.
- `src/vrum/memories.py`: the one owner of facts and beliefs: their evidence and links, replacing and retracting them, confirming a belief and promoting it to a decision (staleness is worked out by the `memory_state` view). `src/vrum/recall.py`: `recall`, everything known about one node or rule by exact links, from decisions and memories. `src/vrum/references.py`: the one owner of the reference syntax (`[[node:12]]`, `[[rule:3]]`, `[[decision:7]]`, `[[fact:5]]`, `[[belief:2]]`: one `REFERENCE_PATTERN`, which `references.js` repeats byte for byte and `tests/test_references.py` compares) and of `find_mentions`, which works out in SQL, when asked, which texts (bodies, decision texts and reasons, fact and belief texts and sources; never titles) name which items, and stores nothing. A reference is only text: it makes no link, readiness or order. With no target it lists every reference (the graph's mentions layer uses that).
- `src/vrum/embeddings.py`: the one small interface to an OpenAI-compatible embedding service (text in, vectors out). `src/vrum/llm.py`: the same for a chat service (one question in, a JSON object out; it never decides whether an answer can be believed). `src/vrum/secret_formats.py`: recognises secrets in well-known formats (`find_secret`, `find_secret_in` for nested arguments, `redact_secrets`), used before text is sent to a model and by M6 on every tool argument and on every write (`common.refuse_secrets`).
- `src/vrum/reflection.py`: the four tools that need a language model (`extract_facts`, `consolidate_memory`, `find_contradictions`, `reflect`) and the checks on what a model says: a passage must be in the text, evidence must be among what it was given, quotes must be there, citations must be of what was retrieved. It writes only through `Memories` (origin `extracted` or `derived`) and logs each answered call as a `model_call` event.
- `src/vrum/indexing.py`: the semantic index and its reindex job, the only code that creates, changes or drops the index tables (`semantic_index`, `semantic_index_info`, which are derived and not in `schema.sql`), plus the background task that keeps it current. `src/vrum/search.py`: search by words, meaning or both, similar items and the overlap finder (read only). Exact-words search reads the `search` columns of the graph tables. `src/vrum/status.py`: `server_status` (versions, the size of each kind of item, the index state with a live probe of the embedding service, and the language model); the last reindex is kept in memory by `Indexer.last_run`, so it is empty after a restart.
- `src/vrum/workflow.py`: what an agent does in a day's work, built on the owners above and not repeating them: `next_work` (pick, claim and brief in one transaction, with the context cut to a size), `finish_work`, `create_plan` (check a whole plan, then create it in one transaction), `update_nodes`, `changes_since` (a feed that never skips a late event; with `newest` it reads the newest events backwards and `before_event_id` goes further back, since events are ordered by `(xid, id)` and not by id), and `create_node`'s check for similar items.
- `src/vrum/server.py`: the MCP tools (thin: they call `Graph` and the other owners), the server instructions, the background reindex task, and the health route.
- `src/vrum/exchange.py`: moving the whole graph as data: `export_graph`'s pages (everything in id order, as plain text and numbers) and `import_graph` (a file is read and checked, every problem listed at once, then loaded into an empty database in one step with its ids; the endings of replaced and retracted things are applied last so that the database's own rules are never bypassed). `src/vrum/markdown.py`: `render`, a pure function from an export to the files of the read-only Markdown copy.
- `src/vrum/guard.py`: `GuardedServer`, the MCP server every tool call goes through: it refuses a secret in any argument before anything else, decides the project of the call (from the agent key in the call's own request headers, looked up again on every call so a revoked key stops at once, even on an open connection; a call the board makes in-process is for the project the board has already shown the person owns), runs the tool `working_for` that project, turns the SDK's validation errors into plain messages that do not repeat what was sent, and logs one line per call (with the project number). `src/vrum/access.py`: the `AccessGuard` around the whole web app: an agent key (valid and not revoked) on everything under `/mcp`, the board's page files and `GET /health` open, the board's `/board/api` calls handed on to the board (they carry a session cookie, checked there), and the request size limit, answering with plain JSON-RPC errors. `src/vrum/logs.py`: the JSON log format and the scrub that removes passwords, keys, sessions and secret formats (`vrk_…` agent keys and `vrs_…` sessions are formats too, so they are also refused in any text an agent writes) from every line.
- `src/vrum/board/`: the board. `__init__.py` is its server side (`add_board`): the page files under `/board` (open, since they hold no data; every response carries the content security policy; `/board/p/<id>` serves the same page), the accounts routes (`POST /board/api/accounts` to register, `POST`/`GET`/`DELETE /board/api/session` to sign in, ask who is signed in and sign out, `GET`/`POST /board/api/projects` and `GET /board/api/projects/<id>`, and `GET`/`POST /board/api/projects/<id>/keys` with `DELETE …/keys/<key>`), and, for a project the signed-in person owns (checked on every request, never in the browser), `POST /board/api/projects/<id>/tool/<name>` (calls the MCP tool of that name on the same server for that project, so every board action is the same operation as the matching tool, with the same refusals; only the tools in `READ_TOOLS` and `WRITE_TOOLS` may be called, and a test checks they exist and that `reindex` is not among them), `GET …/index` (how many items wait to be indexed) and `POST …/try/<name>`; `GET /board/api/info` and `GET /board/api/tools` need a session only. `board/session.py` is how the board knows who is asking: the cookie `vrum_session` (HttpOnly, SameSite=Strict, Path=/board, Secure on https), the check of a session's CSRF secret in the `X-Vrum-CSRF` header and of the `Origin` on everything that changes something, and the same-site JSON check on sign-in and registration. `static/` holds the pages: plain HTML, CSS and ES-module JavaScript with no build step and no library. Text is only ever put on a page as text (`dom.js` builds elements; a test fails on `innerHTML` and the like), and there is no inline script or style. `app.js` is the shell (the person's projects, the top bar with the project switcher, the address, the clock; switching project is a whole page load), `entry.js` the sign-in, registration and project-list pages and `access.js` the Agent access page (keys; the secret is shown once), `api.js` talks to the server (the session's CSRF secret, the project's number in every path, and an answer that arrives after the project was left is dropped as `Stale`), `store.js` holds the copy of the graph and polls `changes_since`, `kanban.js` the Kanban page, `card.js` the card of one item, `panel.js` the side panel, `coverage.js`, `create.js`, `graph.js` (drawing, zoom, pin, lists), `graph-data.js` (what the switches and scopes show) and `layout.js` (the force layout). M11 added `filterbar.js` (the filter box all the list pages share, and `loadRows`: an empty filter reads the store, anything else asks `list_nodes` with `query`), `table.js` (sort and group in the browser on the rows the server's filter returned; in-place edits and the bulk change through `update_node` and `update_nodes`, each at the version the row was shown at), `outline.js` (an ARIA tree; every drop is `move_node`, so the server refuses nonsense), `roadmap.js` (bars from `span_start` to `span_end`; every drag, key and tray drop is `update_node` or `update_nodes`, never clamped, so the server refuses a start after the target) and `dates.js` (UTC day arithmetic, the same day the database uses). M12 added `forms.js` (dialogs, labelled fields, and the pickers for what a record concerns and for a belief's evidence; no field is `required`, so a blank is sent and the server's refusal is what a person reads), `entries.js` (how a decision, fact or belief is shown, with its origin, who, evidence, chain and why; the Memory page and the recall preview both use it), `rules.js` (the Rules page: groups by story with the unplaced rules first, the coverage report below it from `coverage.js`, and a drop onto a story is `place_rule` for a rule in no story and `move_rule` for one that is in a story), `memory.js` (the four lists, their filters, which run in the browser over the lists the store holds, the choosing of facts and beliefs to change together, and what a retraction led to), `memory-forms.js` (every dialog: record, replace, retract, confirm, promote, what it concerns, and the check of a statement against every belief through `find_contradictions`) and `recall.js` (the recall preview: the same `recall` call an agent makes, drawn in its sections with its reasons). M13 added `markdown.js` (`renderMarkdown`: headings, paragraphs, lists, emphasis, code, quotes, `http(s)` links that open in a new tab, built only from text nodes, so raw HTML and an image are shown as the text they are), `references.js` (turns `[[kind:id]]` into a link with the current title or a plain "missing", `refreshReferences` after every batch of news so a rename is followed, `mentionsList` and `mentionedInDetails` for "Mentioned in", and `loadTargets`, which reads the rules, decisions and memories a title needs), `reference-picker.js` (`withReferences(control)`: the `[[` pick-list on a textarea or input; it only writes text), `search.js` (the Search page: the server's `search` read to the end with `callPaged`, with the counts and the type, status and epic filters worked out in the browser over the whole list, and `index()`, which `app.js` calls when the waiting count changes), `ask.js` (the Ask box over `reflect`: the answer is generated, labelled, stored nowhere, and can be recorded as a belief only by a person), `overlaps.js` (the Overlaps page over `find_overlaps`: the threshold and epics are in the address, `Mark as…` is `add_link`) and `switcher.js` (the Ctrl+K / ⌘K quick switcher, which only navigates). `dom.js` has `put(el, ...children)`, which replaces what an element holds and leaves out empty children: a bare `append` or `replaceChildren` with `null` or an array writes "null" or "[object HTMLElement]" on the page. A page exports `mount`, `unmount`, `update(params)` and `refresh(events)`. There is no inline style either (the policy turns it away): `h` has a `css` property that sets `element.style`, and a test fails on a `style:` attribute. `static/brand/` holds the logo and icons. A later board milestone adds its pages as modules like these and the tools they need to `READ_TOOLS` or `WRITE_TOOLS`. A page script may not name a tool in quotes that is not on those lists, so keep tool names out of the words a page shows. M14 added the last four pages: `home.js` (the numbers: a node count is `list_nodes(query, limit 1).total`, the coverage numbers `coverage_report`, the beliefs and overlaps the store; each is a link that lands on the page showing exactly those items), `events.js` (`describe`, every action in plain words, and `eventRow`, which shows a handoff note in full), `activity.js` (the feed over `changes_since`, newest first, and the claims panel over `who_is_working`, `claim_node`, `renew_claim` and `release_claim`, with a one second countdown), `tools.js` (the Tools page over `GET /board/api/tools`, and "Try it" over `POST /board/api/try/<name>`) and `status.js` (the Status page over `server_status` and the export download). `src/vrum/board/tools.py` is the map from every MCP tool to where it is on the board (`OnTheBoard`) or why it is for agents only (`AgentsOnly`); `tests/test_board.py` fails when a tool the server has is in neither, or the map names one it does not (set `VRUM_TEST_DROP_FROM_MAP=<tool>` to see it fail once). Which tools change something is not listed by hand: it is the server's own `read_only_hint` annotation (`_READS` in `server.py`), and the board's try route refuses any tool the live server does not mark read only. A new tool needs one of those annotations if it only reads, and an entry in the map.
- `src/vrum/__main__.py`: starts the server (the logs are set up here). `src/vrum/healthcheck.py`: the container health probe.
- `tests/`: unit tests, plus the integration tests (marked `integration`, driven by `./check.sh`): `test_mcp_integration.py`, `test_graph_integration.py`, `test_links_and_claims_integration.py`, `test_rules_integration.py`, `test_decisions_integration.py`, `test_memories_integration.py`, `test_search_integration.py`, `test_workflow_integration.py`, `test_reflection_integration.py`, `test_hardening_integration.py` and `test_exchange_integration.py` go through a real MCP client (`test_hardening_integration.py` also uses raw HTTP for what a caller that is not an MCP client is told, and reads the container's log; `test_exchange_integration.py` also runs `scripts/export_graph.py` and `scripts/export_markdown.py` as a person would); `test_exchange_second_stack.py` starts a second, separate copy of Vrum (`second_stack.py`: its own compose project `vrum-restore`, volume, port `VRUM_CHECK_PORT` + 3 and token, which `check.sh` also removes if a test dies) to destroy and load databases: the import round trip, and `backup.sh` then `restore.sh` into a fresh container; `test_index_writers.py` proves from the source that only `indexing.py` writes to the index; `scripted_embeddings.py` and `scripted_model.py` are the stand-in embedding service and language model the check stack runs (`compose.check.yaml`), so checks need no model download (a test scripts the model with `ScriptedModel` in `helpers.py` and reads what it was sent); `test_database_constraints.py` runs SQL inside the real database container to prove the database refuses bad data on its own. `helpers.py` holds the small shared test helpers (including `connect`, which opens a client with a token, `export_everything`, and `rich_world`, one of everything the graph holds made through the tools); `documents.py` builds export files by hand. The unit tests `test_access.py` (the guard, the log scrub), `test_guard.py` and `test_init_env.py` cover the M6 pieces that need no containers, `test_exchange.py` (reading a file to import) and `test_markdown.py` (the Markdown copy) the M7 ones, and `test_readme.py` the M9 one: the README's agent guide is `INSTRUCTIONS` word for word, and the files, settings and tools it names exist. `test_board.py` covers the board's server side (which tools its pages may call, what is open without a token, that the pages load nothing from elsewhere, never put text on a page as HTML and never use a style attribute, and that every tool the live server has is on the board or marked for agents only). `test_status_integration.py` goes through a real MCP client: `server_status`'s sizes against the list tools, the index against what `search` reports, a stopped embedding service, the server with no model, and `who_is_working`. The M14 browser tests are `test_board_home_integration.py` (every number against the tools, and where it leads), `test_board_activity_integration.py` (an agent's work, a person's claim, a claim that lapses, the filters), `test_board_tools_integration.py` (the list against the server's, Try it, no Try it for a write) and `test_board_status_integration.py` (Status, the export and the secrets never shown), with `board_m14.py` holding what they share. `test_query.py` covers the filter language's reading and its refusals with no containers. The board's integration tests drive Playwright's Chromium (a development dependency only, never in the app image; `./check.sh` and `./acceptance.sh` run `uv run playwright install chromium`, which downloads it once): `test_board_integration.py` (Kanban, card, refusals, index, text only, keyboard), `test_board_graph_integration.py` (the graph; its "Everything" test runs on a second, empty copy of Vrum from `second_stack.py`), `test_board_tables_integration.py` (Table, Outline and the address of a view) and `test_board_roadmap_integration.py` (the Roadmap), `test_board_rules_integration.py` (the Rules page) and `test_board_memory_integration.py` (the Memory page, its dialogs, the check with the scripted model, and the recall preview compared section by section with `recall`), `test_board_search_integration.py` (the Search page with the embedding service stopped and back, compared with `search`; the counts compared with the list tools; Ask with the scripted model, and on the second server with no model), `test_board_overlaps_integration.py` (the Overlaps page compared with `find_overlaps` on M5's fixture; a click makes exactly one link) and `test_board_references_integration.py` (Markdown that is only text, references and their renames, "Mentioned in" compared with `find_mentions`, the pick-list, the quick switcher on every page, the graph's mentions layer), plus `test_references.py` (the pattern, with no containers) and `test_references_integration.py` (`find_mentions` through a real MCP client), with `board_helpers.py` for the browser (it also holds what the tests share, such as `made`, `plain` (a board's words are an MCP refusal's words), `shown_ids`, `drag_bar`, `asked`, `listed`, `facet`, `pairs_on`, `twin_epics` and `links_of`, and `hold_back_news`, which makes the board hear of no news so that a test can change something behind its back and see a stale change refused). Overlap fixtures repeat across tests, so the Overlaps page may hold more than one page of pairs: read them all with `pairs_on` before looking for a row. A test that follows a change of address polls until the page shows it (`lists_are`), since `location.hash` is handled a moment later. `test_query_integration.py` goes through a real MCP client: each kind of term, the combinations, and the refusals of `list_nodes(query=...)`. Use unique words in titles and `epic:<id>` in a filter (or the `epic=` address) to keep a test to its own epic, since all tests share one database (so never compare a count of everything in the database while another test may be running), and give the browser a tall window (so that nothing scrolls during a drag).
- **Tests and projects (M15).** Every integration test works inside a project it did not invent: `tests/world.py` registers accounts, makes projects and agent keys through the board's real HTTP API (`register`, `make_project`, `the_project()` is the one project almost every test shares, `Person.call` is the board's API as a signed-in person, `api` is one raw request with the cookie, CSRF secret and `Origin` the page would send). `helpers.the_token()` returns the shared project's agent key (the name is older than keys), `board_helpers.board_url` gives a project's board address and `browser_page(token=…)` starts the browser signed in as that project's owner with a session of its own. Ids are per project, so **direct SQL as the database owner sees every project's rows with colliding ids**: `run_sql(..., as_project=True)` runs as the project role (the rows of the shared project only, as the server sees them), and a statement that must run as the owner to prove a constraint (`UPDATE`, `DELETE`, an `INSERT` that must be refused) names its project (`WHERE project_id = … AND id = …`). `test_accounts_integration.py` is accounts, sessions, rate limits, CSRF, projects and keys, `test_projects_isolation_integration.py` is the walls between projects through tools and through the database (three projects, ids that exist in only one, forged arguments, search, recall, claims, feeds, the index, direct SQL as the owner and as the role, export and import into another project), `test_accounts.py` the hash and the limiter without containers, and `test_board_accounts_integration.py` registering, signing in, creating and switching projects and making keys in a real browser.
- `README.md`: what a person reads first: quick start, accounts, projects and agent keys, connecting an agent, the agent guide (a copy of `INSTRUCTIONS` in `server.py`, which `tests/test_readme.py` keeps equal; change both together), backup and restore, settings. A milestone that changes what a person does adds it here.
- `acceptance.sh` and `tests/acceptance*.py`: the acceptance scenario. `acceptance.sh` brings up the throwaway stack and calls `tests/acceptance.py`, which runs the chapters in order (`arriving`, `planning`, `working`, `decisions`, `remembering`, `finding`, `model`, `hardening`, `board`, `views`, `memory`, `connecting`, `running`, `accounts`, `moving`; the chapters are in `acceptance_scenario.py`, `acceptance_finding.py`, `acceptance_model.py`, `acceptance_board.py`, `acceptance_views.py`, `acceptance_memory.py`, `acceptance_connect.py`, `acceptance_run.py`, `acceptance_accounts.py` (M15: it reuses the helpers of `test_accounts_integration.py`, `test_board_accounts_integration.py` and `test_projects_isolation_integration.py`) and `acceptance_moving.py`). Each `proof(milestone, what, held, detail)` prints one line and stops the run with a plain message when it does not hold. It reuses `helpers.py`. It is a walk, not a second test suite: a proof about the source code (`test_index_writers.py`) stays in `check.sh`, and the scenario shows what can be seen from outside. Add the proofs of a new milestone to the chapter they belong to, or a new chapter.

## Working rules

- One milestone per iteration: the first unchecked one in `PROGRESS.md`. Never start the next one.
- A milestone is finished only when its "Proof" in `SPEC.md` passes against the real containers and a real MCP client, with every earlier proof still passing.
- Product decisions that `SPEC.md` does not answer go in `BLOCKED.md` (question, 2 to 3 options, a recommendation, the default you would take). Do not invent answers.
- Defaults the owner may veto are recorded in `DECISIONS.md` and listed under "Defaults taken" in `PROGRESS.md`.
- **No migrations.** Vrum is a prototype with no customer data. The whole database is `src/vrum/schema.sql`. To change the schema, edit that file, tidying it as if it had always been this way, then rebuild the database from scratch: `docker compose down --volumes`, then `docker compose up -d --build --wait` (`./check.sh` already builds a fresh one every run). Do not write migration files, `ALTER TABLE` patches or data-preserving upgrade steps. Reconsider only when a database holds data someone cares about. (Owner's decision, see `DECISIONS.md`.)
- **Prototype stance.** Do not carry production habits that protect data or users that do not exist yet: no backward compatibility, deprecation paths or upgrade steps. When a design changes, change it everywhere and rebuild. Anything `SPEC.md` asks for is still built as written.
- Never commit a secret. Configuration comes from the environment.
- Never touch any Deelio repository or the Taiga project.
- No placeholder or shell code, and no abstraction without a consumer.
- Keep every change small and reviewable. Plain English in every message a person or agent reads.
- The MCP SDK is v2 (`from mcp.server import MCPServer`, `from mcp import Client`); its documentation is at https://py.sdk.modelcontextprotocol.io/. Check it before using an SDK feature.
