# Decisions

The owner's decisions about vrum, newest last. The defaults in section 3 of `SPEC.md` stay in force unless an entry here changes them. Each change names who decided it.

## 2026-11-14: spec defaults adopted as written

- **What:** Python 3.12, the official MCP Python SDK, PostgreSQL with pgvector in the same compose file, streamable HTTP bound to localhost, locally hosted embeddings, and a caller-named actor on every write.
- **Decided by:** the loop, taking the defaults in `SPEC.md`. Waiting for the owner's veto.

## 2026-11-14: choices made while building M0

These fill gaps the spec leaves open. None changes a spec default. The owner may veto any of them.

- **MCP SDK version:** `mcp` 2.x (the SDK's current major version, with `MCPServer` and `Client`), pinned to `>=2.3,<3` and locked in `uv.lock`.
- **Python tooling:** `uv` for dependencies, `ruff` for lint and format, `mypy --strict` for types, `pytest` for tests.
- **Database image:** `pgvector/pgvector:pg17`. The database port is not published to the host; only the app is reachable.
- **Database driver:** `psycopg` 3 with its async connection pool.
- **Authentication:** none until M6; M6 added a required bearer token (see "choices made while building M6"). The server binds to `127.0.0.1` by default through compose, and the token is still sent in clear over HTTP, so a non-local address needs TLS in front of it.
- **Health check:** `GET /health` is the one request that needs no token, and says only `ok` or `unavailable` (M6 made it the only one).
- **Database password:** read from `VRUM_DB_PASSWORD`, with no default. `./scripts/init-env.sh` writes a random one to the git-ignored `.env`.
- **Port:** the server listens on `VRUM_PORT` (default 8000) and compose publishes the same number on the host, because the server only accepts requests addressed to `localhost:<that port>`.

## 2026-11-15: choices made while building M1

These fill gaps the spec leaves open. None changes a spec default. The owner may veto any of them.

- **Ids:** whole numbers given by the database, starting at 1, shared by epics, stories and tasks. They are short enough for an agent to type and read.
- **Priority:** four named levels, `low`, `normal` (the default), `high` and `urgent`, rather than a number whose direction an agent would have to guess.
- **Status:** a node can be `new`, `in_progress`, `blocked`, `done` or `dropped`, and can move freely between them; no workflow rules are invented. `ready` is never stored and cannot be set. M2 works it out from the links, so until then a node shows only its stored status.
- **One parent, one way to change it:** `move_node` is the only way to change a parent. `update_node` also accepts `parent_id` for one reason only: so that an attempt to give a node a second parent is refused with a plain message that points to `move_node`.
- **History:** every create, update and move is an event with the actor, the time, and the changed fields as they were and as they became, each with the node's version. A create lists every field. `node_history` returns them oldest first.
- **No deleting:** there is no delete tool (use status `dropped`). The database also refuses to delete a node that has history, which is every node, and refuses to change or delete an event.
- **Paging:** every list takes `limit` (1 to 200, default 50) and `after_id`, and returns `next_after_id` until the last page. Items come in id order.
- **Titles and actors:** a title or actor that is blank is refused; surrounding spaces are trimmed. Actors are free text, with no list of known actors.
- **Schema changes:** ~~numbered SQL files in `src/vrum/migrations/`~~ Replaced the same day by the owner's decision below: there are no migrations.

## 2026-11-15: choices made while building M2

These fill gaps the spec leaves open. None changes a spec default. The owner may veto any of them.

- **What `ready` shows:** the spec's rule is followed to the letter. A node nobody has started shows as `ready` when everything it needs first is done, and that includes a brand-new node that needs nothing. So the status `new` now means "not started, and waiting for something it needs first". What can be set is unchanged (`new`, `in_progress`, `blocked`, `done`, `dropped`); `ready` is only ever worked out, by the database view `node_state`, and `waiting_on` lists what a node still waits for.
- **Only `done` counts:** a prerequisite that is `dropped` or `blocked` keeps its dependents waiting. If a prerequisite no longer applies, remove the `needs_first` link.
- **Links:** allowed between any two nodes, whatever their kinds. `duplicates` and `relates_to` work both ways, so A to B is the same link as B to A. `supersedes`, `duplicates` and `relates_to` are records only: they change nothing else, such as a status. `list_links` was added so that what is written can be read.
- **Circles of waiting:** refused by the database, which takes a lock so that two links added at the same moment cannot each look fine and together make a circle. The refusal names the whole circle.
- **Claims:** only stories and tasks. A node can be claimed when it is `ready` or `in_progress` and nothing it needs first is open; done, dropped and blocked work and epics are refused with a reason. A claim does not change the node's status and does not stop other people editing the node: it says "I am working on this".
- **Leases:** `lease_seconds` is 1 to 86400 (24 hours), default 900 (15 minutes). A claim lapses on its own with no action. Only the holder can renew (and only before it lapses) or release. Another actor can take over a lapsed claim, and the history records who held it before.
- **`ready_work`:** stories and tasks that are ready and not claimed (`kind` can ask for epics instead), oldest first. Priority is shown on each item but does not change the order, so that paging stays simple.
- **History:** a link event shows in the history of both nodes. Claims and releases are events; a claim lapsing is not, because nothing happens at that moment.

## 2026-11-15: no migrations (owner's decision)

- **What:** the database has no migrations. The whole schema is one file, `src/vrum/schema.sql`, applied to an empty database when the server starts. To change the schema, edit that file and rebuild the database from scratch (`docker compose down --volumes`, then `docker compose up -d --build --wait`). This replaces the numbered migration files and their runner, which were built out of production habit.
- **Why:** Vrum is a prototype with no customer data. Migrations exist to keep a database that already holds real data alive through a change, and there is none to keep. They cost a runner, a history table and the discipline of never editing an applied file, and they would leave the schema as a pile of patches instead of one readable file.
- **One small safeguard kept:** the server records which version of the schema built the database, and refuses to start on a database built from a different one, saying in plain words to rebuild it. That replaces a confusing SQL error with one sentence. It is a few lines and can be removed if the owner prefers.
- **When to reconsider:** when a database holds data someone cares about.
- **Decided by:** the owner (@marie-schmidt).

## 2026-11-15: other production habits looked for (loop's findings, open to veto)

The owner asked the loop to look for other things done out of production habit. Nothing else in the code protects data or users that do not exist yet. What was found:

- **Removed with the migrations:** the proof step "restart the stack and check the data survived and nothing was applied twice". It only mattered because of the migration runner. A restart check that the data survives stays useful, but is no longer a proof step.
- **In `SPEC.md`, so the owner's call, not changed by the loop:** M7's backup and restore scripts and its "destroy the volume, restore" proof exist to protect data that does not exist yet. M7's full export and import as JSON is still useful (the Taiga export and the M8 trial need it). Recommendation: keep export and import, drop the backup and restore scripts and their proof until there is data worth saving. M6 hardening (token, size caps, logs without secrets) is spec'd as written and is cheap, so it stays.
- **Kept on purpose, cheap and asked for by the spec:** the database refusing bad data itself (`SPEC.md` section 1), versions on every edit, the append-only event log, and plain refusals.
- **Kept, small, and easy to drop if the owner wants:** the container runs as a non-root user, the image build is multi-stage, and strict type checking is on.

## 2026-11-15: choices made while building M4

These fill gaps the spec leaves open. None changes a spec default. The owner may veto any of them.

- **A decision is a record, never edited.** There is no `update_decision`. A change of mind is `supersede_decision`: it records a new decision and marks the old one `superseded`, pointing at its replacement, in one step. The database refuses to edit or delete a decision, and refuses to change a superseded one again. A typo is fixed the same way, by superseding. The old text stays, which is the point of a memory.
- **Who is who:** `decided_by` is the person who made the decision (required, the spec says a named person). `actor`, as everywhere, is whoever recorded it, often an agent. There is no list of known people, so `decided_by` is checked only for not being blank.
- **Required fields:** title, text, reason and `decided_by` cannot be blank. The spec lists a reason as a field of a decision, and a decision without its reason is poor memory. `decided_on` defaults to today (UTC) and can be given.
- **Replacing:** a decision can be superseded once. Two agents replacing it at the same moment give one winner; the other is told to supersede the replacement instead. A replacement may be of the other kind, so a decision can become a principle (and the reverse). Replacements are always recorded after what they replace, which the database checks, so they cannot form a circle.
- **Links carry over:** by default (`keep_links` true) a replacement affects what the old decision affected, so that it does not silently drop out of recall; ids given are added, and `keep_links` false starts it with only those. The old decision keeps its links as a record, and its links cannot be changed (the database refuses it); change the replacement's instead.
- **Links:** `link_decision` and `unlink_decision` take lists of node ids and rule ids and change nothing if any is wrong, missing, already linked or not linked. Only active decisions can be relinked.
- **Recall is by exact link and nothing else:** `recall_decisions` takes a node id or a rule id and returns that item's active decisions, every active principle (linked or not), and its linked decisions that have been superseded. Decisions linked to its parent or children are not inferred, so an agent recalls those as well if they matter. A linked principle appears under principles, not under decisions. Each of the three lists is paged on its own with `show` and `after_id`, with counts for all.
- **Active principles:** there is no separate tool; `list_decisions` with `kind=principle` and `status=active` is the list.
- **History:** every recording, link, unlink and supersession is an event. A link event also shows in the history of the node or rule it names. A decision's own history is `decision_history`. The old decision's `decision_superseded` event is in its own history only.

## 2026-11-15: the goal, the product shape and the research behind it (owner's request, loop's choices open to veto)

- **What the owner asked for:** a graph view and a Kanban view in M10, an overview of the MCP tools, and the other pages needed to see every part of the product, as a mix of GitHub Projects, Obsidian, Hindsight or Elasticsearch, and Taiga's MCP capabilities, "but better and complete", with the target goal "effective, efficient, agent and human friendly coding project management". The owner asked for each product to be researched so the intended overlap is clear.
- **Research:** six read-only research threads, each from the product's own documentation: the five products, plus what already works for agents and humans managing work together (Beads, Claude Code task lists, Linear, Task Master, Backlog.md, the Copilot cloud agent). Their conclusions are summarised in `SPEC.md` section 10, with a source for each product. Hindsight and the agent tools gave the clearest lessons: an agent needs one call for the next work with its context, handoff notes, and small answers; and memory must not be written by a language model.
- **Decided by:** the owner asked for the views and the goal. Everything below is the loop's choice, open to veto.

**What changed in the spec**

- **Goal and section 10** added to `SPEC.md`: the goal, a table of what Vrum takes from and deliberately leaves out of each product, the ten capabilities that matter most, and the list of pages.
- **M5 now also does exact-words search.** Reason: Elasticsearch and Hindsight both show that meaning-only search is weaker than words plus meaning, each labelled; PostgreSQL full-text search is in the one database, is never stale, and keeps working when the embedding service is down. It was going to be in M12; it is cheaper and safer to build it with the index.
- **New M5B, agent workflow**, placed right after M5 and named M5B so that no milestone is renumbered: `next_work` (claim the next work and get its context in one call), `finish_work` and a required handoff note, `create_plan` (a whole plan, all or nothing), `update_nodes` (any number of changes, reported one by one), `changes_since` (what changed after an event), compact lists, a similar-items check on create, and server instructions. This changes M2 (release now needs a note) and the shape of earlier answers (lists leave out bodies by default). Under the prototype stance that is done everywhere and the database is rebuilt.
- **M6** refuses text containing a well-known secret format (known token prefixes, private key blocks). It refuses instead of quietly rewriting the text, so nothing is changed behind the writer's back; only well-known formats are checked, to avoid false refusals.
- **M7** adds a read-only Markdown export (one file per item, links as `[[references]]`) next to the JSON export.
- **M9** adds an agent guide to the README, the same text as the server instructions.
- **M10** gains the graph view (global with a cap of 300 items, local at 1 to 3 steps, typed lines, overlap suggestions shown dashed), the page bar and shareable addresses, and progress counts on epics and stories.
- **New M11 to M13** (the other pages): Table, Outline, Rules and Memory with editing, and one filter language shared by people and agents; Search, Overlaps, Markdown, `[[references]]`, "Mentioned in" and a quick switcher; Home, Activity with "Who is working on what", Tools (generated from the live tool list, with a test that every tool is accounted for) and Status.

**Choices and defaults taken, open to veto**

- **Order inside the next-work call:** highest priority first, then oldest. `ready_work` keeps its oldest-first order. `next_work` also marks the item in progress, so the board shows it.
- **Handoff on release:** `release_claim` needs a note. A claim that lapses has none, and says so.
- **Plan size:** no cap on the number of items in one `create_plan` or `update_nodes` (the first draft said 200 and 50, a production habit; removed on the owner's request, 2026-11-15). Only M6's cap on the size of a whole request applies. The one-transaction cost is small at this scale.
- **Graph:** drawn by the board's own code, no library, no internet. Pinned dot positions are kept in the browser only.
- **Views are addresses:** filters and layout live after the `#` in the address. The server stores no views.
- **Markdown (replaces M10's plain-text default):** M10 still shows plain text. M12 adds a small renderer: no raw HTML, no images, web links open in a new tab.
- **References:** `[[node:12]]`, `[[rule:3]]`, `[[decision:7]]`, exact ids only, no matching by title. They are text only and change no link, readiness or order. "Mentioned in" is worked out when asked and stored nowhere.
- **People can do what agents can**, except `reindex` and import. A person can claim, renew and release with a typed name. There is no override of someone else's claim: a claim lapses by itself.
- **The Tools page** has "try it" for tools that only read. Anything that changes data goes through the board's own forms.
- **Home becomes the landing page in M13.** Until then the board opens on the Kanban page.

**Questions for the owner, not built, each with a recommendation**

Recommendation: a one-off Taiga dump exporter after M10 that flattens to one epic per story and writes rules and decisions into descriptions; not before there is a reason.
- **Approval gate for plans.** Task Master and Backlog.md have a point where a person approves a plan before work starts. Recommendation: not now; `create_plan` creates ordinary `new` items that a person sees on the board and can drop. A real draft state can be added if the owner wants it.

- **Issues as a kind, a wiki entity, attachments, custom fields.** Taiga has them. Recommendation: none. Bodies, `[[references]]` and "Mentioned in" cover most of what a wiki is for; an issue is a task with a title that says so.

The owner also asked for the earlier milestones M0 to M4 to be fixed retroactively where needed, with milestones named M0A, M1A and so on, or one special phase run before M5.

- **Decided by:** the owner for the three changes. Everything below is the loop's choice, open to veto.

**Milestone changes**

- **Retro-fixes, as two small milestones rather than one phase.** Each has its own proof, and both run before M5. They are listed in `PROGRESS.md` where they belong (M1A after M1, M4A after M4), so the loop picks M1A first. They change the already-built M1 and M4, and under the prototype stance the database is rebuilt, with no upgrade step.
    - **M1A, dates:** an optional start date and target date on every node, with the database refusing a start after the target; overdue, the worked-out span for an epic or story without dates, and schedule conflicts are all computed.
    - **M4A, facts and beliefs:** the explicit memory layer, plus one `recall` that replaces `recall_decisions` and returns everything known about an item in separate labelled sections.
- **M5C, extraction and reflection**, new, after M5B: the parts of Hindsight that need a language model. It is separate from M4A on purpose, so that the explicit layer is finished and proven first and the model part rests on it.
- **UI milestones renumbered** (they were only written a few hours earlier): M10 Kanban and graph, M11 Table, Outline and Roadmap, M12 Rules and memory, M13 Find and connect, M14 Run and see it all. M12 is new: facts and beliefs would have made the old M11 too big to review.
- **M5, M5B, M6, M7, M10 and M13** pick up the new data: facts and beliefs are indexed and searched with their origin, appear in `next_work`'s context (beliefs as suggestions, stale ones left out), are covered by the secret check, are exported, are cards and graph layers, and get `[[fact:5]]` and `[[belief:2]]` references. `next_work` now breaks priority ties by the earliest target date.

**Choices and defaults taken, open to veto**

- **Why facts and beliefs are safe here.** In Hindsight a model writes the memory and nobody can say who is accountable for it. Vrum keeps its rule, "memory suggests, the graph decides", with guard rails: a fact needs a plain-words source; a belief must list its evidence, which can only be facts and decisions (never other beliefs, so a conclusion is one step from what it rests on); a belief goes stale automatically when its evidence changes; a belief is a suggestion until a named person confirms it, and only a named person can promote it to a decision; nothing is ever edited, only superseded or retracted; and what a model proposes is checked against its quoted passage or its evidence, and labelled, before it is kept.
- **An agent is already a model.** Agents can record facts and beliefs themselves through M4A with no server-side model at all. M5C adds the model on the server for people who want extraction and reflection to run without an agent in the loop, and it is off unless `LLM_BASE_URL` is set.
- **Fact kinds:** `world` and `experience`, as in Hindsight. Hindsight's "observations" are called beliefs here. Its "mental models" and pages (answers a model rewrites on a schedule) are not built: they are the most costly part, and the least checkable.
- **Two dates on a fact:** when it was true or happened (optional) and when it was recorded, as Hindsight does.
- **Extraction stores nothing unless asked.** `extract_facts` returns proposals with their quoted passages, and only the store option keeps them. `consolidate_memory` and `reflect` run only when called, never on a schedule, so there is no hidden cost.
- **Testing a model without a real one.** The proof uses a small scripted OpenAI-compatible test service, so it proves what Vrum does with a model's output (dropping unchecked proposals, refusing uncited answers, never sending secrets), not how good a model is. A real model is tried by hand through the optional configuration.
- **Whole graph:** a dot limit of 1,000, above which each epic collapses into one dot that opens on its own, because Obsidian's graph is reported to become unusable at very large sizes.
- **Roadmap:** start and target dates only, no iterations, because sprints remain out of scope. Dates have no time of day. An epic or story with no dates shows its children's span, marked as worked out. A schedule conflict is a warning, never a refusal, because plans change and a refusal would make agents guess dates.
- **Where Hindsight's benefits come from:** recall saying why each entry is there (M4A), exact links plus words plus meaning (M5), and a briefing at the start of work (M5B's `next_work`).

**Questions for the owner, not built, each with a recommendation**

- **Should a belief that a model drew up count toward `next_work`'s context?** Default: yes, labelled as a suggestion, but only if it is not stale. Say if you would rather they appeared only after a person confirms them.
- **Auto-extract facts from every handoff note.** Hindsight does something like this. Default: no, because it adds noise and cost; an agent or person calls `extract_facts` when they want it.

## 2026-11-15: choices made while building M1A (dates)

These fill gaps the spec leaves open. None changes a spec default. The owner may veto any of them.

- **Dates are plain days, written YYYY-MM-DD.** The server reads them itself and refuses anything else in plain words ("next tuesday", a time of day, `30/11/2026`, a day that does not exist), instead of passing on the raw validation error. The same check is used for the list filters. The decision date on a decision (`decided_on`) still uses the SDK's own date check, so a badly written one gives the raw error; it is a one-line change to give it the same wording if the owner wants it.
- **Clearing a date is a request of its own** (`clear_start_on`, `clear_target_on`), never an empty value, so that leaving a field out always means "leave it as it is". Giving a date and clearing the same one is refused, and clearing a date that is already empty counts as nothing to change.
- **The start may equal the target.** A one-day job starts and ends on one day. Only a start after the target is refused, by the tool in plain words and by the database as the last line of defence.
- **Overdue** uses the node's own target date and the stored status: a past target is overdue until the node is `done` or `dropped`. It is judged against the current day in UTC, which is the database's own clock.
- **The worked-out span** (for the roadmap). A node with any date of its own reports its own start and target as they are, even when what is under it reaches further. A story with none reports the earliest start and latest target of its tasks. An epic with none reports the same over its stories, where a story contributes its own dates if it has any and its tasks' span if not. Dropped stories and tasks do not count; done ones do (they are history). A task never works a span out, and `span_worked_out` is true only when the dates were worked out.
- **Schedule conflicts** are listed for a node that has its own start date and needs something first that is not done and has a target date after that start. A prerequisite that is done no longer conflicts, and neither does one with no target date. It is a list of prerequisite ids on the node, a warning only, and nothing is refused.
- **Filters on `list_nodes`:** `start_from`, `start_to`, `target_from`, `target_to` (inclusive, on a node's own dates, so a node without a date never matches) and `overdue`. The one filter language of M11 will cover the same ground in a single text; `undated` is `no:` there and was not added here.
- **History:** a date change is an ordinary update event listing only the dates that changed, as text, with before and after.

## 2026-11-15: what happens when a belief stops being true (owner's question, loop's choices open to veto)

The owner asked whether Vrum can change every belief that is no longer true when a person shares a contradicting belief, or when an agent says the person changed their mind. The spec only covered the case where a belief's own evidence is retracted or replaced (it goes stale). Nothing handled a contradiction, nothing worked on several beliefs at once, and nothing said who may change what a person had confirmed. M4A and M5C now say so, before M4A is built.

- **The server never decides a contradiction itself.** It is a judgement, and a wrong automatic one would silently delete knowledge. A person, an agent or (M5C, proposals only) a model names which beliefs are replaced. This keeps "memory suggests, the graph decides".
- **One call replaces any number.** `supersede_memory` and `retract_memory` take one or more items, all or nothing, with no cap of their own (the first draft said 20, a habit copied from `update_nodes` and `create_plan`, not a need; M6's cap on request size is the only limit). A new belief still needs its own evidence, so a contradicting belief cannot be recorded as a bare opinion.
- **Checking everything is a walk with a count.** `list_memories` pages every fact and belief in id order and reports how many match, and `within` takes an epic, story or task and everything under it. `find_contradictions` has two scopes: `related` (nearest candidates, and it says "looked at N of M" so it is never mistaken for a full check) and `all` (every active belief, in batches by id, with how many are looked at and how many remain, until none). Ordering by id, not by closeness, makes the sweep exact and resumable; the closeness ordering lives in `related`. The cost is one model call per batch, only when called, never on a schedule. Default batch: 25.
- **Staleness is reported, not cascaded by default.** A belief with several pieces of evidence may still hold when one is retracted, so by default it is only shown as stale. `with_dependent_beliefs` retracts every belief resting on the item in one step for the case where the person says they all fall. Both answers list what went stale, so the caller never has to go looking.
- **What a person confirmed needs a person.** Replacing or retracting a confirmed belief needs `said_by` and `quote`. An agent relaying "the owner changed their mind" passes both, and the history keeps the person and the relaying agent apart. A suggestion nobody confirmed can be changed by anyone with a reason. The server cannot prove the person said it, the same as `decided_by` on decisions; it records who is accountable. Default taken: this applies to beliefs only, since decisions already have `supersede_decision` with `decided_by`, and facts a person recorded can be corrected by anyone with a source.
- **A promoted belief's decision is not touched.** Replacing a belief that became a decision reports the decision and leaves it as it is, because a decision is a person's act. Changing it is `supersede_decision`.
- **`find_contradictions` (M5C)** returns proposals with quoted clashes and changes nothing. Without a model, `search` over beliefs gives the candidates and an agent judges them.
- **Not built:** a "contested" label for two active beliefs that disagree and have not been resolved, and automatic checking of every new belief against every old one. Both add noise and cost. Say if you want either.

## 2026-11-15: choices made while building M4A (facts and beliefs)

These fill gaps the spec leaves open. None changes a spec default. The owner may veto any of them.

- **One table for facts and beliefs, with one id set.** A fact and a belief share `memories`, so `get_memory`, `list_memories`, `supersede_memory` and `retract_memory` take any id without saying which. `type` is `fact` or `belief`; `kind` (`world` or `experience`) belongs to facts only. Decisions keep their own ids, so evidence and links name which one they mean (`evidence_fact_ids`, `evidence_decision_ids`, `rests_on_memory_id`, `rests_on_decision_id`).
- **The database does the guarding, not just the tools.** It refuses a fact without a source or kind, a belief with no evidence (checked when the change is saved), evidence that is a belief, evidence that is not active when it is added, an edit or delete of any fact, belief or piece of evidence, a replacement of another type or an earlier one, and a decision promoted from anything but a belief. Staleness is a column of the `memory_state` view, never stored.
- **Stale means an active belief with evidence that is no longer active.** An ended (superseded or retracted) belief is not called stale; it is ended. A stale belief cannot be confirmed or promoted: replace it with a revised belief first.
- **Confirming is once, by a named person.** A second confirmation is refused rather than overwriting the first, so the record of who looked at it is never lost. A replaced belief keeps its confirmation as history.
- **Promoting.** The new decision uses the belief's text unless a different one is given, concerns what the belief concerned, and records `promoted_from_id`. The belief stays active. A belief that already has an active promoted decision cannot be promoted again; once that decision is superseded, it can.
- **Replacements carry links over** (`keep_links`, true by default), as for decisions: a new fact or belief concerns what the old ones did, plus what is added. A fact being replaced by a fact needs a new source, because the old source does not vouch for the new text. Facts of different kinds need the new kind said.
- **Answers list ids, not copies.** `supersede_memory` and `retract_memory` return the ids of the beliefs that went stale and of the decisions promoted from a replaced belief, to be read through `list_memories` (which pages). This keeps an answer small however many beliefs rest on one fact.
- **`recall` has seven sections:** active decisions, active principles, facts, beliefs, stale beliefs, superseded decisions, and past memories (superseded or retracted facts and beliefs). Each has its own count and page, and every entry has a `why`. A belief appears when it is linked to the item or rests on evidence linked to it. The spec's phrase "evidence for a belief linked here" was reworded to "resting on evidence linked here", which is what is built: a fact is never shown only because a belief rests on it.
- **`recall_decisions` is gone**, replaced by `recall`. Its answer changed shape (each section holds items, a count and a next page), and the earlier tests were changed to match.
- **`within_node_id`** takes the item, everything below it, and rules placed in those stories. It matches what is linked directly to them, never what a belief merely rests on.
- **Locking.** Everything that changes memories takes its row locks in id order, and retracting with dependents looks again for new dependents after its locks are held, so a belief recorded at the same moment is not missed. Two tests race these and fail without the locks.
- **Not built, and not asked for by M4A:** `supersede_decision` still does not list the beliefs that went stale because a decision changed; they show as stale in `recall` and in `list_memories` with `stale=true`.

## 2026-11-15: choices made while building M5 (search and the semantic index)

These fill gaps the spec leaves open. None changes a spec default. The owner may veto any of them.

- **Exact words are PostgreSQL full-text search on generated columns.** Each of nodes, rules, decisions and memories has a `search` column that the database works out from the title and body (a fact's source counts a little less), with a GIN index. It is current the moment a row is saved, needs no embedding service, and needs no code in the writers. The language is `english`, so endings are matched ("migration" finds "migrating"). Other languages are searched as plain words, which works but does not match their endings. A query is read the way web search boxes are: all words must be present, quotes for a phrase, `or`, and `-`. It cannot fail on odd characters.
- **Tasks are found by exact words only.** The spec's index covers epics, stories, rules, decisions, facts and beliefs (not tasks), and its search counts tasks by type, so tasks are in words search and out of the index. A task can still be the thing similar items are found for: its text is embedded for that one question and not stored.
- **A principle is its own type in results and counts** (`decision` and `principle`), because the spec's counts by type list both.
- **The index tables are built and owned by the reindex code, not by `schema.sql`.** They are derived and droppable, and the size of the vectors comes from the model, so `semantic_index` is created with `vector(N)` once the service has said what N is. `schema.sql` only holds what they are made from: the `search` columns and the `index_source` view (the text to embed and its hash). A test proves from the source that nothing but `indexing.py` writes to them. A model change (or a change of vector size) drops and rebuilds them.
- **"Waiting to be indexed" is worked out, not recorded.** An item is waiting when no vector exists for its current text (a hash of the text is stored with the vector). So there are no triggers and no queue, a new fact is waiting without anyone marking it, dropping the index makes everything wait, and a change to status or links costs nothing. Search, similar items and overlaps only use vectors that are current, so a changed item leaves them until it is embedded again.
- **A background task does the indexing.** The server looks every `EMBEDDING_REINDEX_SECONDS` (default 5) and indexes what is waiting; after a failure it waits longer (up to 30 seconds). Without this, the index would only ever be as fresh as the last time someone remembered to call `reindex`. `reindex` runs a pass now; two passes never run at once. This is the "reindex job picks it up right after the save" that M10 describes.
- **No approximate index.** Meaning search compares against every vector, which is exact and takes milliseconds for thousands of items. An approximate index would be extra machinery for a size Vrum does not have. Revisit at tens of thousands of items.
- **Long text is cut.** At most `EMBEDDING_MAX_CHARS` (default 2000) of an item's text, title first, is sent to the model. Chunking long bodies was left out; it matters only for very long stories.
- **Rank fusion** uses the sum of 1 / (60 + rank), the usual constant, with a tie going to what matched both ways and then the lowest id.
- **Paging by offset** for `search`, `similar_items` and `find_overlaps`, because their order is by score and not by id. A page can shift if the graph changes between pages.
- **Overlaps compare stories, epics or rules** (default stories) in different epics. A rule's epic is that of its story; two unplaced rules count as the same place. Dropped items are left out unless asked. Pairs can be limited to those involving given epics, which is how a person checks one epic against the rest. Overlaps never write and never link: a pair that already has a link says so.
- **`recall` with `with_similar`** lists only active decisions, facts and beliefs that are not stale and not already linked, and never principles (they are always in the recall). Without the service it says so and returns what it could.
- **Words-only questions that are all common words** ("the and of") find nothing by words and say why in the note.
- **The check stack uses a scripted embedding service** (`tests/scripted_embeddings.py`): a small OpenAI-compatible program that gives texts the same vector when their words stand for the same ideas. It makes the checks offline, quick and repeatable, and lets tests stop and start the service. It proves what Vrum does with an embedding service. How good a real model is was measured by hand (below).
- **The local real model is Ollama with `all-minilm`**, behind the `local-embeddings` profile. The usual choice for this job, the Hugging Face text-embeddings-inference image, is built for amd64 only, which does not run well on Apple silicon; Ollama has an arm64 image. `all-minilm` is about 46 MB, 384 numbers per vector, and separated real duplicates from unrelated text better than `nomic-embed-text` did in the same test (see below).
- **Default thresholds, measured.** On 10 requirements each written two ways by two people, 4 related but different ones and 90 unrelated pairs, with `all-minilm`: reworded duplicates scored 0.54 to 0.87 (mean 0.71), related but different 0.30 to 0.49, unrelated at most 0.35; short questions scored 0.36 to 0.66 against the story they were about, and the best wrong story scored at most 0.32. With `nomic-embed-text` the same duplicates scored 0.69 to 0.92 but unrelated pairs went up to 0.64, so one threshold cannot separate them as well. So: **overlap threshold 0.55** (flags 9 of 10 duplicates and nothing else in the sample; 0.5 catches all 10 but sits on the highest related pair), **search and similar floor 0.35**. These are small samples and depend on the model, so both are settings, and a person with another model should measure. The first guesses (0.8 and 0.6) would have missed most real duplicates.
- **Open question for the owner:** whether to embed the title twice (or weight it) so short questions match better. Not done: it changes every vector and is easy to try once real use shows what is missed.

## 2026-11-15: choices made while building M5B (agent workflow)

These fill gaps the spec leaves open. The owner may veto any of them.

- **A handoff note is an event.** `finish_work` and `release_claim` write a `handoff` event (outcome and note) and then `claim_released`, in the same transaction as everything else they do. The database itself refuses a handoff without a valid outcome or with a blank note. `get_node` shows the latest note and how many there are; `node_history` has all of them. There is no separate notes table, so a note can never disagree with the history.
- **What each outcome does.** `done`, `blocked` and `dropped` set that status. `released` puts work that was in progress back to not started. `release_claim` does the same, because `next_work` now marks work in progress and released work would otherwise be stuck: neither ready nor lapsed, so nobody could take it. Only the holder can finish or release, including a holder whose claim ran out and was not taken over.
- **A lapsed claim stays visible.** The claim row stays until someone takes it over or its holder ends it. `get_node` shows `lapsed_claim_by` and `lapsed_claim_at` (and no handoff). `next_work` also hands out in-progress work whose claim lapsed, and says who let it lapse, because otherwise abandoned work could never be picked up again.
- **How `next_work` chooses.** Stories and tasks only. Ready (or lapsed) with nothing open that it needs first, and nobody holding it. Order: priority (urgent first), then the item's own target date (none last), then oldest. A story with open tasks is not handed out, because its tasks are the work. The pick, the lock (`FOR UPDATE SKIP LOCKED`), the check again after the lock, the status change and the claim are one transaction, so ten agents asking at once each get a different item. `within_node_id` (an addition) limits the search to one epic or story. When nothing is free the answer is `found: false` with a message counting what is held, being picked up at that moment, waiting and blocked; it is not an error. Under a race that count only covers what is committed, so it can be lower than the final one.
- **The context.** Exact links only: the item's own links and its parents' (epic and story). Parents show a preview of their bodies (600 characters), rules show up to 800. Dropped rules are left out. Superseded decisions linked to the item or its parents have their own section. All active principles are always included. Beliefs that are stale are left out and counted. Similar items (stories, decisions, facts, beliefs; at most 5) come from the index, are labelled as suggestions, and are left out with a note if the service is unreachable (a 5 second wait at most). Size limit `context_chars` (default 10,000, 1,000 to 1,000,000): sections are filled in a fixed order, and once something does not fit nothing after it is kept, so what is cut is the end, counted in `left_out`. The work item itself is never cut.
- **`create_plan`.** One transaction, no limit on size (500 items take about half a second). Items have temporary keys; a parent, link end or rule story is a key or the id of something that exists. Every problem is found first and the message lists all of them, each naming its item, so nothing is created and one reply fixes the plan. Circles of waiting are found in the plan itself and against the links that exist; the database trigger is still the backstop. The similar-items check runs for epics and stories after the plan is saved, so a slow or stopped service never loses a plan.
- **`create_node` and similar items.** Epics and stories are checked after they are saved, against other epics and stories, at the overlap threshold (0.55 by default), with a 5 second wait at most. Tasks are not checked (they are not in the index). Nothing is merged or linked. When the service cannot be reached the answer says so and the item exists anyway.
- **`update_nodes`.** Each change is its own transaction, like `update_node`, so one refusal never undoes the others. The result lists every change in order with `applied`, the new version and status, or the refusal. A refused change changes nothing and has no history entry of its own (the spec's "each is in the history" is read as: each applied change).
- **`changes_since` and the order of events.** An event is shown only when every transaction that began before it has finished, and events are ordered by when their change began (the transaction number), then id. This guarantees that an event written slowly, which can end up with a lower id than one that finished earlier, is never skipped by someone following the feed. The cost: for a moment after a write by a long transaction the feed lags, and two changes made at the very same moment can be shown in an order different from their ids. The page and its `latest_event_id` are read in one snapshot. One item filter at a time (a node, rule, decision or memory), or an actor.
- **Compact lists.** Node and rule lists (and `ready_work` and the coverage report) leave `body` empty by default and give `body_chars` and a 120-character `body_preview`; `detail` brings back whole bodies. Reading one item gives the whole body. Node, rule, decision and link lists also say how many items match in all (`total`). Measured: a list of 50 stories with 4,950-character bodies is 32,633 characters by default and 274,005 with detail (8.4 times smaller). With 2,200-character bodies it is 4.2 times smaller, because each item still carries about 500 characters of fields: the five-times rule needs bodies of a page or so.
- **Server instructions** are about 200 words: what the pieces are, and the loop (`next_work`, `recall` or `search`, `record_decision`, `retain_fact`, `finish_work`). A test compares every backticked name with the live tool list.
- **M5B changes M2 and the shape of earlier answers**, as the spec says. Releasing needs a note; `get_node` returns two more fields; `create_node` returns three more; lists have `body: null`. Earlier tests were changed to match, and nothing was kept for old callers.

## 2026-11-15: choices made while building M5C (extraction and reflection)

These fill gaps the spec leaves open. The owner may veto any of them.

- **The four tools always exist.** Without `LLM_BASE_URL` and `LLM_MODEL` they refuse in plain words and name what to do instead (`retain_fact`, `record_belief`, `list_memories`, `recall` and `search`). `server_status` now says which model is set up, or none, so an agent can tell before trying.
- **What is asked of a model.** One chat request (`/chat/completions`) with a system message that says what to do and the exact JSON to answer with, `temperature` 0 and `response_format` JSON. The answer must be a JSON object; a code fence around it is forgiven and nothing else is. No tool calling and no streaming, so any OpenAI-compatible service works. A reply that is not JSON, or has a key of the wrong shape, is a plain refusal that changes nothing.
- **How strict the checks are.** A passage or quote counts as "in the text" when it is there after runs of white space are made single spaces, and only then: case and wording must match exactly. A model that tidies the case of a quote loses that proposal. Models are not asked for dates, so extracted facts have none. A fact whose kind is not `world` or `experience` is dropped, not guessed. Ids may be written as 12 or "12". Every drop comes back in `dropped` with the reason.
- **Where an extracted fact's source comes from.** It is the passage, exactly as the model gave it (which the server has checked), so the fact is as accountable as one a person wrote.
- **Choosing facts to draw conclusions from.** By id, by item (the item, everything below it, and rules in those stories: the same as `list_memories`'s `within_node_id`) or by search (words and meaning, active facts only). At most `max_facts` (50 by default, up to 200) are shown, in id order, and the rest are counted. A belief may rest on a single fact. A belief with the same words as an active one is not recorded again, because asking twice should not double the memory. Beliefs are not linked to items: `recall` finds them through their evidence.
- **Revising.** Only an active belief that is stale. The model is shown what changed and the evidence that is still valid: a replaced fact or decision is replaced by what replaced it (followed to the end), a retracted fact is only mentioned. It must rest on that, and one revised belief is taken. A belief a person confirmed is refused before the model is asked, unless `said_by` and `quote` are given.
- **`looked_at` and `related`.** For scope `all`, `looked_at` counts the active beliefs passed so far from the first one, so `looked_at` plus `remaining` is always the number of active beliefs; a sweep that starts at `after_id` in the middle therefore shows a high `looked_at` from its first call. For `related`, the candidates are beliefs linked to the same items, resting on the same facts or decisions (or on facts linked to the same items), and beliefs found by words or meaning; the first `batch` (25 by default) are shown and `remaining` says how many were not. A stale belief is checked too and is flagged as stale. A belief is never checked against itself. A batch that is too long for `LLM_MAX_INPUT_CHARS` ends early and `next_after_id` says where to go on.
- **`reflect`.** Retrieval is the same as search, active items only, with two additions: what is linked to the item you name comes first (its recall: decisions, facts, beliefs that are not stale, then principles), and the words of a question are also tried joined with `or`, because a whole question seldom has all its words in one item. A belief that is stale is left out. 12 items by default (up to 200). An answer is refused when it cites a key that was not shown, mentions one inline, or cites nothing. An answer of null is `answered: false`, not an error. Nothing is stored.
- **How much is sent.** `LLM_MAX_INPUT_CHARS`, 12,000 by default (about 3,000 tokens), because Ollama gives a model 4,096 tokens unless it is told otherwise and silently cuts what does not fit. A larger limit is for a model with a larger context. Text longer than the limit is refused for `extract_facts` (it would be read only in part otherwise), and a list of items is cut and counted. One item's text is cut at 4,000 characters when shown.
- **Secrets.** `secret_formats.py` recognises private key blocks and tokens with a known prefix (AWS, GitHub, GitLab, Slack, Stripe, `sk-` keys, Google, npm, Hugging Face, SendGrid, JSON web tokens). It does not look for the word "password" or for long random strings: that refuses ordinary text, which M6 says to avoid. A text, question or statement with one is refused without repeating it; a stored item with one is left out and counted, because items stored before M6 may hold one.
- **The log of a call.** A new event action, `model_call`, about no one item (the database enforces that, and that it says which tool and what was asked). It holds the model, the question (cut at 1,000 characters), the items it was shown and what came of it. It is written when the model answered, in the same transaction as what the call wrote, and also when its answer was refused (a call was made and cost something). A model that cannot be reached, or answers with something unusable, wrote nothing and is not logged.
- **Only these tools make `extracted` and `derived` items.** `origin` is a parameter of the code that records memories, and none of the older tools offers it, so a person or agent cannot pass something off as written by a model, or the reverse.
- **How the checks test a model.** A scripted model (`tests/scripted_model.py`) in the check stack answers whatever a test tells it to and records what it was sent. A second server with no model set up proves the no-model case through a real client. Both take two more ports next to `VRUM_CHECK_PORT`.
- **A real model, tried once.** `scripts/real_model_check.py` runs the same four notes, four statements and three questions against a real model. With `llama3.2` (3 billion parameters, Ollama on this machine, nothing leaving it): 14 facts from four notes with none dropped (some were not really facts, such as "Call with Marie on 3 March"); 5 beliefs from 7 facts, some only restating a fact; 3 of 4 statements judged right (it missed that "every hour" contradicts "once a day, at night"); 1 of 3 questions answered, because the server refused the other two: the model cited a decision that was not among the items shown (it wrote `decision:3`, and the only decision is `decision:1`), and answered an unanswerable question without citing anything. So the guard does its work, and a small model loses answers it cannot cite. A larger model was not tried.
- **Not built:** nothing runs on a schedule (no automatic consolidation), and nothing a model writes is ever kept as a decision. Whether to weight titles in embeddings is still open.

## 2026-11-15: choices made while building M6 (hardening)

These fill gaps the spec leaves open. The owner may veto any of them.

- **The token is required.** The server does not start without `VRUM_TOKEN` (or `VRUM_TOKEN_FILE`, the path of a file that holds it), and says so in plain words. It must be at least 16 visible ASCII characters with no spaces. There is no default and no way to turn it off. `./scripts/init-env.sh` writes a random one (48 hex characters) to `.env`, and adds one to an `.env` from before tokens existed. Compose refuses to start without it. There are no accounts and no scopes: one token, all or nothing, as the spec says.
- **Only `GET /health` is open.** Every other request, including a wrong method on `/health`, an unknown path and the MCP endpoint, needs `Authorization: Bearer <token>`. The check happens before anything is read, compares in constant time, and a token in the address is not looked at. The scheme word is case-insensitive. M10 has to open the board's page files (they hold no data, so a browser can load them before it asks for the token); that is a change to the one list of open paths in `access.py`.
- **How a refusal is sent.** As HTTP 401 (no token, not a bearer token, wrong token) or 413 (too big), with a JSON-RPC error body, because that is the one non-2xx answer an MCP client shows to its user instead of "Server returned an error response". The message says what is wrong and what to do ("send `Authorization: Bearer <token>`"). It never repeats what was sent.
- **No limit on repeated wrong tokens.** A guessing attacker is not slowed down. With a random 192-bit token that does not matter; the 16-character minimum is the only protection for a short token a person chose. A limiter would need state that a restart forgets, so it is left for when the server is reachable from outside.
- **The token travels in clear.** HTTP is not encrypted. On this machine that is fine; for any other address put TLS (a reverse proxy) in front. The SDK's host check still lets in only `localhost` and `127.0.0.1` names.
- **One limit on what a write may hold: the request size.** `VRUM_MAX_REQUEST_BYTES`, 4 MiB by default (the SDK's own default), checked from `Content-Length` before the body is read, or counted as it arrives when the sender does not say. There is still no limit on the number of items in a plan or a batch. One more limit turned up: PostgreSQL cannot search one text that is more than about 1 MB of different words. That used to surface as "cannot reach its database"; it is now a plain refusal that says the text is too long to be searched and to split it, and nothing is changed. A text of 4 MB of one repeated word is fine.
- **Secrets are looked for in every argument of every tool, before anything else.** Not only free text that is stored: also searches and ids, because a search query is sent to the embedding service, and an id with a token in it is a mistake worth stopping. A wrong-typed value that looks like a secret is refused as a secret first. The refusal names the field (`items[2].body`) and the kind ("a GitHub token"), says it was not stored and not sent anywhere, and never repeats the value.
- **A second check where every write is recorded.** The event log is written by every write, so it also refuses a secret in what is about to be written, which stops text a model proposed (`extract_facts`, `consolidate_memory`) at the last step and rolls the write back. It looks at what is written, not at what it replaces, so a secret that got in before can still be edited out. The rows of a rolled-back write stay in the table until PostgreSQL cleans up, as for any rolled-back write; they are not visible.
- **Plain validation messages.** A wrong or missing argument is reported as "the arguments are not valid (limit: Input should be a valid integer)" and "Nothing was changed", with at most 8 problems. The SDK's own message repeats the value sent, which could be a secret or a whole body.
- **Logs are JSON lines on standard output, one per event.** The server says when it started (host, port, limits, model names; no addresses with keys), every tool call (tool, who, outcome `ok`, `refused`, `invalid` or `failed`, milliseconds) and every refused request (why, status, method, path, client address, declared size). They never hold arguments, answers, headers or bodies. A call that was refused for holding a secret is logged with no `actor`, because the actor may be the secret. As a second guard every line is scrubbed of the token, the database password and the API keys (when 8 or more characters long) and of any well-known secret format. The web server's access log is off, since it would repeat every address. The SDK's own log of tool refusals is turned down, since it prints the refusal text.
- **Paging.** A test lists every tool and fails if one returns a list that is neither paged (a `limit` of 1 to 200 and a cursor) nor one of the few lists that are as long as what was sent in or are one item's own links, so a new tool has to decide on purpose. `limit` outside 1 to 200 is refused in words for every paged tool. `reindex` lists at most 50 failures and counts the rest (`failed_total`).
- **Helper scripts take the token from `VRUM_TOKEN`** in the environment (`scripts/vrum_client.py`), so no script has the token on its command line.
- **How the checks test it.** `./check.sh` makes a random token for the throwaway stack and the tests read the same variable. The proof drives a real client with the right token, raw HTTP for what a caller that is not an MCP client sees (no token, a wrong one, a body declared too big, a body sent in chunks), and reads the real container's log. Two servers are covered (with and without a model).

## 2026-11-15: choices made while building M7 (export, import, backup, restore)

These fill gaps the spec leaves open. The owner may veto any of them.

- **Two ways to move data, for two jobs.** A backup (`backup.sh`, `restore.sh`) is the whole database as it is, of any size, for getting back what was lost. An export is the graph as data (`export_graph`, `import_graph`), which a person can read, diff and keep in git, and load into another server. They are separate because they answer different questions, and each is proved on its own.
- **What an export holds.** Every node (with dates), link, rule, decision and principle (with what each affects), fact and belief (with origin, status, what each concerns and what a belief rests on), and the whole event log, because history is part of the record and the spec says nothing is overwritten silently. It is bigger for that. Left out: **claims** (a lease that runs out is not part of the graph, and a copy of someone else's lease would only confuse; the events that recorded the claims are in), and everything **worked out** (what is stale, the search columns, the semantic index, which the server rebuilds by itself after a load).
- **Status in a file is as the server shows it.** A node nobody has started and that waits for nothing is exported as `ready`, as everywhere else in the product. On import `ready` is stored as `new` and comes back as `ready`, because it is worked out from the links. A file where `ready` is wrong therefore cannot make a node ready that is not.
- **Import goes only into an empty server and keeps the ids.** No merging into a server that already has data: that would mean renumbering every id in the file, and the history that points at them, and deciding which items are "the same". A server that holds anything (even one event) refuses, in plain words, and says to use a fresh one or restore a backup. Loading is one step: all of the file or none of it. It writes everything as it was first made and applies endings (replaced, retracted, confirmed) afterwards, so that none of the database's own rules (a record is never edited, evidence must be active when it is added) has to be switched off, and the database checks everything again whatever the file says. New items continue after the highest id in the file.
- **A file is read strictly.** Exactly the fields the export writes, no more and no fewer; dates as `YYYY-MM-DD`; times with a time zone; ids as whole numbers. Every problem is listed at once, by place (`nodes[3].title: Field required`), at most 20, without the value found there. Everything the file points at has to be in it. If the file carries `counts`, they have to match, which catches a file that was cut short. A secret in any text is refused, as for any write. Something only the database can judge (a circle of waiting, a start after a target) is refused with the database's own words and no values.
- **No event for the import itself.** The loaded event log has to be exactly the exported one, so that what is exported afterwards is identical. The server logs one line (`import_finished`, with who and the counts).
- **The size of a file.** `import_graph` takes the whole file in one request, so it is all or nothing, and a file can be as big as one request may be (4 MiB unless `VRUM_MAX_REQUEST_BYTES` is raised). A bigger graph moves by backup and restore. Loading in several requests would need a half-loaded state to be possible.
- **Export is paged, and consistent per page.** 200 items to a page by default (1 to 200), one list at a time, in id order, with a `next_after` to follow, so that an agent is never handed a whole graph in one answer. The first page says how many items each list holds. The script that puts the pages together checks that against what it read and stops with a plain message if the graph changed while it was reading, instead of writing a file whose parts do not fit. For a point-in-time copy of a graph that is being written to, take a backup.
- **The Markdown copy is made from the export, in a script.** `scripts/export_markdown.py` (the work is `vrum.markdown.render`, a pure function), so the copy cannot say anything the export does not and the same graph gives the same files byte for byte: nothing in them says when they were written. It is not an MCP tool: it is for a person's folder. Each file is `<kind>-<id>-<title as words>.md` (`story-12-log-in-with-email.md`; the id keeps it unique and stable), in `epics/`, `stories/`, `tasks/`, `rules/`, `decisions/` (decisions and principles), `facts/` or `beliefs/`. The fields are YAML at the top, written the way Obsidian reads them (text in double quotes, days and times bare); then the title and text (a decision's reason under `## Reason`); then a `## Links` list of `- label: [[file name]]`. Every connection is written at both ends under its own name ("needs first" and "needed first by", "rests on" and "evidence for", "children" and "parent"), so it can be followed in plain text, in git and in Obsidian's backlinks. Text is written as it is: a note whose text contains `[[...]]` or lines like `---` is not escaped.
- **The Markdown folder is replaced, carefully.** The script rewrites the seven folders it owns and leaves anything else in the target folder alone. A target that already holds files and was not made by this script (it leaves a `.vrum-export` marker) is refused, so nothing of yours is overwritten. History, claims and the semantic index are not in the copy: it is the graph as it stands.
- **A backup is the whole database, as a PostgreSQL archive** (`pg_dump` custom format, which compresses), of one consistent snapshot, taken while the server runs. It includes the semantic index, so a restore does not have to call the embedding service again. It is written readable only by its owner and checked to be readable before it is kept; it is **not encrypted**, and it holds all your data, so keep it where only you can read it. Backups go to `backups/` (git-ignored) unless you give a file name.
- **Restore never costs what is there until the new data is whole.** It restores into a new database, and swaps it in only when that finished; a backup that cannot be restored leaves the old data untouched. Into a database that holds data it refuses unless told `--replace`. The server is stopped while it runs and started again at the end. The backup has to be of the same version of the schema as this checkout (there are no migrations), or the server refuses to start and says so.
- **A restore renumbers the transactions of the event log.** The change feed reads events in the order their transactions began, and those numbers only mean something in the database that wrote them. A plain restore into a fresh database left every restored event "in the future": `changes_since` showed nothing written after the restore until the new database's counter had caught up (found by the check, which got an empty answer where it expected the new event). The restore script gives all restored events one new transaction number, in their own order, which is the same state an import leaves.
- **How the checks test it.** A second, separate copy of Vrum (its own compose project, volume, port and token, built from `compose.yaml` alone) is started and removed by the tests that destroy a database; `check.sh` gives it a port (`VRUM_CHECK_PORT` + 3) and removes it if a test dies. The graph they move is made through the tools, then compared whole through the export, never field by field. The Markdown test runs the real script against the real server and checks every connection in the whole database (not only the fixture) at both ends.
- **Scripts run from a checkout.** They put `src` on the path themselves. On this machine macOS marks the files of `.venv` as hidden, and Python skips an editable install's `.pth` file when it is hidden, so `import vrum` in a script failed even though the project is installed.
- **Not built:** scheduled or incremental backups, encryption, merging an import into existing data, importing a part of a graph, and reading the Markdown copy back in (it is read-only).

A refused edit keeps the typed text and, when the item is no longer the version that was read, offers "Load the current version" (which asks first by saying what is lost). Its own changes are followed by one more look at once, so they show without waiting. A page redrawn keeps the focus on the same card.

The test that no code but `indexing.py` writes to the index now reads every file under `src/vrum`, the board's pages included.

Dots: a square for an epic, a circle for a story, a diamond for a task, a triangle for a rule, a hexagon for a decision or principle, a small square for a fact and a dashed one for a belief (a suggestion). Lines: contains, needs first (thick, with an arrow), supersedes (long dashes, with an arrow), duplicates (dots), relates to (short dashes), and, when their dots are on, "rule of" and "concerns" and, for a belief, "rests on" (the spec names what a decision, fact or belief concerns; "rests on" is added because a belief drawn with no link to its evidence says little). Pins are kept for the time the page is open; they are not in the address, and a person can pin with a drag, with the P key or with a button, and release them all.

The top bar lists only the pages that exist (Board and Graph); a later milestone adds its pages.

The two marketing images (website header and social sharing image) are in `docs/marketing/`; the README uses the header and the same words ("Keep building. Keep the context."). The images themselves were not changed.

The "Everything" proofs need a graph of a known size and run on a second, empty copy of Vrum. A browser reports every refusal the server sends (a 400) as a failed load in its console; the tests do not count those as faults, only real script errors.

## 2026-11-16: choices made while building M11 (Table, Outline, Roadmap and the filter language)

These fill gaps the spec leaves open. The owner may veto any of them.

- **One filter language, one owner.** `src/vrum/query.py` reads the text and turns it into a condition on the `node_state` view; `list_nodes` takes it as `query` and ANDs it with its other filters, and the board's filter box sends the same text to `list_nodes`, so people and agents get one answer from one piece of code and the board has no parser of its own. Every value goes to the database as a parameter, never into the statement. The text may be 2,000 characters long at most (a bad query is a refusal, not a slow request).
- **How the text is read.** Terms next to each other must all hold, and `OR` in capitals starts a new group; there are no brackets. So `epic:7 a OR b` means "(epic 7 and a) or b", and a filter that has to stay inside one epic puts `epic:7` in every group. A word matches part of a title or details, ignoring case (a substring, not a search by meaning; `%` and `_` mean themselves); "two words" in quotes is one phrase; a quoted `"claimed"` is a word. `claimed` and `waiting` on their own are flags (held by someone, waiting on something). **Default for veto:** the spec's example `-claimed` is read as "not held by anyone".
- **Fields.** `kind`, `status`, `priority`, `claimed` (a name), `parent`, `epic`, `epic` (the epic an item belongs to, an epic being its own), `story` (the story a task belongs to, a story being its own), `id` (`12` or `#12`), `start`, `target`, `is` (`overdue`, `conflict`, `waiting`, `claimed`, `lapsed`) and `no` (`start`, `target`, `claimed`, `parent`, `body`, `waiting`). `start:` and `target:` look at an item's own dates only, not at the span worked out from what is under it, so `target:none` finds items that really have no target date. A day, a range with either end left open, or `none`. An unknown field, value or date is refused in plain words that say which part was not understood and what is allowed.
- **Table.** The server's filter decides which rows there are; sorting and grouping are done in the browser on those rows (empty dates last, whichever way), and the first 300 rows are drawn, with a button for more. A cell edit is one `update_node` at the version the row was last known at, and edits go one after another so that each starts from the version the one before made. Choosing rows remembers the version each had when it was chosen, so a row an agent changed afterwards is refused by `update_nodes` as stale, and the result lists each row as changed or refused with the server's words. The bulk form changes status and priority (what several items sensibly share); titles and dates are changed row by row.
- **Outline.** An ARIA tree with arrow keys, Home and End, Enter to open and `m` for the Move dialog. Rules show under their story (a dropped rule is hidden). Any drop sends `move_node` and the server says no to nonsense (a story under a task, a loop), so the page does not guess what is allowed. Which branches are folded is in the address as `closed=`.
- **Roadmap.** A day is 10, 4 or 1.2 pixels at month, quarter and year zoom. "Today" is the UTC day, as in the database, so overdue on the page and `is:overdue` always agree. A bar runs from `span_start` to `span_end`; an epic or story with no dates of its own is drawn pale and dashed over its children's span and cannot be dragged. Dragging a bar sends the item's own dates moved by whole days (an item with one date moves that one); an end sends one date. Nothing is clamped on the page: a start dragged past the target is sent and the server's refusal is shown. An item dropped from the tray gets a start where it was dropped and a target six days later (**default for veto:** a week), or the dates typed in the tray. Keys move a bar a day (Shift: a week; Alt: start only; Ctrl: target only) and are added up for 0.7 seconds into one change. Shift- or Ctrl-click, or Space, picks bars to move together through `update_nodes`. Arrows are drawn only between two bars on the page. A schedule conflict is a warning on the label, the bar and the arrow, in words, and never blocks anything.
- **What is in the address.** `q` (the filter), `sort`, `group`, `zoom` and `closed`, after the `#`, never the token; colons and commas in a filter are left readable. The server keeps no saved views (a test reads the database's tables and row counts before and after a second browser opens the address).
- **The board's tools.** `update_nodes` joined `WRITE_TOOLS`; `list_nodes` already was in `READ_TOOLS`.
- **Found along the way.** (1) The content security policy throws away inline style attributes without a word, so the first bars had no position; `h` has a `css` property that sets `element.style` (which the policy allows), and a unit test fails on any `style:` attribute. (2) A row redrawn after the person's own save could still carry the older version and send it with the next edit, which the server rightly refused; the Table now sends the newest version this page itself wrote, and a cell that was refused goes back to the server's value. (3) A late reload could redraw the table over a cell being typed in; a reload now gives way to typing. (4) One stray line of text in a script stopped the whole board from loading, which every browser test caught at once (and `node --check` did not, because the files are modules).

## 2026-11-16: choices made while building M13 (find and connect)

These fill gaps the spec leaves open. The owner may veto any of them.

An epics box (`epics`, ids) asks for only pairs with something in those epics (the tool's own `epic_ids`), which is how a person looks at two epics' fixtures and not the whole project. The two sides show their details as Markdown. **Mark as duplicates** and **Mark as relates to** call `add_link` from the first item to the second under the typed name; a pair already linked that way says so and its button is off. Rules cannot be linked, so their pairs have no buttons.
- **Quick switcher.** Ctrl+K or ⌘K (and a visible "Jump to…" in the top bar, since a shortcut is not discoverable). It matches every word typed against the title and the kind, an id as `12`, `#12`, `node 12`, `rule:3`, `decision 7`, `fact 5` or `belief 2`, and the names of the pages. A bare id offers every kind that has it, nodes first. It only navigates and changes nothing.
- **Ask.** It calls `reflect` under the typed name. The answer is shown with a chip "Generated, not a record" and the model's name, the items it relied on are links, and nothing is stored (a test counts decisions and memories before and after; the one thing logged is the model call, as `reflect` already does). The offer to record a conclusion lists the facts and decisions it relied on as ticked evidence and starts from the answer's words; a belief cannot be evidence for a belief, so beliefs among the items are left out and the page says how many. Without a model the box says so and has no question field.
- **The graph's mentions layer.** Off until chosen (`mentions=1` in the address). A dotted green line runs from the item whose text holds a reference to the item it names, drawn only when both dots are on the page, once for each pair however many times it is written.
- **The Markdown copy.** A reference written in a text (`[[node:12]]`) becomes a link to that item's file in the copy, as Obsidian reads it, so the copy keeps working as a set of links; one that names nothing, or the wrong kind of thing, is written as plain words with no brackets (`node:99 (missing)`). Every reference anywhere in a file is turned into a link, including one in a title, since Obsidian would read it as a link anyway. Any other double brackets in a person's text are left as written.
- **What is read when.** The board holds every node already, so a reference to a node costs nothing. The rules, decisions, facts and beliefs are read only when something needs them: a text on the page that names one, the first `[[` typed into a pick-list, or the quick switcher. Once read they are kept fresh like every other list the board holds.
- **Found along the way.** (1) The page shows "null" and "[object HTMLElement]" when `append` is given empty or listed children (this was found on the first screenshots of M12 as well), so `dom.js` has `put(el, ...children)`, which leaves out the empty ones and opens up lists, for every place that has to. (2) Ids are separate for nodes, rules, decisions and memories, so a mention is always keyed by its kind and its id; one early test compared bare ids and passed by luck. (3) Overlap fixtures are made by many tests with the same titles, so the Overlaps page can hold more than one page of pairs and a test reads every page before it looks for a row. (4) A card still being fetched for the item that was open could be drawn over the card of the next one (a created item's own news started a reload of the old card, which finished last); the panel now marks a card it has left as dead and a dead card is never drawn. A change of words reloads the open card only when the change adds or drops a reference to it.

## 2026-11-16: choices made while building M15 (accounts and private projects)

These fill gaps the spec leaves open. The owner may veto any of them. Email verification, account recovery and password change or deletion are not built; they wait for answers in `BLOCKED.md`.

- **The wall is in the database.** Every graph table has a `project_id` and composite keys, so a link, parent, evidence or replacement in another project is refused by the database itself. Each request runs under the `vrum_project` role with row-level security on the project it was authorised for, so a forgotten filter in code shows nothing of another project. The role can read no account, session or key table.
- **Ids are per project.** Node 12 in two projects is different data; every project counts from 1 with its own sequences. Export and import work on one project and load only into an empty one, with the same ids.
- **Passwords.** scrypt (N 2^15, r 8, p 1), 10 to 200 characters, a name of 1 to 100 characters, a project name unique per owner ignoring case. A sign-in for an unknown address does the same work as one for a known address and says the same words.
- **Sessions.** A random cookie (`HttpOnly`, `SameSite=Strict`, `Path=/board`, `Secure` when served over https; not marked `Secure` over plain http so that a local install works), kept as a hash on the server. 12 hours, absolute. Signing out ends it on the server. Every write also needs the session's CSRF header and a same-site origin.
- **Rate limits (default for veto).** 5 failed sign-ins per address and 200 per client address in 10 minutes, kept in memory, forgiven by a good sign-in. The price: someone can lock an address out for 10 minutes. A locked address is refused even with the right password.
- **Registration is open.** Anyone who can reach the server can make an account; that is the point of a self-hosted install, and the spec asks for no gate.
- **Agent keys.** `vrk_` and 32 random bytes, shown once; only a hash and an 8 character hint are kept, with a label and when it was last used (updated at most once a minute). A key opens one project. It is checked on every call, not only when connecting, so revoking it stops a connected agent on its next request.
- **There is no server token.** `VRUM_TOKEN` is gone: the server starts without it, and only `GET /health` and the board's page files are open. Scripts read `VRUM_AGENT_KEY`.
- **Switching is a whole page load.** A project lives at `/board/p/<id>`; going to another one reloads, so nothing of the first can be drawn on the second. The client also drops any answer that belongs to a project that is no longer open. The board records changes under the account's name by default at sign-in, and the name can be changed.
- **Backup and restore stay whole-install** and outside accounts: one dump holds every account and project, and `restore.sh` makes the database role first because a role belongs to the cluster, not to the database.
- **The semantic index is install-wide** with a `project_id` and the same row-level security; the background job covers every project, and `reindex` through a tool covers the caller's project only.
- **Known wart.** Browsers do not scope cookies by port, so two Vrum servers on one host share the session cookie name and sign each other out. Not addressed.

## 2026-11-16: choices made while building M16 (work and context, without generation)

These fill gaps the spec leaves open. The owner may veto any of them.

- **Two records, one shape.** A fact (statement, source) and a decision (title, text, reason, a named decider) are both records that are never edited, with the same lifecycle (`active`, `superseded`, `withdrawn`, each with a reason once it ends) and the same confirmation field. They stay two tables because their required fields differ; what they share lives in `records.py` (confirmation rules and the plain-words label).
- **Principles became a flag.** A decision that applies throughout its project is `project_wide`; it is a decision like any other. It is in every recall (`project_wide_decisions`) and every `next_work` briefing of its project, whether or not it is linked to the work, and never in another project's. A decision's `project_wide` is part of what it is, so changing it means superseding the decision (or leaving it empty to keep it).
- **The world/experience split and `happened_on` are gone** (the spec removes the split, and the day was only meaningful for experiences). Origins (`extracted`, `derived`) are gone with the generation tools. A fact has a text, a source, who recorded it and when.
- **Withdrawing a decision is new.** The spec asks to "replace and withdraw" records, and a decision could only be superseded. `withdraw_decision` gives an active decision up with a reason, as `withdraw_fact` does for facts (it replaces `retract_memory`, whose wording changed with the rest: a record is withdrawn, not retracted).
- **Confirmation is one operation for both kinds: `set_confirmation(kind, record_id, confirmation, person, quote?)`.** Confirming names the person who reviewed the record (the actor, who made the call, is recorded separately). Recording a record never confirms it, so an agent cannot confirm its own statement by writing it. **Taking a confirmation away** (the spec's dropdown goes both ways) needs the person who says so and their words, because it takes away what a person gave. Only an **active** record's confirmation can change: what a record was confirmed as stays on it after it is replaced or withdrawn, and shows in its history. Each change is an event (`fact_confirmed`, `fact_unconfirmed`, `decision_confirmed`, `decision_unconfirmed`) with the actor, the person, the quote and the time.
- **A person's word is needed to change a confirmed record.** Superseding or withdrawing a confirmed fact or decision needs `said_by` and `quote`, as changing a confirmed belief did before. This is the permission the spec asks for ("an actor name alone never grants access"): the access itself is the project's agent key or the owner's session (M15), and this rule stops an agent from silently replacing what a person reviewed. Both the person and the agent are in the history.
- **53 tools.** The four generation tools, the belief tools and `promote_belief` are gone; the `*_memory` tools became `*_fact` tools (`supersede_fact`, `withdraw_fact`, `link_fact`, `unlink_fact`, `get_fact`, `list_facts`, `fact_history`); `withdraw_decision` and `set_confirmation` are new. `memory_id` became `fact_id` in `changes_since`, `find_mentions` and `similar_items`. Requirements are still `rule` in the API and in `[[rule:3]]` references: only the words on screen say "requirement".
- **No generation, no model.** `LLM_*` settings, the language-model client, the scripted model, the second server with no model, `scripts/real_model_check.py` and the `model_call` event are removed. Optional embeddings are untouched. The compose check stack is now the database, the server and the scripted embedding service, so its port numbers moved down: the restore stack is `VRUM_CHECK_PORT` + 1.
- **Recall and briefings say where a record stands.** Recall's sections are `active_decisions`, `project_wide_decisions`, `facts`, `past_decisions` and `past_facts` (past means superseded or withdrawn), and every entry has `confirmation`, `confirmed_by`, `status` and a plain-words `label`. The briefing in `next_work` has the same sections (it leaves past facts out, as it left out past memories).
- **Search results** carry `label` and `confirmation` instead of `origin`; the facets are epic, story, task, rule, decision and fact (`principle` and `belief` are gone). The semantic index embeds epics, stories, requirements, decisions and facts.
- **Export format.** The sections are nodes, links, rules, decisions, facts and events. Facts and decisions carry their confirmation, lifecycle and links. There is no compatibility with the old format.
- **The board has three pages.** Board is where a project opens; Graph (Work / Context / Everything, Map / List) and Roadmap are the other two. Search and Activity are **drawers**, one at a time, in the left column (`drawer=search` or `drawer=activity` in the address), so a result or a claim can sit beside the detail panel on the right; both stay in place while the address changes, so opening one never throws away a draft typed in the panel. Agent access, Tools and Status are pages reached from the **Settings** menu, not from the main bar. Home, Table, Outline, Rules, Memory, Overlaps and Ask are gone with no alias: an old address lands on Board.
- **One address for a selection.** `sel=<kind>:<id>` (node, rule, decision or fact) opens the shared detail panel and replaces `card=`. Graph keeps `view=`, `as=`, `epic=` and `q=` across both presentations. Search keeps `search`, `search_mode`, `search_type`, `search_status`, `search_epic` and, for Possible duplicates, `dups`, `dup_min`, `dup_epics`; Activity keeps `act_*`.
- **What Home showed is now an attention strip at the top of Board** (ready work nobody holds, blocked, overdue, claims that ran out with no handoff note, requirements in no story, stories with no requirement), each a link to exactly those items. The decisions-this-week, beliefs-waiting and overlap counts went with the pages they led to.
- **Possible duplicates compare what they compared before** (stories, epics and requirements, by `find_overlaps`), as a mode of the search drawer. A decision or a fact cannot be marked a duplicate, because `find_overlaps` does not compare them and nothing links them: the spec asks for marking "where supported". Marking is `add_link`, one per click, and searching never writes.
- **Context in Graph's list.** The Context list has three sections (Requirements, Decisions, Facts) with their own filters, and always shows requirements in no story, loose records and project-wide decisions whatever the epic scope. A requirement can be placed and moved but not unplaced: there is still no tool for that, and the spec does not ask for one. Decisions and facts draw 100 rows, then "Show more".
- **Wording.** The board says "Requirement" where the API says `rule`. A few server refusals still say "rule", because the server owns those words and the API names did not change.

- **What Vrum needs:** only one secret, the database password. It has no application secret key (sessions and CSRF secrets live in the database, hashed), no email setup and no second service. The database is not published outside Docker. The port is the same inside and outside because the server only accepts requests addressed to `localhost` on that port.
- **Chosen (the owner was not available to answer): a generated password, not a fixed default.** The database service's entrypoint makes a random 48-character password the first time it runs and keeps it in a Docker volume of its own (`vrum-secrets`); the server reads it through `VRUM_DB_PASSWORD_FILE` (the server already supported that pattern for the embedding key; now it does for the database password too). So `git clone` then `docker compose up -d --build --wait` is the whole setup, and no two installs share a password. **For veto:** the alternative is a fixed default (`vrum`) in `compose.yaml`, overridable in `.env`, as Taiga does: simpler to read and debug, but the same well-known password everywhere. It is a few lines in `compose.yaml` to switch.
- **The password can still be chosen:** `VRUM_DB_PASSWORD` set before the very first start is used. It is read only once: changing it later is ignored, so it can never lock the server out of its own database (the same rule Postgres itself has for `POSTGRES_PASSWORD`). `check.sh`, `acceptance.sh` and the second stack keep setting it so tests can look for leaks of it.
- **A lost password file is refused in words:** if the data volume exists but the secrets volume was deleted, the database does not start and its log says to set `VRUM_DB_PASSWORD` to the old password or to run `docker compose down --volumes` (which deletes the data). Not silently making a new password that cannot open the database is deliberate.
- **`scripts/init-env.sh` and its test are removed.** Nothing needs them; `.env` is optional and only for changing a setting (`.env.example` says so). The port stays 8000 (free on the owner's machine); the README says how to use another one for a single start (`VRUM_PORT=8090 docker compose up -d --build --wait`).
- **Not done, for the owner to decide later:** publishing a prebuilt image (for example on GitHub's container registry) so that the first start pulls instead of building from source. Taiga pulls images. It would need a release and versioning process, which Vrum does not have.
- **Decided by:** the loop, following the owner's request that Vrum start without variable setup.

## 2026-11-18: choices made while building M24 (email: invitations, verification, password reset; loop's choices open to veto)

- **Email is optional and off by default.** Setting `VRUM_SMTP_HOST` (with `VRUM_SMTP_FROM`) turns it on; with nothing set the start is as before: invitations are copied links, there is no "Forgot your password?" and an address is never confirmed. - **Links in email come from `VRUM_PUBLIC_URL`,** never from the request's Host header (a forged Host would otherwise put someone else's address in a reset link). It defaults to `http://localhost:<port>`, which is right on one machine; behind a proxy it must be set.

## 2026-11-19: choices made while building M29 (search by meaning out of the box; loop's choices open to veto)

## 2026-11-21: choices made while building M37 (code mode: `explore` and `run`; the research and what it changed)

The owner asked whether the tools should be redesigned the way Cloudflare and AWS are doing it (the model writes code, a sandbox runs it, only the result returns), and, once it was written up as an option, said to build it and not to count the cost. The first plan came from one search. The owner asked whether research had been done first, so it was done properly (Cloudflare's Code Mode and its API server, Anthropic's code execution with MCP and its tool search, AWS's MCP server and Strands, OpenAI, Microsoft, Goose, Vercel, Pydantic, UTCP, an independent benchmark, Check Point's 2026 escape of Cloudflare's own runtime, Deno's security notes, and experiments on Deno 2.9.8 in a python:3.12-slim container). What it changed:

- **The script is evaluated from a string, never loaded as a module.** Deno does not check permissions on static imports (it read a file with every permission denied), so the runner is a fixed file, types are stripped in a separate step with no permissions, and the plain JavaScript runs under `new AsyncFunction`, where a static `import` is a syntax error.
- **Deno is one layer, not the wall.** The `node:*` modules stay importable with every permission denied, and the 2026 escape of Cloudflare's runtime went through one of them, so each is stubbed. Under that is a container of its own: no network, no secret, no database, a read-only disk, no extra rights, no root, and limits. The only way in or out is a socket in a shared volume. A full escape of Deno finds an empty box. This is also why the sandbox is a service and not a child process of the server (the first plan): a child of the server shares its user, its files and its memory.
- **Limits that hold.** The heap flag alone aborts uncatchably and ignores memory outside the heap (a 1.5 GB array succeeded), so there is also `RLIMIT_DATA`, a cpu limit, the process group killed at the time limit, the container's own limits, and a script that keeps calling after its call limit is killed and not told again. The runner also runs without JIT (about six times slower on tight loops), which removes a class of V8 bugs for scripts that only glue calls together.
- **Typed results decide success.** An independent benchmark found result types in the stubs moved success by up to 39.5 points for weaker agents, more than any other change. So every function's result type is exact: the SDK's `{"result": ...}` wrapper is unwrapped, fields with a default are required in a result (always present), and a test checks every tool's declared result against a real result.
- **The types are in `run`'s description, in a safe order.** Claude Code cuts a tool description at 2048 characters, so the guide and the function names come first (the whole contract in 1.5 KB) and the signatures follow; a client that cuts them still works, because the guide says to call `explore` first. The 25 standard tools measure 27 KB of signatures (more than first guessed), so the limit is 32 KB: a key with more functions gets names only. Not a setting: `code_mode.MOST_DESCRIPTION_CHARS`.
- **Type-checked before it runs**, inside the sandbox, because the diagnostics are good ("Did you mean `list_nodes`") and cost about a quarter of a second. A weak model can fall into a loop of compile errors, which is the other reason a key chooses its way (below), and why every error is one short sentence with a line.
- **Not one transaction, and it says so.** Nobody ships a script-wide transaction. A failed script lists its calls with their states and whether anything may have changed, never retries and never replays. Writes are serialised (reads run together), calls are capped at 200 and writes at 100. The allowance is the control: a key that may only read can only read in a script.
- **The way of calling is chosen for each key and starts empty.** Anthropic's own numbers show no gain, and about 8% more cost, for one or two sequential calls, and weaker models do worse with code (an independent paper: the pass rate of some fell by half). Cloudflare and Vercel both keep a switch back to plain tools. So `agent_keys.code_mode` defaults to false, nothing existing changes, and the owner can compare models.
- **Secret scanning is best effort here**, since code can build a string in pieces. It still runs on the script and on every argument, but the protection that matters is structural: the sandbox has no network and nothing to send, project data is scoped, and no tool sends anything out.
- **Every inner call is logged like a tool call** (`via=run`, a run number, the order, a short hash of the script, never text), and three refusals in one run are logged once more as a warning, since repeated refusals are what an injection or an escape attempt looks like.
- **Declined for now:** Pydantic's Monty (a Python interpreter in Rust, with a bundled type checker and no second runtime) is a credible alternative for a Python server, but the owner asked for TypeScript as Cloudflare does it, and it is a Python subset with a language-level sandbox only. The host code talks to one small interface (a socket and the protocol in `sandbox/supervisor.py`), so another executor could replace Deno behind it. Also declined: a script-level approval step (Cloudflare's experimental abort-and-replay) and per-tool "revert" handlers; a call to something that must be approved stays a person's job on the board.
- **Not built:** a `sandbox` line on the Status page (`CodeMode.ping()` is ready for it); the x86_64 runtime was not run on an x86 machine (the pinned digest was checked against the real download).
- **A security review after the build found three medium problems, all fixed.** (1) A script could freeze the supervisor, and so every other script, with a long run of spaces in a type error, because of a slow pattern match on text the script controlled: Deno's text is now cut to a small size before anything reads it, read without pattern matching, and parsed off the loop. (2) The key's rights were read once when a script started, so revoking or narrowing a key did not stop a script that was already running, against the rule that a key change applies from the agent's next request: every call a script makes now re-reads its key, and a revoked key or one switched to one tool at a time ends the run. (3) A script that stopped the sandbox reading could make the server hold hundreds of megabytes of replies: the supervisor and the app each bound what they queue per run, run at most eight reads at once, drop a connection that makes no progress, and handle a cancel at once. The review also said that concurrent runs share one user and one process space, which is harmless without a Deno or V8 escape; it is cut down cheaply (each run's files are private, the supervisor cannot be dumped, the Deno binary is execute only) and not more, since real separation per run needs rights the container does not have.

- **Key expiry is a last day, `agent_keys.expires_on` (a date), not a moment.** The spec called it `expires_at`; a day is what a person picks on a calendar, and every other date in Vrum is a UTC day (`start_on`, `target_on`). The key works through that whole UTC day. `expired` is the server's own answer in the key's JSON (the database's clock, never the browser's). A day that has already passed is refused when set ("revoke the key to stop it now"), so the only way for a key to be expired is for its day to pass. An expired key is refused in plain words ("This agent key expired after 2026-11-30 ... the owner can extend it, or make a new key"), told apart from a wrong or revoked key, on its next request, on an open connection and, for a running script, at its next call (`KeyExpired`, read by `project_for_key` and `access_of_key`). Changing the day to one that has not passed makes the key work again at once. No expiry means it never expires, as before, and shows nothing.
- **Not done:** no warning is sent before a key expires (M48's nudges may carry one); the board does not tell an agent's owner a key is about to expire beyond the chip; a run label is not unique, so two runs may share one.

## 2026-11-22: choices made while building M45 (asks, the Needs a person list and a stricter change feed; open to veto)

The owner said "yes add" to the human-loop tier, and asked whether the inbox of decisions and questions is the final vision and whether smart epics and assignment follow (answered: M45 to M47 are the inbox, M43 is the sorting, and the steward's proposals meet the person on the same page).

- **An ask is two events, not a table.** `ask_raised` and `ask_answered` are rows of the append-only log, and the view `ask_state` (schema.sql) joins them. That gives the property the research asked for, a record that cannot be edited, for free, and means the export, the history and the change feed already carry asks. The ask's number is the id of the event that raised it (Q-12 on the board). The database refuses an ask with no question, a kind that is not question or approval, an effect that is not blocks or parks, an answer that is not a person's, and a second answer (a unique index on the ask number among answers).
- **No new agent tool, because the agent set is at its limit of 25.** An agent asks with an `ask` argument on `finish_work` (outcome blocked or released) and on `update_node` (with status blocked). Reading the answer needs no tool: `get_node` and `next_work`'s briefing carry `asks`. None of the three is in the standard agent set; a test proves the set is still 25 or fewer.

A parking ask is attached to work an agent released: the work stays free and the ask waits. An approval is a question whose choices are yes and no. A free question has no choices. At most 8 choices, 1,000 characters of question, 2,000 of answer and comment; a secret in any of them is refused as everywhere else.
- **An answer is final.** One answer per ask, never edited. If something changes, the agent asks again (a new ask). This is deliberate: an answer an agent is acting on must not move under it, and it keeps an ask from turning into a comment thread (still a non-goal).
- **`needs_a_person` is derived and never stored twice.** Four kinds of row: open asks on work that is not finished; blocked, unheld work whose only open checks are `[person]` ones; unconfirmed notes on work that is in progress or held right now; and work whose claim ran out twice (each time a claim was taken over from a lapsed one, plus a lapsed one now). Grouped by story, longest wait first, at most 200 rows with the rest counted. It asks rarely and never answers, ticks or confirms for a person.
- **The change feed got an opaque cursor, `truncated` and `poll_after_seconds`.** The cursor is the same position as `after_event_id`, written so that what it holds can change later; `truncated` is true while another page can be read right now; `poll_after_seconds` is the board's own poll setting (`VRUM_BOARD_POLL_SECONDS`). `after_event_id` still works. This is the poll mode of MCP Events and the source of truth M48's webhooks will point at. `record_event` now returns the new event's id.
- **The code-mode signatures shrank to make room.** Adding the asks arguments pushed the compact signatures of the standard set over the 32,000 characters that `run`'s description may carry, so an argument that several functions describe in the same words (a node's reference, a limit) is now described only where it first appears. No wording was lost for a reader.
- **Not done:** no email or other nudge when something waits (M48); no "snooze"; the page does not rank by importance, only by how long a thing has waited; an ask cannot be withdrawn by the agent (it can be answered "no longer needed" by a person, or left).

## 2026-11-23: choices made while building M43 (the measured test, `suggest_parent`, the Inbox and proposals to move work; open to veto)

- **The measurement came first and it holds, with limits.** `scripts/parent_accuracy.py` hides each story and task in turn (and a story's own tasks with it) and asks which epic, or story, the embedding model finds nearest, three ways: by what the parent says about itself (`own`), by the average of what it already holds (`held`) and by both added together (`both`). On the invented demo project (12 epics, 53 stories, 180 tasks), first and in the first three:

  | question (candidates) | built-in all-MiniLM-L6-v2 | all-MiniLM-L12-v2 | all-mpnet-base-v2 |
  |---|---|---|---|
  | a story, which epic (12; chance 8%), `both` | 74% and 87% | 68% and 94% | 75% and 92% |
  | a story, which epic, `own` / `held` | 68 and 87 / 53 and 79 | 74 and 91 / 42 and 79 | 72 and 85 / 55 and 79 |
  | a task, which story (53; chance 2%), `both` | 63% and 84% | 62% and 84% | 67% and 86% |
  | a task, which story, `own` / `held` | 66 and 82 / 43 and 68 | 68 and 83 / 44 and 67 | 68 and 84 / 49 and 73 |
  | a task, which epic (12), `both` | 62% and 92% | 60% and 91% | 58% and 89% |

  When the best parent was ahead of the second by at least 0.05 (what `suggest_parent` calls sure), `both` was right: a story's epic 92%, 93% and 96% of the time on about half of the stories; a task's story 81%, 79% and 80% on about 60% of the tasks. A margin of 0.10 gave 95% to 100% on about a third. **What it says:** meaning gets the right epic first about three times in four and in the first three about nine times in ten, and it knows fairly well when it is sure, so a suggestion with its reason and a person (or a steward that only acts when sure) is worth having; it is not good enough to move work without one. A model five times larger (mpnet, 110 million parameters) is no better than the built-in one by more than a few points, so **the built-in model stays**. `both` is the one rule used everywhere: it is the best or equal in the first three for every question and model, and its first place is never more than six points under the best view (`own`, once, for a story's epic with the larger MiniLM). The weak case is a story's epic by `held` alone (an epic's other work is a blur of its topics), and the strong help is the epic's own words, which is why a good epic description matters.
- **What was not measured.** One invented project, one model family and no second shaped project (the spec asked for one): the script reads any project's export, so run `scripts/export_graph.py` and then `uv run python scripts/parent_accuracy.py --export <file>` on your own project before relying on the margin. The numbers above are the script's output as run on 2026-11-23 with the models served by the repository's own embedder code; they will differ on other text.
- **`suggest_parent` is the script's arithmetic in the database.** `src/vrum/placement.py` ranks parents in one SQL statement over the index (the epic's own vector and the average of its held items, each made unit length, added, made unit length again, and compared with the work's vector), leaving the item and its own tasks out, and `tests/test_placement_integration.py` proves its scores equal the script's to within a thousandth. It asks for a story or task that is saved (`node`, or `title` and `kind` for work not saved yet), gives at most 10 parents with their score, the score by each view, how many items the parent holds, the two items under it that the work most resembles (the reason), where the item is now and how that ranks, `sure` and the margin, and says plainly how many possible parents are not indexed yet. It refuses without search by meaning. It never moves anything.
- **The Inbox is a convention, not a schema.** An epic called Inbox (any case) is where unsorted work waits. `suggest_parent` never offers it, nor the stories in it, as a parent, and reports its reference as `inbox`. The importers already file work with no epic under one.

Proposals are rows on the Needs a person page in a group called Suggested moves. The database refuses a proposal with no items, no reason, or both or neither of a parent and a new epic, and a decision that is not a person's or is a second one.

Its key is an ordinary agent key allowed four tools, so it cannot move, confirm or decide anything. Vrum has no language model, so naming a group is the agent's or a person's job.

## 2026-11-23: choices made while building M48 (signed webhooks and email nudges; open to veto)

- **Settings of a project and of a person, not graph content.** `webhooks`, `webhook_deliveries`, `nudges` and `notify_cursor` (`schema.sql`) are account-level tables like `agent_keys`: the role a project's work runs as cannot read them (`tests/test_database_constraints.py` lists them), they are not in an export, and an owner reaches them only through the board's own routes (`/board/api/projects/<id>/webhooks...`, `PUT .../nudges`, `GET /board/api/nudges`), not through MCP tools: the tool set is at its limit and this is the owner's setup, not work. **A webhook's secret is kept in full**, because the server signs with it (a hash would be useless). It is `whsec_` and 32 random bytes, shown once when it is made or replaced, never in the graph, an export, a list, a log or a note (the secret scan knows the format), and a backup holds it as it holds the keys' hashes, so a backup is as private as the database; this is written in `docs/configuration.md`.
- **Signed exactly as the Standard Webhooks specification has it**, so any receiver with a library for it can check a message: `webhook-id` (the same through every retry), `webhook-timestamp` and `webhook-signature` (`v1,` and the base64 HMAC-SHA256 of `<id>.<timestamp>.<body>`, one signature for each secret in force). `tests/test_webhooks.py` holds the specification's published example (secret `whsec_MfKQ9r8GKYqrTwjUPD8ILPZIo2LaLaSw`, signature `v1,g0hM9SsE+OTPJTGt/tmIKtSyZlE3uFJELVlNIOLJ1OE=`). Replacing a secret makes a new one and keeps the old one signing too for 24 hours, so a receiver can change over without losing a message.
- **What a message says is closed.** `{"type", "timestamp", "data": {"project", "event_id", "node", "object"}}`: the kind of news, the project's number, the event's number, the story or task's reference and, for an ask, a plan or a proposal, its number (`ask:12`). Never a title, a body, a question or a note, so a receiver that is tricked or leaks tells no one what the work is. The kinds (`notify_events.py`): `ask.raised`, `ask.answered`, `plan.proposed`, `plan.decided`, `placement.proposed`, `placement.decided`, `work.blocked`, `work.done`, `work.available` and `claim.lapsed`. **`work.available` is where this departs from the spec's "work ready":** readiness is worked out from links, gates and plans and is not an event, so the nudge says "work that may be ready changed, read `ready_work`", from the events that can free work (a story or task made, one finished or dropped, a link removed, a gate lifted, a plan approved, a question answered, work released), and at most one every ten seconds for a webhook. A status change is news once: finishing work as blocked or done records an update and a handoff, and only the update is news. **A lapsed claim is a time passing, not an event**, so it is found by looking at the claims table each tick (a claim that ran out since the last look), once for each claim and webhook (unique on the webhook, the kind and the subject).
- **Sent by a background job, never inside a request.** `Dispatcher` (`webhooks.py`, started with the server like the reindex job) reads each project's log from where it stopped (the same `(xid, id)` position and "all earlier transactions have finished" guard the change feed uses, so a late commit is not skipped), queues one row for each webhook that asked for each piece of news, sends what is due and mails the people who asked. A tool call only writes its event, so a dead or slow address cannot slow one (`tests/test_webhooks_integration.py` times 8 tool calls with a webhook that takes 20 seconds). A webhook only gets news after the moment it was added, and one turned off and on again does not get what happened while it was off. Retries wait 10 seconds, 1 minute, 5 minutes, 30 minutes and 2 hours, then the message is given up on (six attempts); a webhook is shown as failing, with what went wrong in words (never the address), until a message gets through; delivered messages are kept 7 days and others 30. "Send a test" sends a `ping` once, at once, and says how it went; it is never retried.
- **Where a webhook may go** (`webhook_address.py`): `https` only (and `http` only with `VRUM_WEBHOOK_ALLOW_INSECURE_HTTP`, for a receiver on this machine), a host, no user name or password, at most 500 characters. The name is looked up and every address it gives must be public (`ipaddress` says loopback, private, link-local which includes 169.254.169.254, shared, multicast, reserved and unspecified are not; an IPv6 address wrapping one is unwrapped first), when the webhook is saved and again just before each call, and the call goes to the address that was checked with the name kept for the certificate and the Host header, so a name that changes its answer in between gets nothing. A redirect is a failure and is never followed. `VRUM_WEBHOOK_ALLOWED_HOSTS` (names, addresses or networks) opens what a self-hosted install wants to reach. Nothing logs or shows an address (they often hold a token): a log line says only which webhook and how it ended. At most 10 webhooks a project.
- **Email nudges** go through the mail server M24 has, to a member who asked for them for a project (any role) and has a **confirmed** address, so that a message cannot be aimed at someone else's address; five kinds (`ask.raised`, `plan.proposed`, `placement.proposed`, `work.blocked`, `claim.lapsed`); the message says the kind, the story or task's reference and a link built from `VRUM_PUBLIC_URL`, nothing anyone wrote; at most ten an hour for a person (in memory, so a restart forgets); a person who leaves the project stops getting them. They are at most once: a failed mail is logged and not retried.
- **Two servers on one database both run the job**, which is safe (a message is leased while it is sent and the project's position is locked while news is read) provided they are set up alike, as replicas are; the check stack's second copy (`app-dex`) is given the same mail and webhook settings for that reason. Found when it was not: it took messages and failed them for want of the setting.
- **Not done:** the board's Users page section and Account page section for these (board worker), and nothing is sent for `gate` or work that becomes ready by a timer.

## 2026-11-23: choices made while building M50, review assistance (open to veto)

- **Checks are read, not stored, and only for a plan that still waits.** They are worked out when `list_plans` reads one plan whole, so they can never be stale; a decided plan has none (null), and a list has none (null). A check never stops or makes a decision: Approve and Reject work whatever the checks say.
- **Three checks, no more.** Circles, unsized work and possible duplicates, as the SPEC says. The circle check is the database's own rule read again (`circle_through` is shared with `create_plan`), so it can only ever agree with it; it cannot fail in practice because the trigger refuses a circle, which is why it exists as a visible assurance and not as a source of work. Unsized is the filter language's `no:size`, so the board's filter and the check cannot say different things, and nothing guesses a size. Duplicates use the same index, threshold and text (title and details) as the check `create_plan` makes, for epics and stories only.
- **Unavailable is its own state.** When meaning search cannot be used the duplicate check says "Not checked" and why; it is never shown as "no duplicates". The words also say when more items are waiting to be indexed than the plan itself holds, because then some existing work could not be compared yet.
- **Move scores are the suggestion ranking, run for the proposed parent.** `suggest_parent` and the scoring now share one preparation and one ranking, so they cannot disagree (a test compares them to 1e-9). The score is computed when a waiting proposal is listed, not stored when it is proposed, so a person never reads an old score. It costs one ranking per moved item (80 ms for a 20 item proposal on a small project) and is capped at 200 items a read; past that the proposal says it was not scored and is not routine.
- **Routine means the evidence all agrees, and it only changes where a card is drawn.** Every item scored, nothing to weigh (held, in progress, moved since, finished), the proposed parent ranks first for every item and is clearly ahead of the next (the same 0.05 margin that makes a suggestion "sure"). A new epic is never routine. A routine proposal is still decided by a person, still shows its whole diff when its group is opened, and the group never hides a warning because a proposal with a warning is never routine.
- **Scores and routine are null in the Needs list.** The sidebar count and the Needs list are read on every piece of news and stay cheap; the page reads `list_placements` once for the waiting proposals and shows a move's card only when that read has come back, so a card does not jump between groups.
- **Confirming a note and ticking a check in place call the item page's own operations.** No new tool, no new permission; a viewer sees the content and no control, and keys never confirm or tick.

## 2026-11-23: choices made while building M51, review conversations and revised plans (open to veto)

- **A revision is the whole plan, and it is kept whole.** An agent sends `revise_plan` with every item the plan should hold now. Each proposal and revision keeps what it held as a snapshot in its own event, so what a person read, and what they said about it, can be read exactly as it was whatever the items have become since. The plan keeps its number (the id of its proposal) and, as before, the plan's items are held while it waits.
- **An item continues another by `ref`, a criterion by `id`; what nothing continues is removed.** A removed item is dropped, with a handoff note "Removed in revision 2 of Plan 3: ...", and is no longer part of the plan, so no later approval frees it. Links and criteria left out of a revision are kept for the items that are kept; given, they are the whole set. A field of a kept item left out takes its default (a size left out clears it), because a revision says what the plan is, not what changed.
- **A revision is checked as a whole with the checks a new plan meets, and a refused one changes nothing.** It uses the same checks as `create_plan` (hierarchy, sizes, dates, links, circles of waiting through the plan and through work that exists) and the rules of revising: what is removed cannot still be referred to, cannot be waited for by work outside the plan (it would wait for dropped work for ever), and cannot have live work outside the plan under it; a kind cannot change; a criterion cannot move to another item. The circle check of `create_plan` and the plan check of M50 now share one function (`circle_through`).
- **Request changes is a person's, separate from Reject.** It keeps the plan held and records a summary (required) and comments on the lines of one revision; the server keeps the words each comment is about (`quoted`), so a later edit cannot attach it to other words. Reject still ends the plan and works in both waiting states; approval is refused while changes are asked for and nobody has revised.
- **A decision names the revision it reviewed.** `approve_plan` takes `revision` (optional on the tool, always sent by the board), and `request_plan_changes` requires it: a plan that has a newer revision is refused with plain words and nothing is changed. It is optional on `approve_plan` so that a script that decides the latest on purpose still can; the board is the only place a person decides.
- **A held plan changed outside a revision cannot be approved.** Items of a waiting plan can still be edited by the ordinary tools, which would make "the revision a person reviewed" mean nothing. The server compares the items with the revision's snapshot (title, details, priority, size, dates, parent, links that make work wait, acceptance criteria, dropped) and refuses to approve while they differ, naming the items; `drift` is shown on the plan so a person sees it first. A link that does not make anything wait (relates to, discovered from) does not count. Rejecting is never held back by it, and a revision brings the plan back in line.
- **`revise_plan` is not in the standard 25 agent tools.** The standard set is at its limit and the harness that drafts and revises plans is given `list_plans` and `revise_plan` in its key's allowance; any agent can still learn of a request from the change feed (the event carries the summary and comments) and from `get_node`'s `held_by`. 65 tools are on the board now, 56 offered to a key with every tool, 7 people only.
- **Anyone who may call `revise_plan` may revise any waiting plan.** Not only its proposer: another agent (a lead agent, a replacement) can take it over, and the history says who made each revision. The person reads every revision before anything is freed, which is the safeguard.
- **Pending comments live in the page, not on the server.** A person collects comments and a summary in the page and they are sent together with Request changes; like Viewed they are lost on reload. When a revision arrives under a person, the unsent comments of the old revision are not kept (they would name the old revision) and the page says so. A pending review stored on the server would be a new table and a new thing to export, and the loss is small.
- **A plan page for the history.** A plan has no page of its own before M51 and a plan waiting for its agent is in no Needs row, so the board has `#/plan?plan=N`: read-only, every revision with the agent's note, the feedback and what changed, and a link to review it when it waits for a person. The Needs page says one quiet line when plans wait for their agent.
- **Webhooks and nudges keep ten kinds.** A revision is news like a proposal (`plan.proposed`) and a request for changes is news like a decision (`plan.decided`), so a harness that waits on a webhook wakes when feedback arrives, and a person is nudged when a revision is ready to read.
- **The change feed carries snapshots.** `plan_proposed` and `plan_revised` events hold the snapshot of what they proposed, so a feed page with several is larger. They are kept there, in the event, because it is the one place that is already append-only, exported and imported.

- **A Viewed mark can come off when the index catches up (found while building the board, M50's rule).** The fingerprint of a plan card includes the words of its duplicate check, and those change when items that were waiting to be indexed get indexed ("2 existing epics and stories are not indexed yet" becomes a result). So a plan marked Viewed can come back unmarked once the index finishes. It is safe (a person re-reads), but it can surprise. The alternative is to leave the index backlog out of the fingerprint, so a mark comes off only when the plan itself changes.
- **Board wording choices.** The crumb on a plan's page reads "Needs a person / Plan 9". An unsent comment about links quotes the server's own words (`needs_first task:5`) so that it equals what the server will keep as the quote. The three decision buttons are disabled only while a card is known to show an older revision than its row, not during the first read of a plan. The plan page shows only the feedback given on the selected revision (the card shows all earlier feedback).
- **Not in M51 on purpose.** No comment on a removed (`-`) line, on a details line or on a criterion line; no comment from the plan page; no removing an item directly (the reviewer asks for it in a comment and the agent removes it); pending comments are lost on reload.
