# vrum: a self-hosted project graph for AI agents

## 1. Purpose

A small server that an AI agent (and a human through the agent) uses to plan and track work as an **exact hierarchy**: Epic → Story → Task. It adds a **derived semantic index** to find overlaps and related items, and a **memory layer** of decisions, principles, facts and beliefs that each point to the items they affect.

**Goal: effective, efficient, agent-friendly and human-friendly coding project management.** *Effective:* an agent always knows what to do next, why, and what was already decided, and two agents never collide or redo each other's work. *Efficient:* every answer is small, every common job is one call, and nothing needs asking twice. *Agent-friendly:* a strict structure the database enforces, plain refusals, and handoffs that survive the end of a session. *Human-friendly:* a person can see everything the agents are doing, and steer it, without learning the tool's internals. Section 10 says what Vrum takes from GitHub Projects, Obsidian, Hindsight, Elasticsearch and Taiga to get there, and what it leaves out.

Three layers, with one rule between them: **memory suggests, the graph decides.**

1. **Exact graph (source of truth).** Epics, stories, tasks, rules (requirements), typed links, decisions, history. Everything that must be true is enforced by the database, not by the agent's good behaviour.
2. **Derived semantic index.** An embedding of every epic, story, rule, decision, fact and belief. It can be dropped and rebuilt at any time and never decides anything.
3. **Memory layer.** Decisions and principles (what people decided, with their reasons), and facts and beliefs (what is known, and what is concluded from it, each saying where it came from). All of it is linked to the items it concerns. Recalling it is exact first (by link), similar second (by index). A decision is authoritative because a named person made it. A fact says where it came from. A belief is a conclusion drawn from named evidence and is only a suggestion until a person confirms it. Whatever a language model wrote is labelled as such everywhere it appears and never counts as a decision.

## 2. Who uses it and how

- **AI agents** connect over **MCP** (Model Context Protocol) to the container. This is the main interface.
- **A human** works through the agent and, from M10 to M14, through the **board** in the browser: a small set of pages (section 10 lists them all) served by the same container, which show every part of the product and let a person do what an agent can do. There is no other web UI. The wider human view of the work may still live elsewhere (for Deelio, a Taiga project), and this tool must be able to export to it later.
- **Self-hosting:** `docker compose up` on one machine. Data lives in a named volume. A backup and a restore are documented and tested.

## 3. Defaults the owner may veto (record each change in DECISIONS.md)

- **Language and framework:** Python 3.12 with the official MCP Python SDK (do not hand-roll the protocol; check its current documentation first), `pytest`, one lint and one type check.
- **Database:** PostgreSQL with `pgvector`, in the same compose file as the app. One database holds the graph and the index tables.
- **MCP transport:** streamable HTTP on a configurable port, bound to localhost by default, with a bearer token read from an environment variable or a secret file. No anonymous access and no default token.
- **Embeddings:** a locally hosted model reached through one small interface and an OpenAI-compatible base URL, configured by `EMBEDDING_BASE_URL` and `EMBEDDING_MODEL`. The compose file offers an optional `local-embeddings` profile that runs a local embedding service (Ollama with the small model `all-minilm`, which is multi-architecture and so runs on Apple silicon too). The vector size is read from the model, never hard-coded. No data leaves the machine unless the owner points the base URL elsewhere.
- **Language model (optional, M5C):** a locally hosted or owner-chosen model reached through the same kind of small interface and an OpenAI-compatible base URL, configured by `LLM_BASE_URL` and `LLM_MODEL`, with a key from the environment or a secret file if one is needed. It is off unless set. Without it, everything works except proposing facts from text, drawing up beliefs, finding which beliefs a new statement contradicts and answering questions in words; an agent can still record facts and beliefs itself. No data leaves the machine unless the owner points the base URL elsewhere, and text containing a well-known secret format is never sent.
- **Identity of actors:** every write names an actor (a person or an agent name) given by the caller.
- **Board (M10 to M14):** plain HTML, CSS and JavaScript served by the same server and port under `/board`, with no build step and nothing loaded from the internet (the graph is drawn by the board's own code, and Markdown by its own small renderer). People sign in with the same bearer token. Browser tests use Playwright, as a development dependency only, never in the app image.

## 4. Non-goals (do not build)

A web UI other than the board pages in M10 to M14, sprints and iterations, story points, velocity and burndown charts, comments threads, notifications, multi-tenant accounts and separate memory banks (one install is one project), billing, a plugin system, plans written by a language model on the server, standing answers or pages that a model rewrites on a schedule, built-in agent orchestration or spawning, importers other than the one in M8, and any abstraction without a consumer in a milestone below. ## 5. The data model (exact; enforced in the database)

- **Node** with a kind: `epic`, `story` or `task`.
    - An epic has no parent. A story has exactly one parent, which is an epic. A task has exactly one parent, which is a story. Any other combination is refused by the database.
    - Fields: id, kind, parent, title, body (plain text or Markdown), status, priority, start date and target date (both optional, from M1A), version (integer for optimistic locking), created and updated times.
    - Dates: a start date and a target date, which are plain dates with no time. When both are set the start is not after the target, which the database enforces. They are what the roadmap draws. An epic or story with no dates of its own shows the span of its children's dates, marked as worked out. A node is overdue when its target date has passed and it is not done or dropped. A node whose own start date is before the target date of something it needs first is shown with a schedule conflict: that is a warning, never a refusal.
    - Status: `new`, `ready`, `in_progress`, `blocked`, `done`, `dropped`. `ready` is computed: a node is ready when it is `new` and every `needs_first` target is `done`.
- **Rule** (a requirement): a stated rule, with a status `held`, `settled` or `dropped`, and **at most one owning story**, enforced by a single column, never a join table. Moving a rule to another story is one atomic operation recorded in history. A rule with no story is "unplaced".
- **Link** between two nodes, with a type:
    - `needs_first` (the source cannot start before the target is done; cycles are refused),
    - `supersedes`, `duplicates`, `relates_to`.
  Links between a node and itself are refused.
- **Decision:** id, date, title, text, reason, decided_by (a named person), status `active` or `superseded`, and a `kind` of `decision` or `principle`. A decision links to zero or more nodes and rules, and may supersede another decision.
- **Fact** (from M4A): a statement about the project or its world, with where it came from. Fields: id, kind `world` (something true about the project, its tools or its domain) or `experience` (something that was done or observed), text, source (plain words saying where it came from, never blank), when it was true or happened (optional) and when it was recorded, who recorded it, origin `stated` (a person or agent wrote it) or `extracted` (a language model proposed it from a quoted passage, M5C), and status `active`, `superseded` (replaced by a newer fact) or `retracted` (found to be wrong, with a reason). A fact is never edited: it is superseded or retracted. A fact links to zero or more nodes, rules and decisions.
- **Belief** (from M4A): a conclusion drawn from evidence. Fields: id, text, evidence (one or more facts or decisions, never other beliefs, so a conclusion is always one step from what it rests on), who recorded it, origin `stated` or `derived` (a language model drew it up from the evidence, M5C), status `active`, `superseded` or `retracted`, and, when a named person has looked at it, who confirmed it and when. How many pieces of evidence it has is worked out. A belief is **stale** when any of its evidence is no longer active, which is worked out and never set. A belief is never edited: it is superseded by a revised belief or retracted. A person can promote a belief to a decision, which records a new decision made by that named person and keeps the link to the belief. A belief links to zero or more nodes and rules, and is only ever a suggestion: it never changes the graph and never counts as a decision.
- **Claim:** at most one actor holds a claim on a task or story at a time, with a lease that expires. Claiming is atomic.
- **Event log:** every create, update, move, link, claim, decision, fact and belief is appended with actor, time and before-and-after. Nothing is overwritten silently. Updates that carry an old `version` are refused with a clear message.

## 6. The MCP tools (plain names, plain descriptions an agent can read)

Create, get, list, update and move nodes (with their dates); add and remove links; ready work; claim, renew and release; place and move rules; coverage report (unplaced rules, stories without rules); record, supersede and recall decisions, principles, facts and beliefs; search; find overlaps; reindex; export and import; history of one node. From M5, search matches by exact words, by meaning or both, and says how each result matched; agents can ask for items similar to an item or a text, for pairs of stories that overlap across epics, and for the index to be brought up to date. From M5B, agents also get: the next work with its context in one call, finishing work with a handoff note, a whole plan created at once, several nodes updated at once, what changed since a given event, and a check for similar existing items. From M5C, and only when a language model is configured, agents can ask for facts to be proposed from text, for beliefs to be drawn up from facts, and for a question to be answered in words from the memory, with every answer labelled and citing the items it used. Search, similar items and find overlaps say how many items are waiting to be indexed (from M5, which M10 shows on its pages). From M13, `find_mentions` lists the items whose text refers to a given item. Every tool returns clear, plain-English refusals that say what was wrong and what to do next, and every list is paged.

## 7. Milestones

Each milestone ends in working behaviour reachable through MCP in the running containers. Tick them in order.

- **M0. Bootstrap.** Repository, SPEC.md, PROGRESS.md, AGENTS.md, DECISIONS.md, one check command (`./check.sh` or equivalent: lint, types, unit and integration tests), and a compose file where the database and the app start and a health check passes.
  *Proof:* from a clean clone, `docker compose up -d` becomes healthy, and an MCP client lists the tools.
- **M1. Graph core.** Schema, constraints, node create, get, list, update and move, optimistic versioning, event log.
  *Proof:* through MCP, a story without an epic, a task under an epic, a second parent and a stale version are each refused with a plain message; a valid epic, story and task are created and their history is readable.
- **M1A. Dates.** Added after M4 and run before M5, because the roadmap (M11) needs them. Every epic, story and task gets an optional start date and an optional target date, set when a node is created or updated, cleared by an explicit request, and shown by `get_node` and `list_nodes`, which can also filter by them. The database refuses a start date after the target date. Nodes report whether they are overdue, the span of their children's dates when they have none of their own, and any schedule conflict (their start is before the target date of something they need first). Date changes are in the history with before and after like any other change. Under the prototype stance the database is rebuilt, with no upgrade step.
  *Proof:* through MCP, a start date after the target date is refused with a plain message, and the database refuses it on its own; dates set and cleared are shown by `get_node` and are in the history with before and after; a node whose target date has passed is overdue until it is done or dropped; an epic with dated children and no dates of its own reports their span, and one with its own dates reports those; a dependent whose start is before its prerequisite's target date is reported with a schedule conflict that goes away when either date changes; a stale version is still refused for a date change. All earlier proofs still pass.
- **M2. Links, readiness and claims.** Link types, cycle refusal, computed readiness, atomic claims with leases.
  *Proof:* a cycle is refused; finishing a prerequisite makes its dependent ready; ten parallel claimers on one ready task produce exactly one winner; an expired lease can be claimed by another actor.
- **M3. Rules and coverage.** Rules placed in exactly one story, atomic moves, the coverage report.
  *Proof:* a rule cannot be placed in two stories; a move is atomic and logged; the coverage report lists unplaced rules and stories with none.
- **M4. Decisions and principles.** Record, link, supersede and exact recall by node, plus the list of active principles.
  *Proof:* recalling a story returns its linked active decisions and all active principles; a superseded decision is shown as such and not as active; nothing is invented.
- **M4A. Facts and beliefs.** Added after M4 and run before M5. The rest of the memory layer from Hindsight, with its guard rails: facts, beliefs, and one recall of everything known about an item.
    - **Facts.** `retain_fact` records a fact with its source, its kind (`world` or `experience`), optionally when it was true, and the nodes, rules and decisions it concerns. A fact is never edited: `supersede_memory` replaces it, or several at once (see "When something is no longer true"), with a newer fact in one step (the old one is kept, marked superseded, pointing at its replacement), and `retract_memory` marks it wrong, with a reason. A blank source or text is refused.
    - **Beliefs.** `record_belief` records a conclusion with its evidence: one or more active facts or decisions. A belief with no evidence, with evidence that does not exist or is not active, or whose evidence includes another belief, is refused. A belief is stale while any of its evidence is not active, which is worked out and shown, never set by hand. A belief is superseded by a revised belief or retracted, never edited. `confirm_belief` records that a named person has looked at it. `promote_belief` turns a belief into a decision made by a named person, with a reason, and keeps the link back.
    - **When something is no longer true.** Nothing is edited, so a change is always a newer item that replaces older ones. The server never decides by itself that something is contradicted: a person or an agent names what is replaced.
        - *Replace several at once.* `supersede_memory` takes one or more active items of the same kind, however many, and the newer item that replaces them; `retract_memory` likewise takes one or more. In one step the newer one is recorded and each old one is marked superseded, pointing at it, with the reason. If any listed item does not exist or is not active, nothing is changed and the message names it. A new belief still needs its own evidence. The only limit is M6's cap on the size of a request.
        - *Walk everything.* `list_memories` pages through every fact and belief in id order (`after_id` and `next_after_id`, like every list) and says how many match in all, so a caller can go through all of them and see from the count that none was skipped. It takes `within_node_id` (an epic, story or task), which matches what concerns that item or anything under it in the hierarchy, or a rule placed in one of those stories, so the beliefs about a whole area are one paged walk and not one recall per item. It also takes `node_id` and `rule_id` for exactly one item.
        - *See what rests on what.* `list_memories` takes `rests_on_memory_id` (a fact) or `rests_on_decision_id` and lists the beliefs that rest on it. The answers of `retract_memory` and `supersede_memory` say which beliefs went stale because of the change (their ids, to read with that filter), and which decisions were promoted from a belief that was replaced (those decisions are only reported, never changed). `retract_memory` with `with_dependent_beliefs` also retracts, in the same step and with the same reason, every active belief that rests on the retracted item. Without it those beliefs are only shown as stale, because a belief with other evidence may still hold.
        - *What a person confirmed needs a person.* Replacing or retracting a belief that a person has confirmed needs `said_by` (who changed their mind) and `quote` (what they said, or where). An agent told "the owner no longer thinks so" passes the owner's name and words, and the history shows both the person and the agent that relayed it. A belief nobody has confirmed (a suggestion, including a derived one) can be replaced or retracted by anyone, with a reason. As with `decided_by` on a decision, the server records who is named and cannot prove that the person said it. A person changing their mind about a decision uses `supersede_decision` (M4).
    - **Links, lists, history.** `link_memory` and `unlink_memory` change what an active fact or belief concerns. `get_memory`, `list_memories` (filtered by type (fact or belief), kind, status, origin, stale, what it concerns and what it rests on) and `memory_history` read them. Everything is in the event log, and what a fact or belief concerns shows in the histories of those nodes.
    - **One recall.** `recall` (it replaces `recall_decisions`, since it returns more than decisions) takes a node or a rule and returns, in separate labelled sections: its active decisions, every active principle, its facts and its beliefs, and, apart from those, what has been superseded, retracted or gone stale. Beliefs are included when they are linked to the item or when their evidence is. Every entry says why it is there (linked directly, a principle that applies everywhere, resting on evidence linked here, replaced by item N), who recorded it and, for a fact or belief, its origin. A belief is always labelled a suggestion. Each section has its own count and page. Nothing is inferred beyond those exact links.
  *Proof:* through MCP, a fact is retained against a story and appears in the story's recall under facts with its source, origin, recorder and both dates, and never under decisions; a belief with two facts as evidence reports two pieces of evidence and appears under beliefs, labelled a suggestion; retracting one of those facts makes the belief stale, shown apart and never as active, with the reason, and so does superseding one; a belief with no evidence, with evidence that does not exist, or with another belief as evidence is refused in plain words; a blank source is refused; confirming a belief records who and when; promoting it records a decision by that person that links back to the belief; a superseded fact shows as superseded with its replacement; the recall holds exactly what the exact links give and nothing else; with three beliefs, a new belief that contradicts two of them replaces both in one `supersede_memory` call, each old one shows as superseded by it and the third is untouched, and a listed belief that is already retracted refuses the whole call and changes nothing, and a call that replaces 30 beliefs at once works; `list_memories` over 60 beliefs, in pages, returns every one exactly once and a count that matches, and `within` an epic returns what concerns its stories and tasks and nothing else; retracting a fact reports the belief that went stale, and with `with_dependent_beliefs` retracts that belief too with the same reason, while `list_memories` with `rests_on` lists the beliefs resting on the fact; replacing or retracting a confirmed belief without `said_by` and `quote` is refused in plain words, and with them it works and the history shows both the person and the agent that relayed it, while an agent alone can retract a belief nobody confirmed; replacing a belief that was promoted reports the decision, which is unchanged. The database refuses, on its own, edits and deletes of facts and beliefs, a belief without evidence, and evidence that is a belief. All earlier proofs still pass, M4's with `recall` in place of `recall_decisions`.
- **M5. Search and the semantic index.** Embedding client, reindex job, and `search` that matches three ways: by exact words (PostgreSQL full-text search over the graph itself, so it is current the moment a change is saved and still works when the embedding service is down), by meaning (the index), or both fused by rank. Each result says how it matched (words, meaning or both), why (the words that matched, or the similarity score), its current parent and status from the graph, and a highlighted snippet; the answer also carries counts by item type and status. Overlap finder (nearest neighbours across epics above a configurable threshold, with scores, never merging or changing anything), similar recall of decisions, facts and beliefs, and "similar items" for an item or a piece of text. Decisions, facts and beliefs are searched too, and each result carries its origin so that a belief or an extracted fact is never mistaken for a decision. Queries never fail on odd characters. Meaning results are suggestions, labelled as such.
    - **Search.** `search` takes a query, a mode (`both`, the default, `words` or `meaning`), optional `types` and `statuses`, a `min_similarity`, and `limit` and `offset` (results are in rank order, so this list pages by offset, not by id). Exact words are whole words with their endings (a search for "migration" finds "migrating"); every word must be present, a phrase goes in double quotes, `or` allows alternatives and `-` leaves a word out. Results cover epics, stories, tasks, rules, decisions, principles, facts and beliefs. Tasks are found by exact words only, because they are many and short; everything else is also embedded. Fusing is by rank (an item's score is the sum of 1 / (60 + its rank) over the lists it is in), so what matches both ways comes first. A result of meaning alone is flagged `suggestion`, as is a belief or anything a model wrote. The counts by type and by status are taken before the `types` and `statuses` filters, so a person can see what filtering would give. When meaning cannot be used (no embedding service, the service cannot be reached, the index is not built for the configured model) the answer says so in a note and still gives the exact-words results; asking for `meaning` alone then is refused in plain words.
    - **The reindex job.** The index holds one vector per epic, story, rule, decision, principle, fact and belief, and is derived from the graph: dropping it loses nothing. The job (`reindex`, and a background task in the server that runs every few seconds when something is waiting) is the only code that writes to it. An item is waiting when it has no vector or its text changed since it was embedded (a change to its status or links does not count), so the job needs no signal from the writers. The size of the vectors is read from the model when the index is built, and an index built with another model or size is dropped and rebuilt. If the service refuses one item the rest are still indexed and the report lists the refused one. If the service cannot be reached, nothing is lost: what was embedded stays and the job tries again later. Every answer of `search`, `similar_items` and `find_overlaps` says how many items are waiting.
    - **Similar items and overlaps.** `similar_items` takes one of a node, rule, decision, fact or belief id, or a text, and returns the items nearest in meaning, with scores, never the item itself. `find_overlaps` returns pairs of stories (or epics, or rules) in different epics whose similarity is at least the threshold (`min_similarity`, default `EMBEDDING_OVERLAP_THRESHOLD`), most alike first, and says which links already join the two; it can be limited to pairs involving given epics, and leaves out dropped items unless asked. It only reports. `recall` gains `with_similar`: a last section of active decisions, facts and beliefs that are alike but not linked, labelled suggestions; the exact sections do not change.
    - **Default thresholds** are for the local model and are measured, not guessed: see `DECISIONS.md`. They are settings (`EMBEDDING_MIN_SIMILARITY`, `EMBEDDING_OVERLAP_THRESHOLD`), because another model scores differently.
  *Proof:* on a fixture of known duplicate and known unrelated pairs, the overlap finder flags the duplicates and not the unrelated pairs, and the measured counts are printed; dropping the index tables and running reindex gives the same results; no tool other than reindex writes to the index. With the embedding service stopped, a phrase added to a story is found by words at once and labelled as an exact-words match, while a paraphrase of it is found by meaning only after the service returns and reindex has run. Results that match both ways are labelled both. The counts by item type equal what the list tools return. A fact and a belief are found by words and by meaning, labelled with their origin. The checks run against a scripted stand-in for the embedding service (`tests/scripted_embeddings.py`, in the check stack), which proves what Vrum does with a service and not how good a model is, so the same fixture of reworded requirements is also run once against the real local model (the `local-embeddings` profile, `scripts/real_embeddings_check.py`) and its measured counts are recorded in `PROGRESS.md`.
- **M5B. Agent workflow.** What an agent needs to do a day's work in few calls and small answers, built on the earlier milestones. It is numbered M5B so that no other milestone is renumbered, and it comes right after M5 in order.
    - **Next work, with its context, in one call.** `next_work` picks the most urgent free story or task (highest priority first, then the earliest target date, then oldest), claims it atomically, marks it in progress, and returns it together with what an agent needs to start: its parent chain, the rules of its story, the active decisions, facts and beliefs linked to it and to its parents (facts and beliefs labelled, beliefs as suggestions, stale ones left out), every active principle, the handoff notes left by earlier holders of the item and of what it waited for, what finishing it will unblock, and similar existing items. Free means nobody holds it, nothing it needs first is open, and it is ready, or it was in progress and its holder's claim ran out (the answer then says who let it lapse). A story whose tasks are still open is not handed out: it is worked through its tasks. An optional `within_node_id` limits the search to one epic or story. A peek option returns the same without claiming. When nothing is free the answer says so and how much work is held, waiting or blocked: this is not an error. Everything in the context comes by exact link; similar items are labelled as suggestions. The context is cut from the end to a stated size (`context_chars`) and says what was left out.
    - **Handoff notes.** Ending work is one call, `finish_work`: the holder says whether the item is done, blocked, dropped or only released (back to not started), and writes a handoff note (what was done, what the next person must know). A blank note is refused, by the tool and by the database. `release_claim` needs a note too, and puts work that was in progress back to not started. Only the holder can finish, including one whose claim ran out before anyone took over. The note is kept in the item's history and comes back with `get_node` and `next_work`; a claim that lapsed shows as lapsed with no handoff.
    - **A whole plan at once.** `create_plan` creates epics, stories, tasks, links between them and rules in one all-or-nothing call, from items given with temporary keys, any number of them. One bad item refuses the whole plan, and the message names that item and what is wrong. A plan that would make a circle of waiting is refused whole.
    - **Several changes at once.** `update_nodes` changes any number of nodes, each with its own expected version, and reports each one separately: one stale version does not undo the others.
    - **What changed.** `changes_since` lists events after a given event id across the whole graph, filtered by actor or by one item, a page at a time, with the latest event id to keep. Events are shown in the order their changes began, and an event is shown only once the change that wrote it has finished, so a follower never skips one that was written slowly. An agent that comes back after a break, and the board, see only what is new.
    - **Small answers.** Lists leave out bodies by default and say so (each item gives its body length and its first 120 characters instead); a detail option asks for them; reading one item always gives the whole body. Lists also say how many items match in all. Every tool that can return a lot has a stated limit and says how much it left out.
    - **Check before creating.** `create_node` (for epics and stories) and `create_plan` (for its epics and stories) answer with similar existing items (from the index, at least as alike as the overlap threshold, labelled as suggestions) and still create. If the embedding service cannot be reached they say so and still create. Tasks are not checked.
    - **Server instructions.** The MCP server's own instructions tell any agent the working loop in a few lines: take work with `next_work`, recall what is known before deciding, record decisions as they are made, end with `finish_work`. They name only tools that exist, and a test compares them with the live tool list.
  *Proof* (a real MCP client against the real containers):
    1. Ten agents call `next_work` at once on five ready tasks: five each get a different task, none gets a task twice, and the rest are told plainly that nothing is free. Each context holds exactly the parent chain, the rules of the story, the linked active decisions (a superseded one only in its own section), all active principles and any earlier handoff notes.
    2. `finish_work` with a blank note is refused and changes nothing. With a note the item is done, its dependent becomes ready, and the next agent's `next_work` shows the note. A claim that lapsed shows as lapsed with no handoff.
    3. `create_plan` creates one epic, three stories, eight tasks, five links and four rules in one call. A plan with one invalid item, or with a circle, creates nothing and names the problem. A plan of 500 items is created in one call.
    4. `update_nodes` with five changes, one of them stale: four apply and are in the history with their actor, one is refused with the stale-version message and changes nothing. A call with 120 changes reports each one.
    5. `changes_since` returns exactly the events made after a given id, nothing before and nothing missing, and pages correctly. An event written by a slow change that finishes after a later one is still shown, once it has finished.
    6. A list of 50 items with long bodies (about a page each) is at least five times smaller by default than with the detail option; both sizes are printed.
    7. Creating a story whose title repeats an existing one returns the existing one as similar, and still creates it; with the embedding service stopped it says so and still creates.
    8. The server instructions are shown by the client and name only tools that exist. All earlier proofs still pass.
- **M5C. Extraction and reflection (needs a configured language model).** The parts of Hindsight's memory that need a model, built so that nothing a model writes can be mistaken for a record. When `LLM_BASE_URL` is not set the tools below say plainly that no language model is configured, and everything else keeps working.
    - **Proposing facts.** `extract_facts` takes a piece of text (an item's body, a handoff note, pasted notes) and returns the facts a model found in it, each with the exact passage it came from. The server checks that each passage occurs in the text and drops any proposal whose passage does not. By default nothing is stored. With the store option each fact is retained with origin `extracted`, the passage as its source, and the caller as the one who recorded it.
    - **Drawing up beliefs.** `consolidate_memory` takes a set of active facts (chosen by item or by search) and asks the model for the conclusions they support. Each belief must name evidence from the facts it was given, and one that names anything else is dropped. It is recorded with origin `derived`. When a belief has gone stale, the model can be asked for a revised belief, which supersedes the old one and is again only a suggestion.
    - **Finding what a new statement contradicts.** `find_contradictions` takes a new statement, or the id of a fact or belief, and has two scopes. `related` (the default) takes the active beliefs it may clash with (the same items, shared evidence, words and meaning, as `reflect` retrieves them) and says how many that was out of all active beliefs, for example "looked at 14 of 312", so a partial look is never taken for a full one. `all` goes through every active belief in id order, one batch per call (25 by default, set by `batch`; `after_id` and `next_after_id` as in every list), and reports how many it has looked at and how many remain, until none remain: that is the check of the whole memory. A belief recorded during a sweep has a higher id and is reached the same way. For each batch the model is asked which of those beliefs the statement contradicts and why. Each answer names a belief in that batch and quotes the clashing part of the belief and of the statement, and the server drops any answer that names a belief not in the batch or quotes text that is not there. It returns proposals only and changes nothing: applying them is a `supersede_memory` or `retract_memory` call by a person or agent, with `said_by` and `quote` where a person confirmed the belief. It costs one model call per batch and runs only when called. Without a model, an agent walks the same way with `list_memories` and judges the beliefs itself.
    - **Answering a question.** `reflect` takes a question, retrieves over decisions, principles, facts and beliefs by exact links, words and meaning (the same retrieval as search), and asks the model to answer using only what was retrieved. The answer lists the items it relied on, and an answer that cites anything that was not retrieved is refused. The answer is labelled generated and is not stored; a caller who wants to keep a conclusion records it as a belief with its evidence.
    - **Care.** Text is checked for well-known secret formats before it is sent, and is never sent if it has one (the same check M6 applies to every write). Every call is in the event log (who asked, what was asked, which items were used). A model that cannot be reached gives a plain message and changes nothing.
  *Proof* (a real MCP client against the real containers, with a scripted model: a small OpenAI-compatible test service in the check stack that gives fixed answers, so that the proof is about what Vrum does with a model's output and not about a model's quality):

    2. `extract_facts` on a text returns the scripted facts with their passages and stores nothing by default. With the store option it retains them with origin `extracted` and the passage as source. A scripted fact whose passage is not in the text is dropped.
    3. `consolidate_memory` records the scripted belief with origin `derived` and its evidence, and drops a scripted belief that names a fact it was not given. Retracting one piece of evidence makes the belief stale, and a revised belief supersedes it.

## 8. Quality bar

- Tests prove behaviour through MCP against real containers. Do not test your own mocks.
- Each milestone keeps all earlier proofs passing.
- Never commit a secret. Configuration comes from the environment.
- Keep to one owner module per concept; reuse it rather than copying.
- Plain English in every message a person or agent reads.
- Answers are small by default, because an agent's context is expensive: lists leave out long text, and any tool that can return a lot has a limit and says how much it left out.
- Every page of the board works from the keyboard and never uses colour alone. Each of M10 to M14 adds its pages to the README and its scenario to `./acceptance.sh`.
- Whatever a language model wrote (an extracted fact, a derived belief, an answer) is labelled as such everywhere it appears, quotes or cites what it came from, is checked against that source by the server, and is never treated as a decision or as part of the graph.
- No part of the product is without a page: a part a person cannot see on the board is a gap, and is listed in `PROGRESS.md` until it has one.

## 9. What the loop must never do

Touch any Deelio repository or the Taiga project, send data to a third party without the owner setting the base URL, invent a product answer, bulk-generate sample data that looks real, or tick a milestone whose proof has not passed.

## 10. Product shape: what Vrum takes from the tools it is measured against

Vrum is one product with two ways in that always call the same operations: MCP for agents, the board for people. It combines the best parts of five products, and this section says which, and what is left out on purpose, so that a missing feature is a decision and not an accident. The sources are each product's own documentation.

| Product | What Vrum takes | Where | Left out on purpose, and where Vrum is better |
|---|---|---|---|
| **GitHub Projects** (docs.github.com/en/issues/planning-and-tracking-with-projects) | Several views of the same items (board, table, roadmap); drag a card or a bar to change its value; filter, group and sort; shareable views; batch edits; progress roll-ups; keyboard use | M1A, M10, M11 | No iterations or sprints, no burn-up charts, no items tied to a repository. Better: a real dependency graph with cycle refusal and a computed "ready" (GitHub stores blocked-by as plain metadata), a roadmap that draws the dependencies and flags schedule conflicts, filters that can OR across fields, and one filter language for agents and people. |
| **Obsidian** (obsidian.md/help) | The whole graph and the local graph with depth, as views; backlinks; `[[references]]`; Markdown; quick switcher; a Markdown export people can open in Obsidian | M7, M10, M13 | The whole graph is one view among several and never the only way to find something, because it stops being usable at very large sizes (so it has a dot limit and collapses epics). No files as the source of truth (no atomic writes or locks), no Canvas, no plugins. Better: enforced structure, computed state, versioned edits and claims. |
| **Hindsight** (hindsight.vectorize.io) | Facts (world and experience) and beliefs drawn from evidence, with how many pieces of evidence, marked stale when the evidence changes; recall that combines exact links, words, meaning and time and says why each result came back; extraction of facts from text, consolidation into beliefs and reflection, when a model is configured; two dates (when true, when recorded); a short start-of-work briefing from exact data; old items marked superseded | M4, M4A, M5, M5B, M5C, M12 | No automatic capture of whole transcripts, no fuzzy merging of entities, no overwriting on re-save, no open MCP by default, no standing answers or pages that a model rewrites on a schedule. Better: every memory has a named author or a labelled origin and exact links; a fact needs a source; a belief can only rest on facts and decisions it names, is a suggestion until a person confirms it, and never counts as a decision; what a model proposes is checked against its quoted passage or its evidence before it is kept; a change supersedes instead of rewriting. |
| **Elasticsearch** (elastic.co/docs) | Exact-words and meaning results fused by rank and labelled; counts by category; highlighted snippets; why a result matched; similar items; queries that cannot fail | M5, M13 | Not Elasticsearch itself (a second heavy datastore to keep in sync), no custom analyzers or relevance tuning, no query language for agents. All of it is done inside PostgreSQL. |
| **Taiga and its MCP servers** (docs.taiga.io and the community MCP servers) | Epics, stories, tasks; bulk creation; filters; history; versioned edits; export | M1 to M7, M5B | No sprints, comments, attachments, roles, issues as a separate kind, wiki pages, votes or watchers. Better: `needs_first` links, computed ready, atomic claims with leases, versions an agent must send back (several Taiga servers fetch the version themselves, which defeats the check), one call for the next work, search by meaning, and rules and decisions as first-class memory. |
| **Agent task tools** (Beads, Claude Code task lists, Linear, Task Master, Backlog.md, the Copilot cloud agent) | Ready-work lists, atomic claims, handoff notes, whole plans created at once, the state of each agent visible to people | M2, M5B, M14 | No agent orchestration or spawning, no plans written by a language model on the server, no heavy locks, no story points. |

**What matters most for effective, efficient, agent- and human-friendly work, in order** (from the research on agents and project management): 1. one call for the next work with its context; 2. ready work that respects dependencies and refuses circles; 3. expiring claims and versions instead of locks; 4. handoff notes that outlive a session; 5. small answers, paging and few consolidated tools; 6. a whole plan created at once; 7. decisions and principles brought to the agent with their reasons; 8. what the agents are doing visible to people, with conflicts and stale claims; 9. finding earlier work before duplicating it; 10. seeing what changed since last time.

**The pages**, so that every part of the product can be seen: Home (the summary), Board and Graph (M10), Roadmap, Table and Outline (M11), Rules and Memory (M12), Search and Overlaps (M13), Activity, Tools and Status (M14).
