# vrum: a self-hosted project graph for AI agents

## 1. Purpose

A small server that an AI agent (and a human through the agent) uses to plan and track work as an **exact hierarchy**: Epic → Story → Task. It adds a **derived semantic index** to find overlaps and related items, and a **memory layer** of decisions and principles that each point to the items they affect.

**Goal: effective, efficient, agent-friendly and human-friendly coding project management.** *Effective:* an agent always knows what to do next, why, and what was already decided, and two agents never collide or redo each other's work. *Efficient:* every answer is small, every common job is one call, and nothing needs asking twice. *Agent-friendly:* a strict structure the database enforces, plain refusals, and handoffs that survive the end of a session. *Human-friendly:* a person can see everything the agents are doing, and steer it, without learning the tool's internals. Section 10 says what Vrum takes from GitHub Projects, Obsidian, Hindsight, Elasticsearch and Taiga to get there, and what it leaves out.

Three layers, with one rule between them: **memory suggests, the graph decides.**

1. **Exact graph (source of truth).** Epics, stories, tasks, rules (requirements), typed links, decisions, history. Everything that must be true is enforced by the database, not by the agent's good behaviour.
2. **Derived semantic index.** An embedding of every epic, story, rule and decision. It can be dropped and rebuilt at any time and never decides anything.
3. **Memory layer.** Decisions and principles, each linked to the items they affect. Recalling them is exact first (by link), similar second (by index).

## 2. Who uses it and how

- **AI agents** connect over **MCP** (Model Context Protocol) to the container. This is the main interface.
- **A human** works through the agent and, from M10 to M13, through the **board** in the browser: a small set of pages (section 10 lists them all) served by the same container, which show every part of the product and let a person do what an agent can do. There is no other web UI. The wider human view of the work may still live elsewhere (for Deelio, a Taiga project), and this tool must be able to export to it later.
- **Self-hosting:** `docker compose up` on one machine. Data lives in a named volume. A backup and a restore are documented and tested.

## 3. Defaults the owner may veto (record each change in DECISIONS.md)

- **Language and framework:** Python 3.12 with the official MCP Python SDK (do not hand-roll the protocol; check its current documentation first), `pytest`, one lint and one type check.
- **Database:** PostgreSQL with `pgvector`, in the same compose file as the app. One database holds the graph and the index tables.
- **MCP transport:** streamable HTTP on a configurable port, bound to localhost by default, with a bearer token read from an environment variable or a secret file. No anonymous access and no default token.
- **Embeddings:** a locally hosted model reached through one small interface and an OpenAI-compatible base URL, configured by `EMBEDDING_BASE_URL` and `EMBEDDING_MODEL`. The compose file offers an optional `local-embeddings` profile that runs a local embedding service. The vector size is read from the model, never hard-coded. No data leaves the machine unless the owner points the base URL elsewhere.
- **Identity of actors:** every write names an actor (a person or an agent name) given by the caller.
- **Board (M10 to M13):** plain HTML, CSS and JavaScript served by the same server and port under `/board`, with no build step and nothing loaded from the internet (the graph is drawn by the board's own code, and Markdown by its own small renderer). People sign in with the same bearer token. Browser tests use Playwright, as a development dependency only, never in the app image.

## 4. Non-goals (do not build)

A web UI other than the board pages in M10 to M13, a roadmap or timeline view (nothing in the model has dates), sprints, story points, velocity and burndown charts, comments threads, notifications, multi-tenant accounts and separate memory banks (one install is one project), billing, a plugin system, summaries, beliefs or plans written by a language model on the server, built-in agent orchestration or spawning, importers other than the one in M8, and any abstraction without a consumer in a milestone below. Section 10 says what was left out on purpose from each product Vrum is measured against.

## 5. The data model (exact; enforced in the database)

- **Node** with a kind: `epic`, `story` or `task`.
    - An epic has no parent. A story has exactly one parent, which is an epic. A task has exactly one parent, which is a story. Any other combination is refused by the database.
    - Fields: id, kind, parent, title, body (plain text or Markdown), status, priority, version (integer for optimistic locking), created and updated times.
    - Status: `new`, `ready`, `in_progress`, `blocked`, `done`, `dropped`. `ready` is computed: a node is ready when it is `new` and every `needs_first` target is `done`.
- **Rule** (a requirement): a stated rule, with a status `held`, `settled` or `dropped`, and **at most one owning story**, enforced by a single column, never a join table. Moving a rule to another story is one atomic operation recorded in history. A rule with no story is "unplaced".
- **Link** between two nodes, with a type:
    - `needs_first` (the source cannot start before the target is done; cycles are refused),
    - `supersedes`, `duplicates`, `relates_to`.
  Links between a node and itself are refused.
- **Decision:** id, date, title, text, reason, decided_by (a named person), status `active` or `superseded`, and a `kind` of `decision` or `principle`. A decision links to zero or more nodes and rules, and may supersede another decision.
- **Claim:** at most one actor holds a claim on a task or story at a time, with a lease that expires. Claiming is atomic.
- **Event log:** every create, update, move, link, claim and decision is appended with actor, time and before-and-after. Nothing is overwritten silently. Updates that carry an old `version` are refused with a clear message.

## 6. The MCP tools (plain names, plain descriptions an agent can read)

Create, get, list, update and move nodes; add and remove links; ready work; claim, renew and release; place and move rules; coverage report (unplaced rules, stories without rules); record, supersede and recall decisions; search; find overlaps; reindex; export and import; history of one node. From M5, search matches by exact words, by meaning or both, and says how each result matched. From M5B, agents also get: the next work with its context in one call, finishing work with a handoff note, a whole plan created at once, several nodes updated at once, what changed since a given event, and a check for similar existing items. From M10, search and find overlaps also say how many items are waiting to be indexed. From M12, `find_mentions` lists the items whose text refers to a given item. Every tool returns clear, plain-English refusals that say what was wrong and what to do next, and every list is paged.

## 7. Milestones

Each milestone ends in working behaviour reachable through MCP in the running containers. Tick them in order.

- **M0. Bootstrap.** Repository, SPEC.md, PROGRESS.md, AGENTS.md, DECISIONS.md, one check command (`./check.sh` or equivalent: lint, types, unit and integration tests), and a compose file where the database and the app start and a health check passes.
  *Proof:* from a clean clone, `docker compose up -d` becomes healthy, and an MCP client lists the tools.
- **M1. Graph core.** Schema, constraints, node create, get, list, update and move, optimistic versioning, event log.
  *Proof:* through MCP, a story without an epic, a task under an epic, a second parent and a stale version are each refused with a plain message; a valid epic, story and task are created and their history is readable.
- **M2. Links, readiness and claims.** Link types, cycle refusal, computed readiness, atomic claims with leases.
  *Proof:* a cycle is refused; finishing a prerequisite makes its dependent ready; ten parallel claimers on one ready task produce exactly one winner; an expired lease can be claimed by another actor.
- **M3. Rules and coverage.** Rules placed in exactly one story, atomic moves, the coverage report.
  *Proof:* a rule cannot be placed in two stories; a move is atomic and logged; the coverage report lists unplaced rules and stories with none.
- **M4. Decisions and principles.** Record, link, supersede and exact recall by node, plus the list of active principles.
  *Proof:* recalling a story returns its linked active decisions and all active principles; a superseded decision is shown as such and not as active; nothing is invented.
- **M5. Search and the semantic index.** Embedding client, reindex job, and `search` that matches three ways: by exact words (PostgreSQL full-text search over the graph itself, so it is current the moment a change is saved and still works when the embedding service is down), by meaning (the index), or both fused by rank. Each result says how it matched (words, meaning or both), why (the words that matched, or the similarity score), its current parent and status from the graph, and a highlighted snippet; the answer also carries counts by item type and status. Overlap finder (nearest neighbours across epics above a configurable threshold, with scores, never merging or changing anything), similar-decision recall, and "similar items" for an item or a piece of text. Queries never fail on odd characters. Meaning results are suggestions, labelled as such.
  *Proof:* on a fixture of known duplicate and known unrelated pairs, the overlap finder flags the duplicates and not the unrelated pairs, and the measured counts are printed; dropping the index tables and running reindex gives the same results; no tool other than reindex writes to the index. With the embedding service stopped, a phrase added to a story is found by words at once and labelled as an exact-words match, while a paraphrase of it is found by meaning only after the service returns and reindex has run. Results that match both ways are labelled both. The counts by item type equal what the list tools return.
- **M5B. Agent workflow.** What an agent needs to do a day's work in few calls and small answers, built on the earlier milestones. It is numbered M5B so that no other milestone is renumbered, and it comes right after M5 in order.
    - **Next work, with its context, in one call.** `next_work` picks the most urgent ready story or task that nobody holds (highest priority first, then oldest), claims it atomically, marks it in progress, and returns it together with what an agent needs to start: its parent chain, the rules of its story, the active decisions linked to it and to its parents, every active principle, the handoff notes left by earlier holders, what finishing it will unblock, and similar existing items. A peek option returns the same without claiming. Everything in the context comes by exact link; similar items are labelled as suggestions. If the context is large it is cut to a stated size and says what was left out.
    - **Handoff notes.** Ending work is one call, `finish_work`: the holder says whether the item is done, blocked, dropped or only released, and writes a handoff note (what was done, what the next person must know). A blank note is refused. `release_claim` needs a note too. The note is kept in the item's history and comes back with `get_node` and `next_work`; a claim that lapsed shows as lapsed with no handoff.
    - **A whole plan at once.** `create_plan` creates epics, stories, tasks, links between them and rules in one all-or-nothing call, from items given with temporary keys, up to 200 items. One bad item refuses the whole plan, and the message names that item and what is wrong. A plan that would make a circle of waiting is refused whole.
    - **Several changes at once.** `update_nodes` changes up to 50 nodes, each with its own expected version, and reports each one separately: one stale version does not undo the others.
    - **What changed.** `changes_since` lists events after a given event id across the whole graph, filtered by actor or item, a page at a time, with the latest event id. An agent that comes back after a break, and the board, see only what is new.
    - **Small answers.** Lists leave out bodies by default and say so; a detail option asks for them. Every tool that can return a lot has a stated limit and says how much it left out.
    - **Check before creating.** `create_node` and `create_plan` answer with similar existing items (from the index, labelled as suggestions) and still create. If the embedding service cannot be reached they say so and still create.
    - **Server instructions.** The MCP server's own instructions tell any agent the working loop in a few lines: recall decisions, take work with `next_work`, record decisions as they are made, end with `finish_work`. They name only tools that exist, and a test compares them with the live tool list.
  *Proof* (a real MCP client against the real containers):
    1. Ten agents call `next_work` at once on five ready tasks: five each get a different task, none gets a task twice, and the rest are told plainly that nothing is free. Each context holds exactly the parent chain, the rules of the story, the linked active decisions (a superseded one only in its own section), all active principles and any earlier handoff notes.
    2. `finish_work` with a blank note is refused and changes nothing. With a note the item is done, its dependent becomes ready, and the next agent's `next_work` shows the note. A claim that lapsed shows as lapsed with no handoff.
    3. `create_plan` creates one epic, three stories, eight tasks, five links and four rules in one call. A plan with one invalid item, or with a circle, creates nothing and names the problem.
    4. `update_nodes` with five changes, one of them stale: four apply, one is refused with the stale-version message, and each is in the history with its actor.
    5. `changes_since` returns exactly the events made after a given id, nothing before and nothing missing, and pages correctly.
    6. A list of 50 items with long bodies is at least five times smaller by default than with the detail option; both sizes are printed.
    7. Creating a story whose title repeats an existing one returns the existing one as similar, and still creates it; with the embedding service stopped it says so and still creates.
    8. The server instructions are shown by the client and name only tools that exist. All earlier proofs still pass.
- **M6. Hardening.** Bearer-token auth, no default token, localhost binding, paging everywhere, limits, input size caps, plain refusals, structured logs without secrets. Text that contains a well-known secret format (access tokens with known prefixes, private key blocks) is refused on write with a plain message, so a pasted secret is never stored; only such well-known formats are checked, to avoid refusing ordinary text.
  *Proof:* a call without or with a wrong token is refused; the logs contain no token; an oversized request is refused with a plain message; a body containing a token in a well-known format is refused, nothing is stored, and the refusal does not repeat the token.
- **M7. Export, import, backup, restore.** Full export and import (JSON), a read-only Markdown export (one file per epic, story, task, rule and decision, with its fields at the top and its links written as `[[file name]]` references, so a person can read it in Obsidian or keep it in git), a backup script and a restore script.
  *Proof:* backup, destroy the volume, restore into a fresh container, and the exported graph is identical to the one taken before. In the Markdown export of a fixture there is one file per item, and every link, rule placement and decision link in the graph appears as a reference whose target file exists.
- **M8. Real-data trial (only if `{{LEDGER_PATH}}` is given).** A one-off importer for the Deelio ledger (epics, rules and their story placement; decisions from `{{DECISIONS_PATH}}` if given). Read-only on the sources. Then run coverage and the overlap finder.
  *Proof:* counts after import equal counts in the source (printed); a report of the top overlap candidates is written for the owner to review; nothing is written to Taiga or to any Deelio file.
- **M9. Docs and acceptance.** README (Docker quick start, how to configure the token, example MCP client configuration, an agent guide that is the same text as the server's instructions, backup and restore) and `./acceptance.sh`, which starts from a clean clone and, through a real MCP client, runs one scenario covering every proof above.
  *Proof:* the acceptance script passes from a clean clone.
- **M10. Board for humans: Kanban and graph.** A Kanban board and a graph view at `/board` on the same server and port, so a person can see what the agents are doing and refine the plan alongside them. They read and write the same graph as the MCP tools and keep no data of their own. M11 to M13 add the other pages (section 10).
    - **What a person sees.** One column per status (new, ready, in progress, blocked, done, dropped), with one lane per epic and a filter by epic. Each card shows kind, title, priority, who holds the claim and until when, and which unfinished prerequisite blocks it. Opening a card shows its body, parent, links, linked rules, linked active decisions and principles, overlap candidates (read-only suggestions from the index) and its history. A read-only panel shows the coverage report (unplaced rules, stories without rules). Epic lanes and story cards show progress (tasks done out of tasks not dropped), and `get_node` and `list_nodes` report the same counts.
    - **What a person can do.** Create an epic, a story (choosing its epic) or a task (choosing its story). Edit title, body and priority. Change status by dragging a card, with a menu as the keyboard alternative. Move a story to another epic or a task to another story. Add and remove links. Rules and decisions stay read-only on the board in M10 and are still edited through an agent; M11 makes them editable.
    - **No logic of its own.** Every board action calls the same owner-module operation as the matching MCP tool, so the same constraints, version checks, claims and event log apply, and a refusal reads the same on the board as through MCP. `ready` is computed, so nothing can be dropped into that column, and the board says so plainly.
    - **Pages and addresses.** A top bar lists the pages that exist (section 10 lists all of them: Home, Board, Graph, Table, Outline, Rules, Memory, Search, Overlaps, Activity, Tools, Status). Every page has its own address, and the filters and layout a person chose live in the address after the `#` (never the token), so a view is shared by copying the link and the server stores no views. Everything on every page can be done from the keyboard, and colour never carries meaning alone: status, kind and link type also have a label or a shape.
    - **Graph view** (the local graph and filters of Obsidian, on Vrum's typed links). The same work drawn as a graph: dots for epics, stories and tasks and, switched on from a menu, rules and decisions; lines for the hierarchy and for each link type, told apart by line style and a label. It opens on one epic (or on everything when there are fewer than 300 items) and says plainly when it is showing only part of the graph and why. Choosing a dot opens the same card as on the board. A local graph shows only the items within 1 to 3 steps of the chosen one. People can colour by kind, status or epic, drag and pin dots, zoom and pan, and filter by kind, status and link type. A list of the chosen item's neighbours beside the drawing does everything a click on it does, for keyboard and screen-reader use. Overlap candidates can be shown as dashed "might be the same as" lines, labelled as suggestions from the index with their scores; nothing is saved from them and drawing them never changes a link. The graph reads the same data as the board, updates from the same events, and is drawn by the board's own code with no library fetched from the internet.
    - **Named actors.** The person types their name on first use (kept in the browser). Every write carries it, and a blank name is refused.
    - **Conflicts.** An edit carries the version the person saw. If an agent changed the item meanwhile, the edit is refused with the plain stale-version message, the typed text stays in the form, and the card offers to load the current version.
    - **Agents show up on the board.** The board asks for new events every few seconds (default 5), through the same `changes_since` operation agents use, and updates the affected cards without a reload. It never overwrites a form someone is typing in.
    - **The index follows the graph.** The board never writes to the semantic index. Any change to the title or body of an epic, story, rule or decision, by a person or an agent, marks that item as waiting to be indexed. The reindex job, still the only writer to the index, picks it up right after the save, and again later if the embedding service cannot be reached. A failed embedding never fails or delays the edit, because the graph is the source of truth. The board, `search` and `find overlaps` all say how many items are waiting. Moves and status changes need no new embedding, but search and overlap results must show the current parent and status from the graph, never a stale copy.
    - **Sign-in and safety.** The same bearer token as MCP (M6), typed once per browser session and sent in the Authorization header. It is never put in the address, a cookie or a log, and there are no accounts. The page files hold no data, and the data calls under `/board/api` refuse any request without a valid token. All text is shown escaped as plain text (Markdown is not rendered until M12), the page carries a strict content security policy (own origin only), and it works with no internet.
  *Proof* (a real headless browser and a real MCP client, against the real containers):
    1. A wrong or empty token is refused with a plain message, and the data calls refuse requests without a valid token. With the right token the board loads.
    2. Through MCP, create an epic, a story, a task, a `needs_first` link and a claim. Without reloading the page, and within 10 seconds, the board shows them in the right lane and column, with the claim holder and the blocking prerequisite.
    3. In the browser, create an epic, a story and a task, edit title, body and priority, drag a task to in progress and then to done, move a task to another story, and add and remove a link. Through MCP, `get`, `list` and the history then show exactly that, with the typed actor name, the right before-and-after and the right version numbers.
    4. These are each refused on the board with the same plain message the MCP tool gives for the same attempt, leave the graph unchanged and keep the typed text: dropping a card on `ready`, a link that makes a cycle, an edit from a stale version, and a blank actor name.
    5. Edit a story on the board to contain a phrase that appears nowhere else. MCP `search` finds that story by the phrase, and the waiting count reaches zero, with no manual reindex. Stop the embedding service and edit again: the edit still saves, the board and `search` both report one item waiting, and after the service returns the count reaches zero and the item is found. The M5 proof that no tool other than reindex writes to the index still passes, and its test now also covers the board's endpoints.
    6. A title containing HTML and script markup is shown as literal text and nothing runs. Every request the browser makes goes to the server's own address, and the content security policy header is present.
    7. Through MCP, create an epic with two stories and three tasks, a `needs_first` link, a `relates_to` link, a rule, and a decision linked to a story. The graph shows each of them, with the right kind of line between the right dots, and shows rules and decisions only once they are switched on. A `needs_first` link then made through MCP appears within 10 seconds without a reload, and a story moved to another epic on the board changes its hierarchy line in the graph.
    8. Choosing a dot opens the same card as on the board. The local graph at one step shows exactly the item's neighbours and no others, and the neighbour list offers the same choices as a click. The whole graph can be reached and chosen from the keyboard. Overlap candidates appear only when switched on, are dashed and labelled as suggestions, and `list_links` through MCP is unchanged afterwards.
    9. All earlier proofs still pass. The README has a "Board" section (the address, signing in, what a person can and cannot do), `./acceptance.sh` gains a board scenario in the real headless browser, and the layout in `AGENTS.md` lists the board module. Each of M11 to M13 does the same for its own pages.
- **M11. More views of the work, with rules and decisions.** The pages for looking at the same work in other ways, and for rules and decisions, which become editable on the board. The rules of M10 apply: the same operations as the MCP tools, no data of its own, keyboard use, and refusals that read the same as through MCP.
    - **Table** (as in GitHub Projects). One row per epic, story or task, with columns for kind, title, parent, status, priority, claim holder, waiting on, progress and last change. Sort, group by (epic, story, status, priority, claim holder) and filter. Rows can be edited in place, and several rows can be changed at once through `update_nodes`: each row is its own versioned change, and the result says which changed and which were refused, and why.
    - **One filter language** for people and agents: words and `field:value` terms, commas for "any of these values", `OR` between groups, a leading `-` to leave something out, and `no:field` for empty, as in `kind:task status:ready,in_progress -claimed priority:high OR kind:story`. The table's filter box and the MCP `list_nodes` (as `query`) take the same text and give the same answer, and a bad query is refused with a plain message saying what was not understood.
    - **Outline** (as the file tree of Obsidian). A collapsible tree of epics, stories and tasks, with the rules shown under their story and progress on every branch. A story or task can be dragged to a new parent, or moved with a menu.
    - **Rules.** All rules grouped by story, with the unplaced ones first and the full coverage report (unplaced rules, stories without rules, dropped ones left out). A person can create, edit and change the status of a rule, and place or move it by dragging it onto a story or with a menu. Placing a rule that is already placed is refused with the MCP message.
    - **Memory.** Decisions and principles, newest first with the principles pinned, filterable by kind, status, who decided, date and the item they are linked to. A person can record a decision with the items it affects, link and unlink it, and supersede it (the form starts from the old text and records a new decision). A superseded decision is shown as such, with what replaced it as a chain. A recall preview takes a node or a rule and shows exactly what `recall_decisions` returns for it, so a person sees what an agent would be told.
  *Proof* (a real headless browser and a real MCP client, against the real containers):
    1. Through MCP, create twelve items. In the Table, sort, group and filter them: the rows and groups equal what `list_nodes` returns for the same query, and the same `query` text through MCP gives the same ids. A bad query is refused in plain words.
    2. Select three rows and set their priority and status. One of them was changed by an agent in the meantime: that row is refused with the stale-version message, the other two change, and the history shows each with the typed actor.
    3. The Outline shows the same tree as `list_nodes`. Dragging a task to another story matches `get` and the history through MCP, and the branch counts follow.
    4. On the Rules page, create an unplaced rule: it is first in the list and in the coverage report. Place it, and it leaves both. Placing it in a second story is refused with the MCP message. Moving it by drag is atomic and appears in the histories of the rule and of both stories.
    5. On the Memory page, record a decision with two links, then supersede it. The page shows the chain with the old one marked superseded, and the recall preview for the linked story equals the output of `recall_decisions` through MCP (same ids, same sections). A blank reason is refused with the MCP message.
    6. A view's address opened in a second browser profile after signing in reproduces the same filter and sort, and the server has stored nothing for it.
    7. All earlier proofs still pass, and the README, `./acceptance.sh` and `AGENTS.md` cover these pages.
- **M12. Find and connect.** Search, overlaps, Markdown, references between items, backlinks and a quick switcher, so that everything written down can be found and followed.
    - **Search page** (the recall of Hindsight and the search of Elasticsearch, inside PostgreSQL). One box over the `search` of M5: each result shows how it matched (words, meaning or both), why, a highlighted snippet and its current parent and status from the graph. Counts by item type (epic, story, task, rule, decision, principle), status and epic filter the results. The page says how many items are waiting to be indexed, so a person knows meaning results may lag while words results never do.
    - **Overlaps page.** The overlap candidates of M5 across epics with their scores, a threshold the person can change, and the two items side by side. Each pair can be marked `duplicates` or `relates_to` with one click (the same `add_link`). Nothing is linked unless a person clicks.
    - **Markdown.** Bodies, rules, reasons and decision texts are shown as Markdown by the board's own small renderer: headings, paragraphs, lists, emphasis, code, quotes, and links to web addresses that open in a new tab. Raw HTML is never rendered and nothing is loaded from elsewhere, so a script or image tag is shown as text.
    - **References and backlinks** (as in Obsidian). Writing `[[node:12]]`, `[[rule:3]]` or `[[decision:7]]` in any text makes a link to that item, shown with its current title, and the editor offers a pick-list as the person types. An id that does not exist is shown plainly as missing. A reference is only text: it creates no link, changes no readiness and no order. Every item shows "Mentioned in", the items whose text refers to it, from `find_mentions`, which the server works out when asked and stores nowhere. The graph gets a "mentions" layer for them.
    - **Quick switcher.** One key combination on every page opens a box that jumps to an item by a word of its title or by its id, and to any page.
  *Proof* (a real headless browser and a real MCP client, against the real containers):
    1. With the embedding service stopped, add a phrase to a story on the board. The Search page finds it by words at once, labelled as an exact-words match, and shows one item waiting to be indexed. After the service returns and the count reaches zero, a paraphrase is found by meaning. The page's results equal MCP `search` for the same query: same ids, same order, same labels.
    2. The counts by item type and status equal what the list tools return.
    3. The Overlaps page lists the M5 fixture's known duplicates and not the unrelated pairs, with the same scores as MCP. Marking a pair as duplicates creates exactly one `duplicates` link, visible through `list_links`, and nothing is created without a click.
    4. A body with a heading, a list, code, a script tag and an image tag from another address shows the structure, shows the script and image tags as literal text, and the browser makes no request to any other address.
    5. `[[node:12]]` shows as a link with the item's title, and follows a rename. A missing id shows as missing. `list_links` is unchanged by references. "Mentioned in" equals `find_mentions` through MCP.
    6. The quick switcher opens from the keyboard on every page and jumps to an item by a word of its title and by its id.
    7. All earlier proofs still pass, and the README, `./acceptance.sh` and `AGENTS.md` cover these pages.
- **M13. Run and see it all.** The pages that show the whole product at a glance, what the agents are doing, how to use the tools, and the health of the server.
    - **Home.** The first page after signing in. What needs attention: counts by status for each epic (plain numbers and bars, no burndown), ready work that nobody holds, blocked items, claims that lapsed with no handoff, stories without rules and rules without stories, decisions recorded this week, overlap candidates waiting for a look, items waiting to be indexed, and the health of the server. Each number is a link to the page that shows those items.
    - **Activity.** A live feed of everything that happens, newest first, in plain words ("ann moved rule 4 from story 12 to story 15"), through `changes_since`, filterable by actor, kind of change, item and time. Handoff notes are shown in full. Beside it, "Who is working on what": every current claim with its holder and a countdown to its lease, the state of each agent (working, lapsed, finished with handoff), and buttons to claim, renew or release with the person's typed name, using the same operations.
    - **Tools.** The reference of every MCP tool, generated from the server's own live tool list (name, description, input fields with their types and descriptions, and whether the tool changes anything), grouped by area and searchable, so it can never drift from the code. Each tool says where on the board a person can do the same thing, or that it is for agents only and why (`reindex` and import are). The tools that only read have a "try it" form built from their input description, which shows what the tool returns. The page also shows the endpoint address, how to give the token, and an example client configuration. A test compares the live tool list with the page's map and fails if any tool is neither mapped to the board nor marked agent-only.
    - **Status.** `server_status`, the versions, the size of each kind of item, the state of the index (items indexed, items waiting, the last reindex and its result, whether the embedding service answers, its model and vector size), and a download of the full export. Import and backup stay with the command line and the README, and the page says so. It never shows the token, the database password or any other secret.
  *Proof* (a real headless browser and a real MCP client, against the real containers):
    1. Every number on Home equals what MCP gives for the same question (`list_nodes` with filters, `ready_work`, `coverage_report`, the index state), and following a number lands on the page showing exactly those items.
    2. Through MCP an agent takes work with `next_work`, edits a rule, records a decision and finishes with a handoff note. Within 10 seconds Activity shows each in plain words with the actor, the handoff note in full, and the claim in "Who is working on what". In the browser, a person claims another task with a typed name, and a claim that lapses moves to lapsed.
    3. The Tools page lists exactly the tools the server lists (same count, same names), each with its description and fields, each mapped or marked agent-only. "Try it" on `list_nodes` returns what MCP returns, and no tool that changes anything has one. The classification test fails when one tool is removed from the map (shown once, then restored).
    4. Status equals `server_status` and the index state through MCP, and the downloaded export is identical to the MCP export. The token and the database password appear nowhere in any page or data call of the board (searched for in every response).
    5. All earlier proofs still pass, and the README, `./acceptance.sh` and `AGENTS.md` cover these pages.

## 8. Quality bar

- Tests prove behaviour through MCP against real containers. Do not test your own mocks.
- Each milestone keeps all earlier proofs passing.
- Never commit a secret. Configuration comes from the environment.
- Keep to one owner module per concept; reuse it rather than copying.
- Plain English in every message a person or agent reads.
- Answers are small by default, because an agent's context is expensive: lists leave out long text, and any tool that can return a lot has a limit and says how much it left out.
- Every page of the board works from the keyboard and never uses colour alone. Each of M10 to M13 adds its pages to the README and its scenario to `./acceptance.sh`.
- No part of the product is without a page: a part a person cannot see on the board is a gap, and is listed in `PROGRESS.md` until it has one.

## 9. What the loop must never do

Touch any Deelio repository or the Taiga project, send data to a third party without the owner setting the base URL, invent a product answer, bulk-generate sample data that looks real, or tick a milestone whose proof has not passed.

## 10. Product shape: what Vrum takes from the tools it is measured against

Vrum is one product with two ways in that always call the same operations: MCP for agents, the board for people. It combines the best parts of five products, and this section says which, and what is left out on purpose, so that a missing feature is a decision and not an accident. The sources are each product's own documentation.

| Product | What Vrum takes | Where | Left out on purpose, and where Vrum is better |
|---|---|---|---|
| **GitHub Projects** (docs.github.com/en/issues/planning-and-tracking-with-projects) | Several views of the same items (board, table); drag a card to change its value; filter, group and sort; shareable views; batch edits; progress roll-ups; keyboard use | M10, M11 | No roadmap or iterations (the model has no dates or sprints), no burn-up charts, no items tied to a repository. Better: a real dependency graph with cycle refusal and a computed "ready" (GitHub stores blocked-by as plain metadata), filters that can OR across fields, and one filter language for agents and people. |
| **Obsidian** (obsidian.md/help) | Local graph with depth; backlinks; `[[references]]`; Markdown; quick switcher; a Markdown export people can open in Obsidian | M7, M10, M12 | No global graph as the main way to navigate (it does not scale), no files as the source of truth (no atomic writes or locks), no Canvas, no plugins. Better: enforced structure, computed state, versioned edits and claims. |
| **Hindsight** (hindsight.vectorize.io) | Recall that combines exact links, words, meaning and time, saying why each result came back; answers cut to a stated size; two dates (when decided, when recorded); a short start-of-work briefing from exact data; old items marked stale when superseded | M4, M5, M5B, M11 | No facts extracted by a language model, no beliefs or "reflect" written by one, no automatic transcript capture, no fuzzy merging of entities, no overwriting on re-save, no open MCP by default. Better: every memory has a named author, a reason and exact links, and a change supersedes instead of rewriting. |
| **Elasticsearch** (elastic.co/docs) | Exact-words and meaning results fused by rank and labelled; counts by category; highlighted snippets; why a result matched; similar items; queries that cannot fail | M5, M12 | Not Elasticsearch itself (a second heavy datastore to keep in sync), no custom analyzers or relevance tuning, no query language for agents. All of it is done inside PostgreSQL. |
| **Taiga and its MCP servers** (docs.taiga.io and the community MCP servers) | Epics, stories, tasks; bulk creation; filters; history; versioned edits; export | M1 to M7, M5B | No sprints, comments, attachments, roles, issues as a separate kind, wiki pages, votes or watchers. Better: `needs_first` links, computed ready, atomic claims with leases, versions an agent must send back (several Taiga servers fetch the version themselves, which defeats the check), one call for the next work, search by meaning, and rules and decisions as first-class memory. |
| **Agent task tools** (Beads, Claude Code task lists, Linear, Task Master, Backlog.md, the Copilot cloud agent) | Ready-work lists, atomic claims, handoff notes, whole plans created at once, the state of each agent visible to people | M2, M5B, M13 | No agent orchestration or spawning, no plans written by a language model on the server, no heavy locks, no story points. |

**What matters most for effective, efficient, agent- and human-friendly work, in order** (from the research on agents and project management): 1. one call for the next work with its context; 2. ready work that respects dependencies and refuses circles; 3. expiring claims and versions instead of locks; 4. handoff notes that outlive a session; 5. small answers, paging and few consolidated tools; 6. a whole plan created at once; 7. decisions and principles brought to the agent with their reasons; 8. what the agents are doing visible to people, with conflicts and stale claims; 9. finding earlier work before duplicating it; 10. seeing what changed since last time.

**The pages**, so that every part of the product can be seen: Home (the summary), Board and Graph (M10), Table, Outline, Rules and Memory (M11), Search and Overlaps (M12), Activity, Tools and Status (M13).
