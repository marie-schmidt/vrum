# vrum: a self-hosted project graph for AI agents

**Final contract (M16):** this file describes the product as M16 leaves it. M16 replaced server-side language-model generation, the expanded memory taxonomy (beliefs, principles, world and experience facts) and the many-page navigation with the two context records (facts and decisions) and three views (Board, Graph, Roadmap). Milestones M0 to M15 keep their numbers, titles and order as the history of how the product was built; where M16 replaced what a milestone built, its text says what Vrum does now, and a proof that no longer applies is marked "Replaced by M16". Epic → Story → Task, optional embeddings, shared board/MCP operations and project isolation are unchanged.

**Approved frontend redesign (M17):** after M16, apply the owner's approved visual direction throughout the frontend, with equally designed light and dark modes. The refined reference screenshots and the implementation/proof contract are in M17 below. This is a planned milestone, not permission to skip earlier milestones.

## 1. Purpose

A small server that an AI agent (and a human through the agent) uses to plan and track work as an **exact hierarchy**: Epic → Story → Task. It adds a **derived semantic index** to find overlaps and related items, and a **context layer** of decisions and facts that each point to the items they affect.

**Goal: effective, efficient, agent-friendly and human-friendly coding project management.** *Effective:* an agent always knows what to do next, why, and what was already decided, and two agents never collide or redo each other's work. *Efficient:* every answer is small, every common job is one call, and nothing needs asking twice. *Agent-friendly:* a strict structure the database enforces, plain refusals, and handoffs that survive the end of a session. *Human-friendly:* a person can see everything the agents are doing, and steer it, without learning the tool's internals. Section 10 says what Vrum takes from GitHub Projects, Obsidian, Hindsight, Elasticsearch and Taiga to get there, and what it leaves out.

Three layers, with one rule between them: **context informs, the graph decides.**

1. **Exact graph (source of truth).** Epics, stories, tasks, rules (requirements), typed links, history. Everything that must be true is enforced by the database, not by the agent's good behaviour.
2. **Derived semantic index.** An embedding of every epic, story, rule, decision and fact. It can be dropped and rebuilt at any time and never decides anything.
3. **Context layer.** Decisions (what people decided, with their reasons) and facts (what is known, each saying where it came from). Both are linked to the items they concern, and a decision that applies throughout its project is marked project-wide. Recalling them is exact first (by link), similar second (by index). A decision is authoritative because a named person made it. A fact says where it came from. Each is either **unconfirmed** or **confirmed** by a named person who reviewed it, which says that someone looked at it, never that Vrum proved it true, and each is either in force or superseded or withdrawn. Vrum stores, retrieves, coordinates and enforces; it never generates answers or conclusions. The coding agents connected to it do the reasoning and record what they find through ordinary, validated writes.

## 2. Who uses it and how

- **AI agents** connect over **MCP** (Model Context Protocol) to the container. This is the main interface.
- **A human** works through the agent and, from M10, through the **board** in the browser, served by the same container. From M16 the board has three views of the same work (Board, Graph and Roadmap), a search drawer (with possible duplicates), an activity drawer and a settings menu (agent access, the tool reference, status and export); section 10 lists them. They show every part of the product and let a person do what an agent can do. There is no other web UI. The wider human view of the work may still live elsewhere (for Deelio, a Taiga project), and this tool must be able to export to it later.
- **Self-hosting:** `docker compose up` on one machine. Data lives in a named volume. A backup and a restore are documented and tested.
- **Accounts and projects (M15):** a person creates an account with email and password managed by Vrum, then creates a private project. One account may own several projects, and one install may hold several accounts. Each project's graph and context belong only to that project; only its owner and agents authorised for it may reach them.

## 3. Defaults the owner may veto (record each change in DECISIONS.md)

- **Language and framework:** Python 3.12 with the official MCP Python SDK (do not hand-roll the protocol; check its current documentation first), `pytest`, one lint and one type check.
- **Database:** PostgreSQL with `pgvector`, in the same compose file as the app. One database holds the graph and the index tables.
- **MCP transport:** streamable HTTP on a configurable port, bound to localhost by default, with a bearer token read from an environment variable or a secret file through M14. M15 replaces the install-wide credential with project-scoped agent access. No anonymous data access and no default token.
- **Embeddings:** a locally hosted model reached through one small interface and an OpenAI-compatible base URL, configured by `EMBEDDING_BASE_URL` and `EMBEDDING_MODEL`. The compose file offers an optional `local-embeddings` profile that runs a local embedding service (Ollama with the small model `all-minilm`, which is multi-architecture and so runs on Apple silicon too). The vector size is read from the model, never hard-coded. No data leaves the machine unless the owner points the base URL elsewhere.
- **No language model (M16):** Vrum has no language-model client, no setting for one and no generation tool. The coding agents connected to it do the reasoning. The optional embedding service above only turns text into numbers, so that records can be compared. No data leaves the machine unless the owner points the embedding base URL elsewhere, and text containing a well-known secret format is refused on every write.
- **Identity of actors:** every write names an actor (a person or an agent name) given by the caller.
- **Board (M10 to M16):** plain HTML, CSS and JavaScript served by the same server and port under `/board`, with no build step and nothing loaded from the internet (the graph is drawn by the board's own code, and Markdown by its own small renderer). People sign in with the same bearer token through M14; M15 replaces that screen with account registration and email/password sign-in, followed by creating or choosing a private project. M16 leaves three views (Board, Graph, Roadmap). Browser tests use Playwright, as a development dependency only, never in the app image.

## 4. Non-goals (do not build)

A web UI other than the board and account/project pages in M10 to M16, sprints and iterations, story points, velocity and burndown charts, comments threads, notifications, shared projects, invitations and member roles, external identity providers, billing, a plugin system, any generation by the server (plans, answers or conclusions written by a language model, standing answers or pages that a model rewrites on a schedule), built-in agent orchestration or spawning, importers other than the one in M8, and any abstraction without a consumer in a milestone below. Accounts and separate project graphs and context are required by M15, not non-goals. Section 10 says what was left out on purpose from each product Vrum is measured against.

## 5. The data model (exact; enforced in the database)

- **Account and project (M15):** an account has a unique email and a securely hashed password; a project has an id, a name and exactly one owning account. Every graph record, context record, claim and event belongs to one project. Parentage, links, evidence and supersession cannot connect records in different projects, enforced by the database. Account credentials and sessions are never graph content or part of a project export.
- **Node** with a kind: `epic`, `story` or `task`.
    - An epic has no parent. A story has exactly one parent, which is an epic. A task has exactly one parent, which is a story. Any other combination is refused by the database.
    - Fields: id, kind, parent, title, body (plain text or Markdown), status, priority, start date and target date (both optional, from M1A), version (integer for optimistic locking), created and updated times.
    - Dates: a start date and a target date, which are plain dates with no time. When both are set the start is not after the target, which the database enforces. They are what the roadmap draws. An epic or story with no dates of its own shows the span of its children's dates, marked as worked out. A node is overdue when its target date has passed and it is not done or dropped. A node whose own start date is before the target date of something it needs first is shown with a schedule conflict: that is a warning, never a refusal.
    - Status: `new`, `ready`, `in_progress`, `blocked`, `done`, `dropped`. `ready` is computed: a node is ready when it is `new` and every `needs_first` target is `done`.
- **Rule** (a requirement; the board and the documentation call it a **Requirement**, while the database, the tools and `[[rule:3]]` references keep the name `rule`): a stated rule, with a status `held`, `settled` or `dropped`, and **at most one owning story**, enforced by a single column, never a join table. Moving a rule to another story is one atomic operation recorded in history. A rule with no story is "unplaced".
- **Link** between two nodes, with a type:
    - `needs_first` (the source cannot start before the target is done; cycles are refused),
    - `supersedes`, `duplicates`, `relates_to`.
  Links between a node and itself are refused.
- **Decision** (a context record, from M4): id, title, text, reason (never blank), decided_by (a named person), the day it was decided, `project_wide` (true when it applies throughout its project; it is the same kind of record, not another type), status `active`, `superseded` (replaced by a newer decision) or `withdrawn` (given up, with a reason), who recorded it and when, and its confirmation (below). A decision links to zero or more nodes and rules. A decision is never edited: a change of mind is a newer decision that supersedes it, or a withdrawal, and the old one stays as a record.
- **Fact** (a context record, from M4A): a statement about the project, its tools or its domain, with where it came from. Fields: id, text, source (plain words saying where it came from, never blank), who recorded it and when, status `active`, `superseded` (replaced by a newer fact) or `withdrawn` (found wrong or no longer wanted), a reason once it is no longer active, and its confirmation (below). There is no world/experience split and no date for when it was true; whoever records a fact is named, and nothing says a model wrote it. A fact links to zero or more nodes, rules and decisions. A fact is never edited: it is superseded or withdrawn.
- **Confirmation** (M16; a field of a fact or a decision, not a record of its own): `unconfirmed` (the start, and what recording always gives) or `confirmed`, with the named person who reviewed it and when. It says that someone looked at the record, not that Vrum proved it true, and recording a statement never confirms it, so an agent cannot confirm its own writing. Only an active record's confirmation changes; what a record was confirmed as stays on it, visibly, after it is superseded or withdrawn. Each change is attributed and logged, and changing a confirmed record (replacing it, withdrawing it, taking its confirmation away) needs a person's word. There is no belief, no evidence, no staleness and no promotion: the server infers no conclusion.
- **Claim:** at most one actor holds a claim on a task or story at a time, with a lease that expires. Claiming is atomic.
- **Event log:** every create, update, move, link, claim, decision, fact and change of confirmation is appended with actor, time and before-and-after. Nothing is overwritten silently. Updates that carry an old `version` are refused with a clear message.

## 6. The MCP tools (plain names, plain descriptions an agent can read)

Create, get, list, update and move nodes (with their dates); add and remove links; ready work; claim, renew and release; place and move rules (requirements); coverage report (unplaced rules, stories without rules); record, link, supersede, withdraw and recall decisions (project-wide ones included) and facts, and confirm or un-confirm either (`set_confirmation`); search; find overlaps; reindex; export and import; history of one node, rule, decision or fact. There are 53 tools in all, and the board's Tools page lists them from the server itself. From M5, search matches by exact words, by meaning or both, and says how each result matched; agents can ask for items similar to an item or a text, for pairs of stories that overlap across epics, and for the index to be brought up to date. From M5B, agents also get: the next work with its context in one call, finishing work with a handoff note, a whole plan created at once, several nodes updated at once, what changed since a given event, and a check for similar existing items. From M7, agents can read the whole graph out a page at a time, and load such a file into an empty server. Search, similar items and find overlaps say how many items are waiting to be indexed (from M5, which M10 shows on its pages). From M13, `find_mentions` lists the items whose text refers to a given item. There are no tools that generate text (M16 removed `extract_facts`, `consolidate_memory`, `find_contradictions` and `reflect` with the language model they needed): the agent reasons, and records what it finds with `retain_fact` and `record_decision`. Every tool returns clear, plain-English refusals that say what was wrong and what to do next, and every list is paged.

## 7. Milestones

Each milestone ends in working behaviour reachable through MCP in the running containers. Tick them in order.

- **M0. Bootstrap.** Repository, SPEC.md, PROGRESS.md, AGENTS.md, DECISIONS.md, one check command (`./check.sh` or equivalent: lint, types, unit and integration tests), and a compose file where the database and the app start and a health check passes.
  *Proof:* from a clean clone, `docker compose up -d` becomes healthy, and an MCP client lists the tools.
- **M1. Graph core.** Schema, constraints, node create, get, list, update and move, optimistic versioning, event log.
  *Proof:* through MCP, a story without an epic, a task under an epic, a second parent and a stale version are each refused with a plain message; a valid epic, story and task are created and their history is readable.
- **M1A. Dates.** Added after M4 and run before M5, because the roadmap (M11) needs them. Every epic, story and task gets an optional start date and an optional target date, set when a node is created or updated, cleared by an explicit request, and shown by `get_node` and `list_nodes`, which can also filter by them. The database refuses a start date after the target date. Nodes report whether they are overdue, the span of their children's dates when they have none of their own, and any schedule conflict (their start is before the target date of something they need first). Date changes are in the history with before and after like any other change. Under the prototype stance the database is rebuilt, with no upgrade step.
  *Proof:* through MCP, a start date after the target date is refused with a plain message, and the database refuses it on its own; dates set and cleared are shown by `get_node` and are in the history with before and after; a node whose target date has passed is overdue until it is done or dropped; an epic with dated children and no dates of its own reports their span, and one with its own dates reports those; a dependent whose start is before its prerequisite's target date is reported with a schedule conflict that goes away when either date changes; a stale version is still refused for a date change. All earlier proofs still pass.
- **M2. Links, readiness and claims.** Link types, cycle refusal, computed readiness, atomic claims with leases.
  *Proof:* a cycle is refused; finishing a prerequisite makes its dependent ready; ten parallel claimers on one ready task produce exactly one winner; an expired lease can be claimed by another actor.
- **M3. Rules and coverage.** Rules placed in exactly one story, atomic moves, the coverage report.
  *Proof:* a rule cannot be placed in two stories; a move is atomic and logged; the coverage report lists unplaced rules and stories with none.
- **M4. Decisions and principles.** Record, link, supersede, withdraw and exact recall by node. M4 built principles as a kind of decision; M16 makes that a flag, so a decision that applies throughout its project is `project_wide` and is part of every recall and `next_work` briefing of its project.
  *Proof:* recalling a story returns its linked active decisions and every active project-wide decision; a superseded or withdrawn decision is shown as such and not as active; nothing is invented. (Replaced by M16: "all active principles" became "every active project-wide decision".)
- **M4A. Facts and beliefs.** Added after M4 and run before M5. The rest of the context layer, with its guard rails: facts, and one recall of everything known about an item. M4A also built beliefs (conclusions drawn from evidence, with staleness and promotion to a decision); M16 removed them and the world/experience kinds of fact, so this milestone is described as it now stands, and its belief proofs are marked as replaced.
    - **Facts.** `retain_fact` records a fact with its source and the nodes, rules and decisions it concerns. A fact is never edited: `supersede_fact` replaces it, or several at once (see "When something is no longer true"), with a newer fact in one step (the old one is kept, marked superseded, pointing at its replacement, with the reason), and `withdraw_fact` marks it withdrawn, with a reason. A blank source or text is refused.
    - **Confirmation.** Every fact (and every decision) starts **unconfirmed**. `set_confirmation` records that a named person has reviewed it (who and when are kept) or takes that away again; the person's name is required and the actor who made the call is recorded separately, so recording a fact never confirms it. Only an active record's confirmation can change, and what a record was confirmed as stays on it after it is superseded or withdrawn. This is M16's replacement of beliefs: the server infers no conclusion, so there is nothing to confirm but what a person or agent recorded.
    - **When something is no longer true.** Nothing is edited, so a change is always a newer item that replaces older ones. The server never decides by itself that something is contradicted: a person or an agent names what is replaced.
        - *Replace several at once.* `supersede_fact` takes one or more active facts, however many, and the newer fact that replaces them; `withdraw_fact` likewise takes one or more. In one step the newer one is recorded and each old one is marked superseded, pointing at it, with the reason. If any listed fact does not exist or is not active, nothing is changed and the message names it. The only limit is M6's cap on the size of a request.
        - *Walk everything.* `list_facts` pages through every fact in id order (`after_id` and `next_after_id`, like every list) and says how many match in all, so a caller can go through all of them and see from the count that none was skipped. It takes `within_node_id` (an epic, story or task), which matches what concerns that item or anything under it in the hierarchy, or a rule placed in one of those stories, so the facts about a whole area are one paged walk and not one recall per item. It also takes `node_id`, `rule_id` and `decision_id` for exactly one item, and filters by `status` and `confirmation`.
        - *What a person confirmed needs a person.* Replacing or withdrawing a fact (or a decision) that a person has confirmed needs `said_by` (who changed their mind) and `quote` (what they said, or where). An agent told "the owner no longer thinks so" passes the owner's name and words, and the history shows both the person and the agent that relayed it. A record nobody confirmed can be replaced or withdrawn by anyone, with a reason. As with `decided_by` on a decision, the server records who is named and cannot prove that the person said it. A person changing their mind about a decision uses `supersede_decision` or `withdraw_decision` (M4, M16).
    - **Links, lists, history.** `link_fact` and `unlink_fact` change what an active fact concerns (a record that has ended keeps the links it had). `get_fact`, `list_facts` (filtered by status, confirmation and what it concerns) and `fact_history` read them. Everything is in the event log, and what a fact concerns shows in the histories of those nodes.
    - **One recall.** `recall` (it replaces `recall_decisions`, since it returns more than decisions) takes a node or a rule and returns, in separate labelled sections: its active decisions, every active project-wide decision (linked or not), its facts, and, apart from those, its past decisions and past facts (superseded or withdrawn). Every entry says why it is there (linked directly, a project-wide decision that applies everywhere, replaced by item N), who recorded it, whether a named person confirmed it and whether it is still in force, so an unconfirmed record is never presented as confirmed. Each section has its own count and page. Nothing is inferred beyond those exact links.
  *Proof:* through MCP, a fact is retained against a story and appears in the story's recall under facts with its source, recorder and time, shown as not confirmed by a person, and never under decisions; confirming it with `set_confirmation` records who and when, and recall then shows that; a blank source is refused; a superseded fact shows as superseded with its replacement and a withdrawn one as withdrawn with its reason; the recall holds exactly what the exact links give and nothing else; with three facts, a new fact that replaces two does so in one `supersede_fact` call, each old one shows as superseded by it and the third is untouched, and a listed fact that is already withdrawn refuses the whole call and changes nothing, and a call that replaces 30 facts at once works; `list_facts` over 60 facts, in pages, returns every one exactly once and a count that matches, and `within_node_id` an epic returns what concerns its stories and tasks and nothing else; withdrawing a fact works with a reason, and replacing or withdrawing a confirmed fact without `said_by` and `quote` is refused in plain words, and with them it works and the history shows both the person and the agent that relayed it, while an agent alone can withdraw a fact nobody confirmed. The database refuses, on its own, edits and deletes of facts. All earlier proofs still pass, M4's with `recall` in place of `recall_decisions`. (Replaced by M16: the proof lines about beliefs, their evidence, staleness, confirming and promoting a belief, `with_dependent_beliefs` and `rests_on`, and `kind`, `origin` and `happened_on` of a fact, no longer apply because those things no longer exist.)
- **M5. Search and the semantic index.** Embedding client, reindex job, and `search` that matches three ways: by exact words (PostgreSQL full-text search over the graph itself, so it is current the moment a change is saved and still works when the embedding service is down), by meaning (the index), or both fused by rank. Each result says how it matched (words, meaning or both), why (the words that matched, or the similarity score), its current parent and status from the graph, and a highlighted snippet; the answer also carries counts by item type and status. Overlap finder (nearest neighbours across epics above a configurable threshold, with scores, never merging or changing anything), similar recall of decisions and facts, and "similar items" for an item or a piece of text. Decisions and facts are searched too, and each result carries its confirmation and lifecycle so that an unconfirmed fact is never mistaken for a confirmed decision. Queries never fail on odd characters. Meaning results are suggestions, labelled as such.
    - **Search.** `search` takes a query, a mode (`both`, the default, `words` or `meaning`), optional `types` and `statuses`, a `min_similarity`, and `limit` and `offset` (results are in rank order, so this list pages by offset, not by id). Exact words are whole words with their endings (a search for "migration" finds "migrating"); every word must be present, a phrase goes in double quotes, `or` allows alternatives and `-` leaves a word out. Results cover epics, stories, tasks, rules (shown as requirements), decisions and facts. Tasks are found by exact words only, because they are many and short; everything else is also embedded. Fusing is by rank (an item's score is the sum of 1 / (60 + its rank) over the lists it is in), so what matches both ways comes first. A result of meaning alone is flagged `suggestion`. The counts by type and by status are taken before the `types` and `statuses` filters, so a person can see what filtering would give. When meaning cannot be used (no embedding service, the service cannot be reached, the index is not built for the configured model) the answer says so in a note and still gives the exact-words results; asking for `meaning` alone then is refused in plain words.
    - **The reindex job.** The index holds one vector per epic, story, rule, decision and fact, and is derived from the graph: dropping it loses nothing. The job (`reindex`, and a background task in the server that runs every few seconds when something is waiting) is the only code that writes to it. An item is waiting when it has no vector or its text changed since it was embedded (a change to its status or links does not count), so the job needs no signal from the writers. The size of the vectors is read from the model when the index is built, and an index built with another model or size is dropped and rebuilt. If the service refuses one item the rest are still indexed and the report lists the refused one. If the service cannot be reached, nothing is lost: what was embedded stays and the job tries again later. Every answer of `search`, `similar_items` and `find_overlaps` says how many items are waiting.
    - **Similar items and overlaps.** `similar_items` takes one of a node, rule, decision or fact id, or a text, and returns the items nearest in meaning, with scores, never the item itself. `find_overlaps` returns pairs of stories (or epics, or rules) in different epics whose similarity is at least the threshold (`min_similarity`, default `EMBEDDING_OVERLAP_THRESHOLD`), most alike first, and says which links already join the two; it can be limited to pairs involving given epics, and leaves out dropped items unless asked. It only reports. `recall` gains `with_similar`: a last section of active decisions and facts that are alike but not linked, labelled suggestions; the exact sections do not change.
    - **Default thresholds** are for the local model and are measured, not guessed: see `DECISIONS.md`. They are settings (`EMBEDDING_MIN_SIMILARITY`, `EMBEDDING_OVERLAP_THRESHOLD`), because another model scores differently.
  *Proof:* on a fixture of known duplicate and known unrelated pairs, the overlap finder flags the duplicates and not the unrelated pairs, and the measured counts are printed; dropping the index tables and running reindex gives the same results; no tool other than reindex writes to the index. With the embedding service stopped, a phrase added to a story is found by words at once and labelled as an exact-words match, while a paraphrase of it is found by meaning only after the service returns and reindex has run. Results that match both ways are labelled both. The counts by item type equal what the list tools return. A fact and a decision are found by words and by meaning, each labelled with its confirmation and lifecycle. The checks run against a scripted stand-in for the embedding service (`tests/scripted_embeddings.py`, in the check stack), which proves what Vrum does with a service and not how good a model is, so the same fixture of reworded requirements is also run once against the real local model (the `local-embeddings` profile, `scripts/real_embeddings_check.py`) and its measured counts are recorded in `PROGRESS.md`.
- **M5B. Agent workflow.** What an agent needs to do a day's work in few calls and small answers, built on the earlier milestones. It is numbered M5B so that no other milestone is renumbered, and it comes right after M5 in order.
    - **Next work, with its context, in one call.** `next_work` picks the most urgent free story or task (highest priority first, then the earliest target date, then oldest), claims it atomically, marks it in progress, and returns it together with what an agent needs to start: its parent chain, the rules of its story, the active decisions and facts linked to it and to its parents (each saying whether a person confirmed it, and past decisions kept in a section of their own), every active project-wide decision, the handoff notes left by earlier holders of the item and of what it waited for, what finishing it will unblock, and similar existing items. Free means nobody holds it, nothing it needs first is open, and it is ready, or it was in progress and its holder's claim ran out (the answer then says who let it lapse). A story whose tasks are still open is not handed out: it is worked through its tasks. An optional `within_node_id` limits the search to one epic or story. A peek option returns the same without claiming. When nothing is free the answer says so and how much work is held, waiting or blocked: this is not an error. Everything in the context comes by exact link; similar items are labelled as suggestions. The context is cut from the end to a stated size (`context_chars`) and says what was left out.
    - **Handoff notes.** Ending work is one call, `finish_work`: the holder says whether the item is done, blocked, dropped or only released (back to not started), and writes a handoff note (what was done, what the next person must know). A blank note is refused, by the tool and by the database. `release_claim` needs a note too, and puts work that was in progress back to not started. Only the holder can finish, including one whose claim ran out before anyone took over. The note is kept in the item's history and comes back with `get_node` and `next_work`; a claim that lapsed shows as lapsed with no handoff.
    - **A whole plan at once.** `create_plan` creates epics, stories, tasks, links between them and rules in one all-or-nothing call, from items given with temporary keys, any number of them. One bad item refuses the whole plan, and the message names that item and what is wrong. A plan that would make a circle of waiting is refused whole.
    - **Several changes at once.** `update_nodes` changes any number of nodes, each with its own expected version, and reports each one separately: one stale version does not undo the others.
    - **What changed.** `changes_since` lists events after a given event id across the whole graph, filtered by actor or by one item, a page at a time, with the latest event id to keep. Events are shown in the order their changes began, and an event is shown only once the change that wrote it has finished, so a follower never skips one that was written slowly. An agent that comes back after a break, and the board, see only what is new.
    - **Small answers.** Lists leave out bodies by default and say so (each item gives its body length and its first 120 characters instead); a detail option asks for them; reading one item always gives the whole body. Lists also say how many items match in all. Every tool that can return a lot has a stated limit and says how much it left out.
    - **Check before creating.** `create_node` (for epics and stories) and `create_plan` (for its epics and stories) answer with similar existing items (from the index, at least as alike as the overlap threshold, labelled as suggestions) and still create. If the embedding service cannot be reached they say so and still create. Tasks are not checked.
    - **Server instructions.** The MCP server's own instructions tell any agent the working loop in a few lines: take work with `next_work`, recall what is known before deciding, record decisions as they are made, end with `finish_work`. They name only tools that exist, and a test compares them with the live tool list.
  *Proof* (a real MCP client against the real containers):
    1. Ten agents call `next_work` at once on five ready tasks: five each get a different task, none gets a task twice, and the rest are told plainly that nothing is free. Each context holds exactly the parent chain, the rules of the story, the linked active decisions (a superseded or withdrawn one only in its own section), all active project-wide decisions and any earlier handoff notes.
    2. `finish_work` with a blank note is refused and changes nothing. With a note the item is done, its dependent becomes ready, and the next agent's `next_work` shows the note. A claim that lapsed shows as lapsed with no handoff.

## 10. Product shape: what Vrum takes from the tools it is measured against

Vrum is one product with two ways in that always call the same operations: MCP for agents, the board for people. It combines the best parts of five products, and this section says which, and what is left out on purpose, so that a missing feature is a decision and not an accident. The sources are each product's own documentation.

| Product | What Vrum takes | Where | Left out on purpose, and where Vrum is better |
|---|---|---|---|
| **GitHub Projects** (docs.github.com/en/issues/planning-and-tracking-with-projects) | Several views of the same items (board, graph, roadmap); drag a card or a bar to change its value; filter and group; shareable views; batch edits; progress roll-ups; keyboard use | M1A, M10, M11 | No iterations or sprints, no burn-up charts, no items tied to a repository. Better: a real dependency graph with cycle refusal and a computed "ready" (GitHub stores blocked-by as plain metadata), a roadmap that draws the dependencies and flags schedule conflicts, filters that can OR across fields, and one filter language for agents and people. |

**What matters most for effective, efficient, agent- and human-friendly work, in order** (from the research on agents and project management): 1. one call for the next work with its context; 2. ready work that respects dependencies and refuses circles; 3. expiring claims and versions instead of locks; 4. handoff notes that outlive a session; 5. small answers, paging and few consolidated tools; 6. a whole plan created at once; 7. decisions (project-wide ones included) and facts brought to the agent with their reasons and sources; 8. what the agents are doing visible to people, with conflicts and stale claims; 9. finding earlier work before duplicating it; 10. seeing what changed since last time.

**The views, drawers and settings**, so that every part of the product can be seen. Three views are the primary navigation: Board (M10), Graph (M10; M16 adds the Work, Context and Everything presets and the Map and List presentations, with the requirements, decisions and facts list) and Roadmap (M11). Two drawers open over any view: search, with Possible duplicates as a mode (M13), and Activity (M14). The Settings menu holds Agent access (M15), Tools and Status (M14). The shared detail panel opens any item, requirement, decision or fact. Home, Table, Outline, Rules, Memory, Overlaps and Ask no longer exist (M16).

**Getting into the product (M15):** account registration and email/password sign-in, the owner's project list and project creation, a project switcher, and project-scoped agent credentials. The existing pages show only the selected private project. Shared projects, invitations and member roles remain out of scope.
