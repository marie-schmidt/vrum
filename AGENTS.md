# AGENTS.md

How to work in this repository. Read `SPEC.md` first, then `PROGRESS.md`.

## Running the checks

`./check.sh` is the one check command. It runs, in order:

1. lint: `uv run ruff check .` and `uv run ruff format --check .`
2. types: `uv run mypy` (strict)
3. unit tests: `uv run pytest -m "not integration"`
4. integration tests: builds the image, starts the real database and server in a throwaway compose project (`vrum-check`, port 18000 or `VRUM_CHECK_PORT`, random password and random `VRUM_TOKEN`, removed afterwards; `check.sh` exports the token and the tests read the same variable), together with the stand-ins and extras in `compose.check.yaml` (which `check.sh` adds through `COMPOSE_FILE`): a scripted embedding service, a scripted language model (its port, `VRUM_CHECK_PORT` + 2, is published so tests can script it and read what it was sent), and a second server with no language model set up (`VRUM_CHECK_PORT` + 1). It runs `uv run pytest -m integration` with a real MCP client against it. A proof stack started by hand (a clean clone, another compose project and port) needs the same `COMPOSE_FILE=compose.yaml:compose.check.yaml`, the ports `VRUM_NO_MODEL_PORT` and `VRUM_MODEL_SCRIPT_PORT`, and `VRUM_TEST_URL`, `VRUM_NO_MODEL_TEST_URL` and `VRUM_TEST_MODEL_URL` to match, and `VRUM_TOKEN` (the same one in the stack and in the tests), because the tests stop and start the stand-ins.

It needs Docker (with compose) and `uv`. It never touches your own stack or your `.env`. Run it before every commit; fix `ruff format` problems with `uv run ruff format .`.

`./acceptance.sh` is the other command: the shorter walk a person can read. It starts its own throwaway stack (compose project `vrum-acceptance`, port 18400 or `VRUM_ACCEPTANCE_PORT` with the next two ports for the second server and the scripted model, and the one after for the second, empty copy the board chapter makes (compose project `vrum-restore`), random password and token, the same stand-ins as the check stack; it needs `openssl` too), runs one scenario through a real MCP client, prints one line for each proof of each milestone, and removes everything afterwards, even when it fails. Name chapters to run only those (`./acceptance.sh arriving moving`; the names are in `tests/acceptance.py`). It runs in the checkout it is in, so "from a clean clone" means: clone, then run it there. Each later milestone adds its proofs to it.

## Running the stack

```
./scripts/init-env.sh      # once: writes .env with a random database password and a random token
docker compose up -d --build --wait
```

The MCP endpoint is `http://127.0.0.1:8000/mcp` (or `VRUM_PORT`), and the board (M10 onward) is at `http://127.0.0.1:8000/board` on the same port: open it in a browser and type the token. While working on the board's pages (`src/vrum/board/static`), the server reads them once at start, so rebuild the image to see a change, or mount that folder over `/app/.venv/lib/python3.12/site-packages/vrum/board/static` in a scratch compose override and restart `app`. Every request to it needs the token from `.env`, as `Authorization: Bearer <token>`; the server does not start without `VRUM_TOKEN`, and only `GET /health` (the health check) is open. For a script or a client of your own, `scripts/vrum_client.py` connects with the token it reads from the `VRUM_TOKEN` environment variable (`export VRUM_TOKEN=...` first; the helper scripts below need it). The most one request may hold is `VRUM_MAX_REQUEST_BYTES` (4 MiB). `docker compose down` stops it; add `--volumes` to also delete the data. Logs are JSON lines (`docker compose logs app`): they never hold the token, passwords, keys or what was written.

**Backing up and moving data.** `./scripts/backup.sh [file]` writes the whole database to one file (default `backups/vrum-<time>.dump`, git-ignored, readable only by you) while the server runs. `./scripts/restore.sh <file>` puts it back: into a fresh database (after `docker compose down --volumes`) it just restores; into one that holds data it refuses unless you add `--replace`. For data you can read, keep or load into another server: `uv run python scripts/export_graph.py <url> <file.json>` writes everything as one JSON file, `scripts/import_graph.py <url> <file.json>` loads such a file into an empty server (all or nothing; as big as one request may be), and `scripts/export_markdown.py <url> <folder>` writes a read-only Markdown copy, one file per item with `[[references]]`, to read in Obsidian or keep in git. All three need `VRUM_TOKEN` set, and work from a checkout without installing anything.

Search by meaning, similar items and overlaps need an embedding service; exact-words search needs nothing. To run one on this machine, add `EMBEDDING_BASE_URL=http://ollama:11434/v1` and `EMBEDDING_MODEL=all-minilm` to `.env` and start with `docker compose --profile local-embeddings up -d --build --wait` (the first start downloads the model, about 50 MB). Any OpenAI-compatible service works instead: set the two variables to its address and model (see `.env.example`). To see what a real model does with realistic requirements, run `uv run python scripts/real_embeddings_check.py http://127.0.0.1:8000/mcp` (with `VRUM_TOKEN` set to the token in `.env`; it adds a few clearly named epics and stories). The thresholds depend on the model: measure, then set `EMBEDDING_MIN_SIMILARITY` and `EMBEDDING_OVERLAP_THRESHOLD`.

`extract_facts`, `consolidate_memory`, `find_contradictions` and `reflect` need a language model; without one they say so and everything else works. Set `LLM_BASE_URL` and `LLM_MODEL` in `.env` (any OpenAI-compatible chat service; see `.env.example`). To use Ollama installed on this machine: `LLM_BASE_URL=http://host.docker.internal:11434/v1` and `LLM_MODEL=llama3.2`. To see what a real model does with the same notes and questions every time, run `uv run python scripts/real_model_check.py http://127.0.0.1:8000/mcp` (it adds a few clearly named items); what it prints is recorded in `PROGRESS.md`.

## Layout

- `src/vrum/config.py`: settings from the environment (the only place that reads it), including the token, the request size limit and the optional embedding and language services.
- `src/vrum/db.py`: the PostgreSQL pool, transactions, and `prepare_schema`, which builds an empty database from `schema.sql` and refuses one built from any other version of it.
- `src/vrum/schema.sql`: the whole database in one file: tables, constraints, triggers and the `node_state`, `decision_state` and `memory_state` views.
- `src/vrum/common.py`: what the modules below share: `Refusal` (the plain-English refusals), argument checks (including `parse_day` for dates), paging, and database helpers.
- `src/vrum/graph.py`: the one owner of epics, stories and tasks (`Graph`), and of how a node is read (`node_state`, backed by the `node_state` view that decides what `ready` means).
- `src/vrum/links.py`: the one owner of links. `src/vrum/claims.py`: the one owner of claims, leases and the handoff note that ends one (`next_work` and `finish_work` use its helpers).
- `src/vrum/rules.py`: the one owner of rules and the coverage report. `src/vrum/decisions.py`: the one owner of decisions and principles, their links and supersession.
- `src/vrum/memories.py`: the one owner of facts and beliefs: their evidence and links, replacing and retracting them, confirming a belief and promoting it to a decision (staleness is worked out by the `memory_state` view). `src/vrum/recall.py`: `recall`, everything known about one node or rule by exact links, from decisions and memories.
- `src/vrum/embeddings.py`: the one small interface to an OpenAI-compatible embedding service (text in, vectors out). `src/vrum/llm.py`: the same for a chat service (one question in, a JSON object out; it never decides whether an answer can be believed). `src/vrum/secret_formats.py`: recognises secrets in well-known formats (`find_secret`, `find_secret_in` for nested arguments, `redact_secrets`), used before text is sent to a model and by M6 on every tool argument and on every write (`common.refuse_secrets`).
- `src/vrum/reflection.py`: the four tools that need a language model (`extract_facts`, `consolidate_memory`, `find_contradictions`, `reflect`) and the checks on what a model says: a passage must be in the text, evidence must be among what it was given, quotes must be there, citations must be of what was retrieved. It writes only through `Memories` (origin `extracted` or `derived`) and logs each answered call as a `model_call` event.
- `src/vrum/indexing.py`: the semantic index and its reindex job, the only code that creates, changes or drops the index tables (`semantic_index`, `semantic_index_info`, which are derived and not in `schema.sql`), plus the background task that keeps it current. `src/vrum/search.py`: search by words, meaning or both, similar items and the overlap finder (read only). Exact-words search reads the `search` columns of the graph tables.
- `src/vrum/workflow.py`: what an agent does in a day's work, built on the owners above and not repeating them: `next_work` (pick, claim and brief in one transaction, with the context cut to a size), `finish_work`, `create_plan` (check a whole plan, then create it in one transaction), `update_nodes`, `changes_since` (a feed that never skips a late event), and `create_node`'s check for similar items.
- `src/vrum/server.py`: the MCP tools (thin: they call `Graph` and the other owners), the server instructions, the background reindex task, and the health route.
- `src/vrum/exchange.py`: moving the whole graph as data: `export_graph`'s pages (everything in id order, as plain text and numbers) and `import_graph` (a file is read and checked, every problem listed at once, then loaded into an empty database in one step with its ids; the endings of replaced and retracted things are applied last so that the database's own rules are never bypassed). `src/vrum/markdown.py`: `render`, a pure function from an export to the files of the read-only Markdown copy.
- `src/vrum/guard.py`: `GuardedServer`, the MCP server every tool call goes through: it refuses a secret in any argument before anything else, turns the SDK's validation errors into plain messages that do not repeat what was sent, and logs one line per call. `src/vrum/access.py`: the `AccessGuard` around the whole web app: the bearer token on everything but `GET /health` and the request size limit, answering with plain JSON-RPC errors. `src/vrum/logs.py`: the JSON log format and the scrub that removes the token, passwords, keys and secret formats from every line.
- `src/vrum/board/`: the board. `__init__.py` is its server side (`add_board`): the page files under `/board` (open, since they hold no data; every response carries the content security policy), `POST /board/api/tool/<name>` (calls the MCP tool of that name on the same server, so every board action is the same operation as the matching tool, with the same refusals; only the tools in `READ_TOOLS` and `WRITE_TOOLS` may be called, and a test checks they exist and that `reindex` is not among them), `GET /board/api/info` and `GET /board/api/index` (how many items wait to be indexed). `static/` holds the pages: plain HTML, CSS and ES-module JavaScript with no build step and no library. Text is only ever put on a page as text (`dom.js` builds elements; a test fails on `innerHTML` and the like), and there is no inline script or style. `app.js` is the shell (sign-in, name, address, top bar), `api.js` talks to the server, `store.js` holds the copy of the graph and polls `changes_since`, `kanban.js` the Kanban page, `card.js` the card of one item, `panel.js` the side panel, `coverage.js`, `create.js`, `graph.js` (drawing, zoom, pin, lists), `graph-data.js` (what the switches and scopes show) and `layout.js` (the force layout). `static/brand/` holds the logo and icons. A later board milestone adds its pages as modules like these and the tools they need to `READ_TOOLS` or `WRITE_TOOLS`.
- `src/vrum/__main__.py`: starts the server (the token and the logs are set up here). `src/vrum/healthcheck.py`: the container health probe.
- `tests/`: unit tests, plus the integration tests (marked `integration`, driven by `./check.sh`): `test_mcp_integration.py`, `test_graph_integration.py`, `test_links_and_claims_integration.py`, `test_rules_integration.py`, `test_decisions_integration.py`, `test_memories_integration.py`, `test_search_integration.py`, `test_workflow_integration.py`, `test_reflection_integration.py`, `test_hardening_integration.py` and `test_exchange_integration.py` go through a real MCP client (`test_hardening_integration.py` also uses raw HTTP for what a caller that is not an MCP client is told, and reads the container's log; `test_exchange_integration.py` also runs `scripts/export_graph.py` and `scripts/export_markdown.py` as a person would); `test_exchange_second_stack.py` starts a second, separate copy of Vrum (`second_stack.py`: its own compose project `vrum-restore`, volume, port `VRUM_CHECK_PORT` + 3 and token, which `check.sh` also removes if a test dies) to destroy and load databases: the import round trip, and `backup.sh` then `restore.sh` into a fresh container; `test_index_writers.py` proves from the source that only `indexing.py` writes to the index; `scripted_embeddings.py` and `scripted_model.py` are the stand-in embedding service and language model the check stack runs (`compose.check.yaml`), so checks need no model download (a test scripts the model with `ScriptedModel` in `helpers.py` and reads what it was sent); `test_database_constraints.py` runs SQL inside the real database container to prove the database refuses bad data on its own. `helpers.py` holds the small shared test helpers (including `connect`, which opens a client with a token, `export_everything`, and `rich_world`, one of everything the graph holds made through the tools); `documents.py` builds export files by hand. The unit tests `test_access.py` (the guard, the log scrub), `test_guard.py` and `test_init_env.py` cover the M6 pieces that need no containers, `test_exchange.py` (reading a file to import) and `test_markdown.py` (the Markdown copy) the M7 ones, and `test_readme.py` the M9 one: the README's agent guide is `INSTRUCTIONS` word for word, and the files, settings and tools it names exist. `test_board.py` covers the board's server side (which tools its pages may call, what is open without a token, that the pages load nothing from elsewhere and never put text on a page as HTML). The board's integration tests drive Playwright's Chromium (a development dependency only, never in the app image; `./check.sh` and `./acceptance.sh` run `uv run playwright install chromium`, which downloads it once): `test_board_integration.py` (Kanban, card, refusals, index, text only, keyboard) and `test_board_graph_integration.py` (the graph; its "Everything" test runs on a second, empty copy of Vrum from `second_stack.py`), with `board_helpers.py` for the browser. Use unique words in titles and the `epic=` address to keep a test to its own epic, since all tests share one database, and give the browser a tall window (so that nothing scrolls during a drag).
- `README.md`: what a person reads first: quick start, token, connecting an agent, the agent guide (a copy of `INSTRUCTIONS` in `server.py`, which `tests/test_readme.py` keeps equal; change both together), backup and restore, settings. A milestone that changes what a person does adds it here.
- `acceptance.sh` and `tests/acceptance*.py`: the acceptance scenario. `acceptance.sh` brings up the throwaway stack and calls `tests/acceptance.py`, which runs the chapters in order (`arriving`, `planning`, `working`, `decisions`, `remembering`, `finding`, `model`, `hardening`, `board`, `moving`; the chapters are in `acceptance_scenario.py`, `acceptance_finding.py`, `acceptance_model.py`, `acceptance_board.py` and `acceptance_moving.py`). Each `proof(milestone, what, held, detail)` prints one line and stops the run with a plain message when it does not hold. It reuses `helpers.py`. It is a walk, not a second test suite: a proof about the source code (`test_index_writers.py`) stays in `check.sh`, and the scenario shows what can be seen from outside. Add the proofs of a new milestone to the chapter they belong to, or a new chapter.

## Working rules

- One milestone per iteration: the first unchecked one in `PROGRESS.md`. Never start the next one.
- A milestone is finished only when its "Proof" in `SPEC.md` passes against the real containers and a real MCP client, with every earlier proof still passing.
- Product decisions that `SPEC.md` does not answer go in `BLOCKED.md` (question, 2 to 3 options, a recommendation, the default you would take). Do not invent answers.
- Defaults the owner may veto are recorded in `DECISIONS.md` and listed under "Defaults taken" in `PROGRESS.md`.
- **No migrations.** Vrum is a prototype with no customer data. The whole database is `src/vrum/schema.sql`. To change the schema, edit that file, tidying it as if it had always been this way, then rebuild the database from scratch: `docker compose down --volumes`, then `docker compose up -d --build --wait` (`./check.sh` already builds a fresh one every run). Do not write migration files, `ALTER TABLE` patches or data-preserving upgrade steps. Reconsider only when a database holds data someone cares about. (Owner's decision, see `DECISIONS.md`.)
- **Prototype stance.** Do not carry production habits that protect data or users that do not exist yet: no backward compatibility, deprecation paths or upgrade steps. When a design changes, change it everywhere and rebuild. Anything `SPEC.md` asks for is still built as written.
- Never commit a secret. Configuration comes from the environment.
- Never touch any Deelio repository or the Taiga project.
- No placeholder or shell code, and no abstraction without a consumer.
- Keep every change small and reviewable. Plain English in every message a person or agent reads.
- The MCP SDK is v2 (`from mcp.server import MCPServer`, `from mcp import Client`); its documentation is at https://py.sdk.modelcontextprotocol.io/. Check it before using an SDK feature.
