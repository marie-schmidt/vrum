# AGENTS.md

How to work in this repository. Read `SPEC.md` first, then `PROGRESS.md`.

## Running the checks

`./check.sh` is the one check command. It runs, in order:

1. lint: `uv run ruff check .` and `uv run ruff format --check .`
2. types: `uv run mypy` (strict)
3. unit tests: `uv run pytest -m "not integration"`
4. integration tests: builds the image, starts the real database and server in a throwaway compose project (`vrum-check`, port 18000 or `VRUM_CHECK_PORT`, random database password, removed afterwards; there is no token: the tests register an account, make a project and an agent key through the board's own HTTP API, `tests/world.py`), together with the one extra in `compose.check.yaml` (which `check.sh` adds through `COMPOSE_FILE`): a scripted embedding service (`tests/scripted_embeddings.py`; tests stop and start it to see what happens when it is gone) and the settings that point the server at it. The stack is, since M25, `db`, `app`, `scripted-embeddings`, `scripted-mail` and the sign-in providers, and, since M37, the real `sandbox` of code mode (it comes from `compose.yaml`, with nothing scripted in its place): `scripted-oidc` (`tests/scripted_oidc.py`) and `scripted-github` (`tests/scripted_github.py`), stdlib stand-ins that mint real RS256 tokens and GitHub's documented responses and can be told to misbehave through `POST /_control` (wrong nonce, audience, issuer, expired, `alg: none`, a tampered signature, an unverified or missing address, and so on) and to say what they were asked at `GET /_log`; `ldap`, a REAL OpenLDAP (`osixia/openldap:1.5.0`, fictional people loaded from `tests/providers/ldap/people.ldif`); and `dex` (a REAL OpenID provider, `ghcr.io/dexidp/dex`) with `app-dex`, a second copy of the server pointed at it (Dex is reached at `dex.localhost` on the same port inside and outside, so the browser and the server see one issuer address). The app's OIDC slot points at `scripted-oidc`, GitHub at `scripted-github` and LDAP at `ldap`. A browser must use `http://localhost:<port>/board` (not `127.0.0.1`) for any provider leg, because the redirect addresses and the `vrum_sso` cookie are for `localhost`. Ports come from `VRUM_OIDC_PORT`, `VRUM_GITHUB_PORT`, `VRUM_DEX_PORT` and `VRUM_DEX_APP_PORT` (`check.sh` uses the app port plus 3 to 6; `acceptance.sh` plus 3, 6, 7 and 8); a stack started by hand must set all of them. Tests that need other settings restart `app` with `VRUM_SSO_CREATE_ACCOUNTS` or an `*_ALLOWED_DOMAINS` variable set (compose.check.yaml passes those through), which also forgets the in-memory limits. `scripted-mail` is the stand-in mail server of M24 (`tests/scripted_mail.py`: an SMTP receiver that keeps what it is sent and shows it as JSON and as a plain page, at `VRUM_TEST_MAIL_URL`; an address at `reject.example` is refused with a 550 so a test can see a failure; `check.sh` and `acceptance.sh` pick its port); `second_stack.py` is built from `compose.yaml` alone, so it has no mail and no provider. There is no language model and no stand-in for one. It runs `uv run pytest -m integration` with a real MCP client and a real headless browser against it. The tests that destroy or load a whole database start a second, separate copy of Vrum (`tests/second_stack.py`: compose project `vrum-restore`, built from `compose.yaml` alone, on port `VRUM_CHECK_PORT` + 1, which `check.sh` passes as `VRUM_RESTORE_TEST_PORT` and also removes if a test dies). A proof stack started by hand (a clean clone, another compose project and port) needs the same `COMPOSE_FILE=compose.yaml:compose.check.yaml`, `VRUM_TEST_URL` for its MCP endpoint and `VRUM_RESTORE_TEST_PORT` for the second copy (plus `VRUM_RESTORE_PROJECT` if several stacks share one machine), because the tests stop and start the stand-in.

It needs Docker (with compose) and `uv`. It never touches your own stack or your `.env`. Fix `ruff format` problems with `uv run ruff format .`.

**When to run the long checks (owner's rule, 2026-11-17).** The full `./check.sh` (about 30 minutes) and a clean-clone `./acceptance.sh` (about 10 minutes) are not run on every change or every commit. Run only what the change needs while working: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy`, the unit tests (`uv run pytest -m "not integration"`, seconds), and the few integration tests or acceptance chapters that cover the area changed, on a stack with its own project name and port. Run the full `./check.sh` and `./acceptance.sh` only when the owner asks for them explicitly. When the owner asks to commit or push to `main` (that is, toward production), suggest running them first, say what has and has not been run since the last full pass, and let the owner decide. A local checkpoint commit does not need them. Never claim a full pass that was not run.

`./acceptance.sh` is the other command: the shorter walk a person can read. It starts its own throwaway stack (compose project `vrum-acceptance`, or `VRUM_ACCEPTANCE_PROJECT`; port 18400 or `VRUM_ACCEPTANCE_PORT`, and the next port for the second, empty copy that the numbering, quickstart and moving chapters make for a database of their own (compose project `vrum-restore`, or `VRUM_RESTORE_PROJECT`), so that several walks can run on one machine at once; random password, the same scripted embedding service as the check stack; it needs `openssl` too), runs one scenario through a real MCP client and a headless browser, prints one line for each proof of each milestone, and removes everything afterwards, even when it fails. Name chapters to run only those (`./acceptance.sh finding board`; the names are the keys of `CHAPTERS` in `tests/acceptance.py`). It runs in the checkout it is in, so "from a clean clone" means: clone, then run it there. Each later milestone adds its proofs to it.

## Running the stack

```
./start.sh
```

There is nothing to set up first: no `.env`, no variable. `./start.sh` is `docker compose up -d --build --wait` followed by a message with the board's address. The first start makes a random database password in the `vrum-secrets` volume (the database service's entrypoint in `compose.yaml` writes `/secrets/db-password`; the server reads it through `VRUM_DB_PASSWORD_FILE`). Set `VRUM_DB_PASSWORD` before the very first start to choose it; it is ignored afterwards. `compose.yaml` must never use a `${NAME:?...}` that refuses to start without a value (`tests/test_config.py` fails on one), and `tests/test_zero_setup_integration.py` starts a copy with nothing set to prove it. **Before any `docker compose down` or `up` of your own in this checkout, set a scratch `COMPOSE_PROJECT_NAME` (and port):** the default project name is `vrum`, which is the owner's own stack.

The board is at `http://127.0.0.1:8000/board` (or `VRUM_PORT`) and the MCP endpoint is `http://127.0.0.1:8000/mcp` on the same port. There is no install-wide token: open the board, create an account (email and password kept by Vrum, `src/vrum/accounts.py`), create a project (it opens at `/board/p/<id>`), and on its **Agent access** page (Settings menu) make an agent key (`vrk_…`, shown once, only its hash is kept). Every request to the MCP endpoint needs a project's agent key, as `Authorization: Bearer <key>`, and reaches that project only; the board's own calls under `/board/api` carry a session cookie and the session's CSRF secret instead; only `GET /health` and the board's page files are open. While working on the board's pages (`src/vrum/board/static`), the server reads them once at start, so rebuild the image to see a change, or mount that folder over `/app/.venv/lib/python3.12/site-packages/vrum/board/static` in a scratch compose override and restart `app`. For a script or a client of your own, `scripts/vrum_client.py` connects with the key it reads from the `VRUM_AGENT_KEY` environment variable (`export VRUM_AGENT_KEY=...` first; the helper scripts below need it). The most one request may hold is `VRUM_MAX_REQUEST_BYTES` (4 MiB). `docker compose down` stops it; add `--volumes` to also delete the data. Logs are JSON lines (`docker compose logs app`): they never hold passwords, sessions, keys or what was written.

**Looking around with sample data.** `./demo.sh` starts a separate stack (compose project `vrum-demo`, or `VRUM_DEMO_PROJECT`, which must contain `demo`; port 8091, or `VRUM_DEMO_PORT`; its own volumes; it ignores `.env`) and fills it through the real board API and a real MCP client with a fictional bike-share project (`tests/demo_data.py` is the description, `tests/demo_details.py` holds what stories and tasks say about themselves, `tests/demo_world.py` loads it, `tests/test_demo.py` tests all three): 13 epics (one is the Inbox, with seven loose stories), 65 stories, 190 tasks, 48 links (four are `discovered_from`), 156 acceptance criteria (on about half the tasks and most stories), a definition of done set by the demo owner (nine lines: six ordinary checks, one tagged `[verifier]`, one `[github]` and one `[person]`), 40 notes (21 with a person who decided them), claims, dependencies and a history (about 1,420 changes; the waiting plan, "Winter fleet expansion", hangs under the existing Fleet epic with 3 stories and 4 tasks, sizes (one task unsized on purpose), a high priority, details, dates, criteria, two `needs_first` links and a `relates_to` link, so that its card on the Needs page has a diff worth reading, and its third story, `winter-battery`, repeats the existing story "Battery swap schedule" in other words so that the plan's duplicate check is a real warning, measured with the real model at about 0.72; since M51 it is at revision 2 after the demo owner's two comments, which stay as threads under their lines, and a second plan, "Spring tyre check", waits for its agent after a request for changes and is in no Needs row; 13 items are held in all), six asks (Q-numbers are event ids: three still waiting for a person and three answered, one by a person's comment) with 17 rows on the Needs a person page (4 ask, 1 check, 1 gate, 1 lapse, 6 note, 3 placement, 1 plan; since M50 one of the three waiting moves is routine, which the loader reads from the server and `Flow.check` insists on, and a second-look move made by hand for the deposit story shows a low score beside a higher one). Five claims say where the work is (M41: a branch, a commit and a pull request address of the made-up `example-org/bike-share`, a run label and a client name; one key holds work under two run labels, as two instances would, one claim says nothing and one has lapsed) and 13 of the 19 handoff notes say a branch and a pull request (the same address as the verifier's `[github]` tick on finished work); `docs-agent`'s key has a last day 90 days after the day the demo is loaded, so the Users page shows it. One kept key, `review-agent`, is a **verifier** (M40): four tasks are blocked, held by nobody and handed over with a note saying they are ready for it (`is:unverified` finds them, and also the other blocked work that nobody holds), and the 48 finished stories and tasks have the `[verifier]` and `[github]` checks ticked by it, the `[github]` one with evidence in the fixed form and a made-up pull request address of `example-org/bike-share`. Every epic and all but two stories have a description, about two thirds of the tasks a few sentences, and the rest are blank on purpose so that the empty Details field shows. It prints the address and a random password for `demo@example.com`, and running it again starts from a fresh database. Search by meaning in the demo runs on the real embedding service (the `embeddings` container: `compose.demo.yaml` points the app at it and `demo.sh` turns its `real-embeddings` profile on), not on the checks' scripted stand-in. The demo also runs the stand-in mail server (port 8092, or `VRUM_DEMO_MAIL_PORT`) and prints its address: it sends no real email, and its page shows every message the demo sent (Priya's invitation, and the confirmation link of each account, and any reset link you ask for), so they can be read and clicked there. It also runs the sandbox of code mode, so a key made in the demo that calls Vrum by running code works, and the stand-in OpenID provider (port 8093, `VRUM_DEMO_OIDC_PORT`), the stand-in GitHub (port 8094, `VRUM_DEMO_GITHUB_PORT`) and a real OpenLDAP with fictional people (no browser port), so the sign-in buttons work and nothing real is contacted: signing in as the stand-in person Priya joins her confirmed demo account, Tom is refused because his demo account's address was never confirmed, and Noor is a new person who gets an account with no password. `./demo.sh stop` removes its containers, volumes and image and nothing else. It is a way to look at the board before putting real work in, not a seeding feature: nothing on the server creates sample data.

**Backing up and moving data.** `./scripts/backup.sh [file]` writes the whole database to one file (default `backups/vrum-<time>.dump`, git-ignored, readable only by you) while the server runs: every account and project, hashes included, so it is for whoever runs the server and not an account's to take. `./scripts/restore.sh <file>` puts it back (it creates the database role the projects run as first, since a role belongs to the server and not to a database): into a fresh database (after `docker compose down --volumes`) it just restores; into one that holds data it refuses unless you add `--replace`. For one project's data that you can read, keep or load into another project or server: `uv run python scripts/export_graph.py <url> <file.json>` writes the project as one JSON file (ids included: each project numbers its own), `scripts/import_graph.py <url> <file.json>` loads such a file into an empty project (all or nothing; as big as one request may be), and `scripts/export_markdown.py <url> <folder>` writes a read-only Markdown copy, one file per item with `[[references]]`, to read in Obsidian or keep in git. All three need `VRUM_AGENT_KEY` set (the project's key), and work from a checkout without installing anything.

Search by meaning, similar items and possible duplicates need an embedding service, and **one comes with Vrum** (M29): the `embeddings` service of `compose.yaml`, built from `embedder/` (`server.py`: a stdlib HTTP server speaking the one OpenAI call Vrum uses, `POST /v1/embeddings`, plus `GET /health`, with the model loaded by `load_model` so its request handling is tested without it; `fetch_model.py`: fetches all-MiniLM-L6-v2 at a fixed revision into the image at build time and checks its SHA-256, so nothing downloads when it runs; `requirements.txt`: compiled with hashes by `uv pip compile requirements.in --universal --generate-hashes --python-version 3.12 -o requirements.txt`; the Dockerfile installs with `--require-hashes`). The app defaults to it (`EMBEDDING_BASE_URL` `http://embeddings:8080/v1`, `EMBEDDING_MODEL` `all-MiniLM-L6-v2`, in `compose.yaml` as `${NAME-default}`, so a value set to nothing means none) and does not wait for it. It is not published outside Docker. Its refusals are plain sentences, and it never logs a text. The check stack (`compose.check.yaml`) leaves it out (`profiles: ["real-embeddings"]`) and uses the scripted stand-in; the second stack leaves it out too unless `SecondStack(embeddings=True)` (`tests/test_embeddings_second_stack.py` is the one proof of the real thing). To use another OpenAI-compatible service set both variables to its address and model and leave the built-in one out with `docker compose up -d --build --wait --scale embeddings=0`; both set to nothing means no meaning search at all. To see what a real model does with realistic requirements, run `uv run python scripts/real_embeddings_check.py http://127.0.0.1:8000/mcp` (with `VRUM_AGENT_KEY` set to a project's agent key; it adds a few clearly named epics and stories). The thresholds depend on the model and were measured on the built-in one (0.35 and 0.55 stand: 9 of 10 reworded duplicates, 1 of 5 related pairs and 0 of 125 unrelated pairs flagged); for another model measure, then set `EMBEDDING_MIN_SIMILARITY` and `EMBEDDING_OVERLAP_THRESHOLD`.

Vrum has no language model and no setting for one: nothing on the server generates text. An agent that wants a conclusion kept records it with `add_note` like any other statement.

**Code mode (M37): the sandbox.** A key made with `code_mode` (the board's "How it calls Vrum", `agent_keys.code_mode`) is offered exactly `explore` and `run`, and everything it may do is a function of `vrum` inside a TypeScript script. The script is untrusted code and runs ONLY in the `sandbox` service of `compose.yaml`, built from `sandbox/` like `embedder/`: `supervisor.py` (stdlib asyncio; one connection per run on the Unix socket `/run/sandbox/run.sock`, a volume shared with the app; the wire protocol is documented at the top of the file and fixed by `tests/test_code_mode.py`'s fake sandbox), `prepare.ts` (strips types in a process with no permission), `deno check` against `prelude.d.ts` and the declarations the app sends, and `runner.ts` (evaluates the plain JavaScript from a STRING with `new AsyncFunction`, never as a module: Deno does not check permissions on static imports; every `node:*` module is stubbed by `import_map.json`; `Deno` and the other globals are removed after the runner has used them). Deno 2.9.8 is pinned by SHA-256 for both architectures in `sandbox/Dockerfile` (`fetch_deno.py`, build time only). The container has no network (`network_mode: none`), no secret, a read-only root, no capabilities, a non-root user (10002; the app is 10001 and joins group 10003 to use the socket), and limits on memory, processes and cpu; each run also gets a heap limit, `RLIMIT_DATA`, `RLIMIT_CPU`, a process group that is killed at the time limit, and an empty environment. `tests/sandbox_attacks.py` (not collected by pytest; run it with `uv run python -m tests.sandbox_attacks --container <sandbox container>`) is the exhaustive list of attacks (about 140 lines, 3 to 4 minutes) and one integration test runs it. On the app side `src/vrum/sdk.py` turns the tools' JSON schemas into TypeScript (result types exact: fields with defaults are required, the SDK's `{"result": ...}` wrapper is unwrapped) and `src/vrum/code_mode.py` is the host: it connects, sends the script and answers each call through `GuardedServer.call_inner` (the same secret scan, allowance check, project, identity and log line as a tool call, with `via=run`, a `run_id` and a script hash, never text), serialises writes, counts calls (200, 100 of them writes), bytes and time itself without trusting the sandbox, allows four scripts at once, and says plainly when the sandbox is not running. Never run model-written code anywhere else, and never give the sandbox a network, a secret or a database.

## Layout

- `src/vrum/config.py`: settings from the environment (the only place that reads it), including the request size limit, the board's poll interval, the optional embedding service and the optional mail server (`VRUM_PUBLIC_URL`, `VRUM_SMTP_HOST`, `VRUM_SMTP_PORT`, `VRUM_SMTP_SECURITY`, `VRUM_SMTP_USER`, `VRUM_SMTP_PASSWORD` or `_FILE`, `VRUM_SMTP_FROM`: off unless `VRUM_SMTP_HOST` is set; links in mail are built from `VRUM_PUBLIC_URL`, never from the Host header; `docs/configuration.md` lists them) and the optional sign-in providers (`VRUM_SSO_CREATE_ACCOUNTS`, `VRUM_SSO_ALLOW_INSECURE_HTTP`, the `VRUM_OIDC_*`, `VRUM_GITHUB_*` and `VRUM_LDAP_*` settings of M25, each provider off unless its main setting is set, client secrets and the LDAP bind password read like the SMTP password). There is no token setting and no language-model setting.
- `src/vrum/accounts.py`: the one owner of accounts, sessions, projects, agent keys, members and invites (the `accounts`, `sessions`, `projects`, `agent_keys`, `project_members` and `project_invites` tables, which are not graph content and which a project's database role cannot reach): `Accounts.register`/`sign_in` (scrypt hashes, `hash_password`/`password_matches`; the failures of one address or one network address are counted by `src/vrum/ratelimit.py`'s `AttemptLimiter`, in memory), `session` (a cookie's value, of which only a SHA-256 is stored, plus a CSRF secret), `projects`/`create_project`/`project_of` (which returns the person's role, `owner`, `editor` or `viewer`; a project that does not exist, one that is someone else's and one the person is not in are refused in the same words), the account's rename and password change (a name must be unique among a project's people, checked under one lock), `create_key`/`keys`/`revoke_key`/`set_key_tools`/`set_key_verifier`/`set_key_expiry`/`project_for_key` (a key is `vrk_…`, shown once, only its hash stored; its name is the agent's name, unique among the project's keys in force; `agent_keys.verifier` (M40) marks an agent that checks other agents' work, set when the key is made or by the owner, applying on its next request; `agent_keys.expires_on` (M41) is the last UTC day the key works, set when it is made or by the owner (`clean_expiry`: a day that has passed is refused, an empty value clears it), with `KeyInfo.expired` the server's own answer; `project_for_key` and `access_of_key` raise `KeyExpired` for a key whose day has passed, so the request, an open connection and a running script's next call are each refused in words that say it expired and who can fix it, told apart from a wrong or revoked key (the access guard logs `key_expired`); its allowance, `agent_keys.allowed_tools`, is NULL for the standard tools (the set Vrum offers agents, `surface.AGENT_TOOLS`, at most 25) or a list of exactly the tools it may call (any the server has except people-only ones, offered or not), deny by default for a later tool; the key routes are the owner's), and the members and invites (`vri_…` tokens, shown once, hashed, valid 7 days, used once; failed lookups are rate limited; an invitation sent to an address is bound to it: only an account with that address can accept it, a refusal names it masked, `create_invite(email=…)` sends the link through `mail.py` and answers `emailed` and `email_problem`, `resend_invite` makes a new token and stops the old one), and, when mail is on, email confirmation (`accounts.email_verified_at`, `vrv_…` links valid 24 hours, `send_verification`/`verify_email`, soft: nothing is gated on it) and password reset (`request_reset` always gives the same answer for any address and sends in the background; `vrr_…` links valid 1 hour, used once; `reset_password` ends every session of the account and spends its other reset links; limits per address and per network address in memory). Both kinds of link live in the account-level table `email_tokens` (hashed), which has no `project_id`; a GET never uses a link, only a POST does. Refusals are `AccessRefusal` (a `Refusal` with an HTTP status).
- `src/vrum/db.py`: besides the pool and `prepare_schema`, how work is bound to a project: `working_for(project_id)` sets the project for everything done inside it (a `ContextVar`), `Database.transaction()` is the project-scoped transaction (it does `set_config('vrum.project_id', …)` and `SET ROLE vrum_project`, so the database shows only that project's rows; with no project named it raises `NoProject` and the database shows none), and `Database.admin_transaction()` is for what is not a project's own work (accounts, projects, keys, the index job, building the schema). Never use `admin_transaction` for graph data in a tool.
- `src/vrum/schema.sql`: the whole database in one file: the account tables, then the graph tables (`nodes`, `links`, `claims`, `rules`, `notes` with their link tables `note_nodes`, `note_rules` and `note_notes`, and `events`), constraints, triggers and the `node_state` and `note_state` views (plus `search_documents` and `index_source`, which exact-words search and the index read). Every graph table has a `project_id` that is part of its primary key and of every foreign key, so a row cannot refer to a row of another project; each project numbers its own epics, stories, tasks, links, rules, notes and events from 1, **each kind with its own counter** (a sequence per project and kind, made when the project is made, read with `next_id(kind)`; `continue_ids_after` sets it after an import). A node has no integer id: its key is `kind` and `number`, and its generated `ref` (`story:12`) is what every other table's foreign key holds (`links.source/target`, `claims.node`, `rules.story`, `decision_nodes.node`, `fact_nodes.node`, `events.node/other_node`, `nodes.parent`), with `kind_rank` to order epics, stories, tasks; and row-level security with a policy `project_id = current_project()` on every graph table, for the role `vrum_project` (the server switches to it for each project transaction; it has only the rights listed at the end of the file and none on accounts, sessions, projects or keys). Views are `security_invoker`. A note is a record the database never lets be edited or deleted (triggers): only its status between unconfirmed and confirmed (with who confirmed it and when) changes while it is in force, and an ended one (superseded or withdrawn) cannot change at all. A note in force is `confirmed` exactly when `confirmed_by` is set. The derived index tables made by `indexing.py` carry a `project_id` and the same policy. A new graph table needs `project_id`, composite keys, the policy and the grants.
- `src/vrum/common.py`: what the modules below share: `Refusal` (the plain-English refusals), argument checks (including `parse_day` for dates), **the node reference helpers** (an epic, story or task is named only by `kind:number`, such as `story:12`: `node_ref`, `split_node_ref`, `node_order`, `parse_node_ref`, `parse_node_refs`, `kind_rank`, and the `Ref` type that tools take, which also refuses a bare number in plain words; rules and notes keep their own `id`), paging, and database helpers. `src/vrum/items.py`: `NamedItem`/`named()`, how a mixed list (search, overlaps, mentions) names an item: every item has `item_type` and `ref`, and an epic, story or task has no `id` while an acceptance criterion (rule), decision or fact keeps its own.
- `src/vrum/graph.py`: the one owner of epics, stories and tasks (`Graph`), and of how a node is read (`node_state`, backed by the `node_state` view that decides what `ready` means).
- `src/vrum/query.py`: the one owner of the filter language (words, `field:value`, commas, `OR`, a leading `-`, `no:field`, date ranges, `is:overdue`). `compile_query(text)` returns a condition on the `node_state` view with every value passed as a parameter, or refuses in plain words; `Graph.list_nodes(query=...)` ANDs it with the other filters, so the board's filter box and the agents' `list_nodes` give one answer. The board does not parse the text: it sends it as `query` to `list_nodes` (`filterbar.js`).
- `src/vrum/links.py`: the one owner of links. `src/vrum/claims.py`: the one owner of claims, leases and the handoff note that ends one (`next_work` and `finish_work` use its helpers), and `Claims.who_is_working` (every claim in force or lapsed, the latest handoff of each agent and the server's clock, for the Activity drawer; read only). `src/vrum/whereabouts.py` (M41) owns the six optional words a holder may say about where the work is and which run it is: `repository`, `branch`, `commit`, `pull_request` (the four of "where") and `run_label`, `client_name` (a label for the run, never an identity: the key's name still says who). `clean_whereabouts` checks them (a strict short alphabet, `https` addresses with no password, a commit of 7 to 64 hex digits, a branch that cannot start with `-`; blank means not said; the refusal never repeats the value; a secret is refused), `Whereabouts` is the model that `Claim`, `HeldWork`, `LastHandoff` and `Handoff` extend, and the `claims` table repeats the patterns (`tests/test_whereabouts.py` keeps the two equal). They are optional arguments of `claim_node` and `next_work` (all six) and of `renew_claim`, `release_claim` and `finish_work` (the four of where): no tool was added, because the agent set is at 25, and the short descriptions matter because the compact signatures of `run` are cut at `MOST_DESCRIPTION_CHARS`. They are kept on the claim and copied into the events (`claimed`, `claim_renewed`, the `handoff`'s `after`, `claim_released`'s `before`; an event that was given none has none of these keys), `get_node().where` is the live claim's words or the latest handoff's, a claim taken over starts only with the new holder's words, and Vrum never reads a checkout or asks GitHub: it is the agent's word. `scripts/verify_pr.py` uses the item's `where.pull_request` when no address is given. The export needs no new version (events carry them; the import checks them with `clean_whereabouts`), and the Markdown copy adds a "Where the work is" section to a story or task from its latest claim or handoff that said any. ## Working rules

- One milestone per iteration: the first unchecked one in `PROGRESS.md`. Never start the next one.
- **Long checks are on request.** Do not run the full `./check.sh` or `./acceptance.sh` unless the owner asks; suggest them when the owner asks to commit or push to `main` (see "When to run the long checks" above).
- A milestone is proven only when its "Proof" in `SPEC.md` passes against the real containers and a real MCP client, with every earlier proof still passing (except where `SPEC.md` marks one "Replaced by M16": a proof of something M16 removed is not kept). The owner decides when that full proof is run (see "When to run the long checks"); until then a milestone is marked built, with the checks that were run listed in `PROGRESS.md` and the full proof stated as not run.
- Product decisions that `SPEC.md` does not answer go in `BLOCKED.md` (question, 2 to 3 options, a recommendation, the default you would take). Do not invent answers.
- Defaults the owner may veto are recorded in `DECISIONS.md` and listed under "Defaults taken" in `PROGRESS.md`.
- **No migrations.** Vrum is a prototype with no customer data. The whole database is `src/vrum/schema.sql`. To change the schema, edit that file, tidying it as if it had always been this way, then rebuild the database from scratch: `docker compose down --volumes`, then `docker compose up -d --build --wait` (`./check.sh` already builds a fresh one every run). Do not write migration files, `ALTER TABLE` patches or data-preserving upgrade steps. Reconsider only when a database holds data someone cares about. (Owner's decision, see `DECISIONS.md`.)
- **Prototype stance.** Do not carry production habits that protect data or users that do not exist yet: no backward compatibility, deprecation paths or upgrade steps. When a design changes, change it everywhere and rebuild. Anything `SPEC.md` asks for is still built as written.
- Never commit a secret. Configuration comes from the environment.
- Never touch any Deelio repository or the Taiga project.
- No placeholder or shell code, and no abstraction without a consumer.
- Keep every change small and reviewable. Plain English in every message a person or agent reads.
- The MCP SDK is v2 (`from mcp.server import MCPServer`, `from mcp import Client`); its documentation is at https://py.sdk.modelcontextprotocol.io/. Check it before using an SDK feature.
