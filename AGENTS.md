# AGENTS.md

How to work in this repository. Read `SPEC.md` first, then `PROGRESS.md`.

## Running the checks

`./check.sh` is the one check command. It runs, in order:

1. lint: `uv run ruff check .` and `uv run ruff format --check .`
2. types: `uv run mypy` (strict)
3. unit tests: `uv run pytest -m "not integration"`
4. integration tests: builds the image, starts the real database and server in a throwaway compose project (`vrum-check`, port 18000 or `VRUM_CHECK_PORT`, random database password, removed afterwards; there is no token: the tests register an account, make a project and an agent key through the board's own HTTP API, `tests/world.py`), together with the one extra in `compose.check.yaml` (which `check.sh` adds through `COMPOSE_FILE`): a scripted embedding service (`tests/scripted_embeddings.py`; tests stop and start it to see what happens when it is gone) and the settings that point the server at it. The stack is three services: `db`, `app` and `scripted-embeddings`. There is no language model and no stand-in for one. It runs `uv run pytest -m integration` with a real MCP client and a real headless browser against it. The tests that destroy or load a whole database start a second, separate copy of Vrum (`tests/second_stack.py`: compose project `vrum-restore`, built from `compose.yaml` alone, on port `VRUM_CHECK_PORT` + 1, which `check.sh` passes as `VRUM_RESTORE_TEST_PORT` and also removes if a test dies). A proof stack started by hand (a clean clone, another compose project and port) needs the same `COMPOSE_FILE=compose.yaml:compose.check.yaml`, `VRUM_TEST_URL` for its MCP endpoint and `VRUM_RESTORE_TEST_PORT` for the second copy (plus `VRUM_RESTORE_PROJECT` if several stacks share one machine), because the tests stop and start the stand-in.

It needs Docker (with compose) and `uv`. It never touches your own stack or your `.env`. Run it before every commit; fix `ruff format` problems with `uv run ruff format .`.

`./acceptance.sh` is the other command: the shorter walk a person can read. It starts its own throwaway stack (compose project `vrum-acceptance`, port 18400 or `VRUM_ACCEPTANCE_PORT`, and the next port for the second, empty copy that the graph chapter makes for its graph of a known size (compose project `vrum-restore`), random password, the same scripted embedding service as the check stack; it needs `openssl` too), runs one scenario through a real MCP client and a headless browser, prints one line for each proof of each milestone, and removes everything afterwards, even when it fails. Name chapters to run only those (`./acceptance.sh finding board`; the names are the keys of `CHAPTERS` in `tests/acceptance.py`). It runs in the checkout it is in, so "from a clean clone" means: clone, then run it there. Each later milestone adds its proofs to it.

## Running the stack

```
./start.sh
```

There is nothing to set up first: no `.env`, no variable. `./start.sh` is `docker compose up -d --build --wait` followed by a message with the board's address. The first start makes a random database password in the `vrum-secrets` volume (the database service's entrypoint in `compose.yaml` writes `/secrets/db-password`; the server reads it through `VRUM_DB_PASSWORD_FILE`). Set `VRUM_DB_PASSWORD` before the very first start to choose it; it is ignored afterwards. `compose.yaml` must never use a `${NAME:?...}` that refuses to start without a value (`tests/test_config.py` fails on one), and `tests/test_zero_setup_integration.py` starts a copy with nothing set to prove it. **Before any `docker compose down` or `up` of your own in this checkout, set a scratch `COMPOSE_PROJECT_NAME` (and port):** the default project name is `vrum`, which is the owner's own stack.

The board is at `http://127.0.0.1:8000/board` (or `VRUM_PORT`) and the MCP endpoint is `http://127.0.0.1:8000/mcp` on the same port. There is no install-wide token: open the board, create an account (email and password kept by Vrum, `src/vrum/accounts.py`), create a project (it opens at `/board/p/<id>`), and on its **Agent access** page (Settings menu) make an agent key (`vrk_…`, shown once, only its hash is kept). Every request to the MCP endpoint needs a project's agent key, as `Authorization: Bearer <key>`, and reaches that project only; the board's own calls under `/board/api` carry a session cookie and the session's CSRF secret instead; only `GET /health` and the board's page files are open. While working on the board's pages (`src/vrum/board/static`), the server reads them once at start, so rebuild the image to see a change, or mount that folder over `/app/.venv/lib/python3.12/site-packages/vrum/board/static` in a scratch compose override and restart `app`. For a script or a client of your own, `scripts/vrum_client.py` connects with the key it reads from the `VRUM_AGENT_KEY` environment variable (`export VRUM_AGENT_KEY=...` first; the helper scripts below need it). The most one request may hold is `VRUM_MAX_REQUEST_BYTES` (4 MiB). `docker compose down` stops it; add `--volumes` to also delete the data. Logs are JSON lines (`docker compose logs app`): they never hold passwords, sessions, keys or what was written.

**Backing up and moving data.** `./scripts/backup.sh [file]` writes the whole database to one file (default `backups/vrum-<time>.dump`, git-ignored, readable only by you) while the server runs: every account and project, hashes included, so it is for whoever runs the server and not an account's to take. `./scripts/restore.sh <file>` puts it back (it creates the database role the projects run as first, since a role belongs to the server and not to a database): into a fresh database (after `docker compose down --volumes`) it just restores; into one that holds data it refuses unless you add `--replace`. For one project's data that you can read, keep or load into another project or server: `uv run python scripts/export_graph.py <url> <file.json>` writes the project as one JSON file (ids included: each project numbers its own), `scripts/import_graph.py <url> <file.json>` loads such a file into an empty project (all or nothing; as big as one request may be), and `scripts/export_markdown.py <url> <folder>` writes a read-only Markdown copy, one file per item with `[[references]]`, to read in Obsidian or keep in git. All three need `VRUM_AGENT_KEY` set (the project's key), and work from a checkout without installing anything.

Search by meaning, similar items and possible duplicates need an embedding service; exact-words search needs nothing. To run one on this machine, add `EMBEDDING_BASE_URL=http://ollama:11434/v1` and `EMBEDDING_MODEL=all-minilm` to `.env` and start with `docker compose --profile local-embeddings up -d --build --wait` (the first start downloads the model, about 50 MB). Any OpenAI-compatible service works instead: set the two variables to its address and model (see `.env.example`). To see what a real model does with realistic requirements, run `uv run python scripts/real_embeddings_check.py http://127.0.0.1:8000/mcp` (with `VRUM_AGENT_KEY` set to a project's agent key; it adds a few clearly named epics and stories). The thresholds depend on the model: measure, then set `EMBEDDING_MIN_SIMILARITY` and `EMBEDDING_OVERLAP_THRESHOLD`.

Vrum has no language model and no setting for one: nothing on the server generates text. An agent that wants a conclusion kept records it with `retain_fact` or `record_decision` like any other statement.

## Layout

- `src/vrum/config.py`: settings from the environment (the only place that reads it), including the request size limit, the board's poll interval and the optional embedding service. There is no token setting and no language-model setting.
- `src/vrum/accounts.py`: the one owner of accounts, sessions, projects and agent keys (the `accounts`, `sessions`, `projects` and `agent_keys` tables, which are not graph content and which a project's database role cannot reach): `Accounts.register`/`sign_in` (scrypt hashes, `hash_password`/`password_matches`; the failures of one address or one network address are counted by `src/vrum/ratelimit.py`'s `AttemptLimiter`, in memory), `session` (a cookie's value, of which only a SHA-256 is stored, plus a CSRF secret), `projects`/`create_project`/`project_of` (a project that does not exist and one that is someone else's are refused in the same words), and `create_key`/`keys`/`revoke_key`/`project_for_key` (a key is `vrk_…`, shown once, only its hash stored). Refusals are `AccessRefusal` (a `Refusal` with an HTTP status).
- `src/vrum/db.py`: besides the pool and `prepare_schema`, how work is bound to a project: `working_for(project_id)` sets the project for everything done inside it (a `ContextVar`), `Database.transaction()` is the project-scoped transaction (it does `set_config('vrum.project_id', …)` and `SET ROLE vrum_project`, so the database shows only that project's rows; with no project named it raises `NoProject` and the database shows none), and `Database.admin_transaction()` is for what is not a project's own work (accounts, projects, keys, the index job, building the schema). Never use `admin_transaction` for graph data in a tool.
- `src/vrum/schema.sql`: the whole database in one file: the account tables, then the graph tables (`nodes`, `links`, `claims`, `rules`, `facts`, `decisions` with their link tables `fact_nodes`, `fact_rules`, `fact_decisions`, `decision_nodes` and `decision_rules`, and `events`), constraints, triggers and the `node_state`, `decision_state` and `fact_state` views (plus `search_documents` and `index_source`, which exact-words search and the index read). Every graph table has a `project_id` that is part of its primary key and of every foreign key, so a row cannot refer to a row of another project; each project numbers its own nodes, links, rules, facts, decisions and events from 1 (a sequence per project and kind, made when the project is made, read with `next_id(kind)`; `continue_ids_after` sets it after an import); and row-level security with a policy `project_id = current_project()` on every graph table, for the role `vrum_project` (the server switches to it for each project transaction; it has only the rights listed at the end of the file and none on accounts, sessions, projects or keys). Views are `security_invoker`. A fact and a decision are records the database never lets be edited or deleted (triggers): only their confirmation changes while they are active, and an ended one (superseded or withdrawn) cannot change at all. The derived index tables made by `indexing.py` carry a `project_id` and the same policy. A new graph table needs `project_id`, composite keys, the policy and the grants.
- `src/vrum/common.py`: what the modules below share: `Refusal` (the plain-English refusals), argument checks (including `parse_day` for dates), paging, and database helpers.
- `src/vrum/graph.py`: the one owner of epics, stories and tasks (`Graph`), and of how a node is read (`node_state`, backed by the `node_state` view that decides what `ready` means).
- `src/vrum/query.py`: the one owner of the filter language (words, `field:value`, commas, `OR`, a leading `-`, `no:field`, date ranges, `is:overdue`). `compile_query(text)` returns a condition on the `node_state` view with every value passed as a parameter, or refuses in plain words; `Graph.list_nodes(query=...)` ANDs it with the other filters, so the board's filter box and the agents' `list_nodes` give one answer. The board does not parse the text: it sends it as `query` to `list_nodes` (`filterbar.js`).
- `src/vrum/links.py`: the one owner of links. `src/vrum/claims.py`: the one owner of claims, leases and the handoff note that ends one (`next_work` and `finish_work` use its helpers), and `Claims.who_is_working` (every claim in force or lapsed, the latest handoff of each agent and the server's clock, for the Activity drawer; read only).
- `src/vrum/rules.py`: the one owner of rules (the board calls them requirements; the database, the tools and `[[rule:3]]` keep the name) and the coverage report. There is no tool to take a rule out of its story: it is placed (`place_rule`) or moved (`move_rule`).
- `src/vrum/records.py`: what facts and decisions share, so that they behave alike: confirmation (`apply_confirmation`: a named person confirms or un-confirms an **active** record, recording one never confirms it, un-confirming needs the person and their words, and what a record was confirmed as stays on it once it ends), the person's word that changing a confirmed record needs (`said`, `require_a_person_for_confirmed`) and the plain-words label of where a record stands (`label_of`, `confirmation_words`, `ended_words`).
- `src/vrum/facts.py`: the one owner of facts: recording one (`retain_fact`: a text and its source, never blank), what it concerns (`link_fact`, `unlink_fact`), replacing one or several at once (`supersede_fact`) or withdrawing them (`withdraw_fact`), confirmation, and reading and listing them (`get_fact`, `list_facts`, `fact_history`; the `fact_state` view adds the derived `confirmation`, what a fact replaced and what it concerns). A fact is never edited. `src/vrum/decisions.py`: the same for decisions (a title, text, reason and a named decider; `project_wide` is a flag on the same kind of record, and changing it means superseding the decision): `record_decision`, `supersede_decision`, `withdraw_decision`, the links to nodes and rules, confirmation, and `decision_history`; the `decision_state` view adds `confirmation`, what a decision replaced and what it affects. Both log each change as an event (`fact_recorded`, `fact_confirmed`, `decision_withdrawn` and so on).
- `src/vrum/recall.py`: `recall`, everything known about one node or rule by exact links, in the sections `active_decisions`, `project_wide_decisions` (every active project-wide decision of the project, linked or not), `facts`, `past_decisions` and `past_facts` (superseded or withdrawn), plus `similar` when asked; every entry says why it is there and carries its confirmation, its status and its plain-words label, so an unconfirmed record is never shown as confirmed. `src/vrum/references.py`: the one owner of the reference syntax (`[[node:12]]`, `[[rule:3]]`, `[[decision:7]]`, `[[fact:5]]`: one `REFERENCE_PATTERN`, which `references.js` repeats byte for byte and `tests/test_references.py` compares) and of `find_mentions`, which works out in SQL, when asked, which texts (bodies, decision texts and reasons, fact texts and sources; never titles) name which items, and stores nothing. A reference is only text: it makes no link, readiness or order. With no target it lists every reference (the graph's References layer uses that).
- `src/vrum/embeddings.py`: the one small interface to an OpenAI-compatible embedding service (text in, vectors out); the only outside service Vrum talks to. `src/vrum/secret_formats.py`: recognises secrets in well-known formats (`find_secret`, `find_secret_in` for nested arguments, `redact_secrets`), used by M6 on every tool argument and on every write (`common.refuse_secrets`).
- `src/vrum/indexing.py`: the semantic index (epics, stories, requirements, decisions and facts) and its reindex job, the only code that creates, changes or drops the index tables (`semantic_index`, `semantic_index_info`, which are derived and not in `schema.sql`), plus the background task that keeps it current. `src/vrum/search.py`: search by words, meaning or both (result types epic, story, task, rule, decision and fact; each result carries its confirmation and label), similar items and the overlap finder (read only). Exact-words search reads the `search` columns of the graph tables. `src/vrum/status.py`: `server_status` (versions, the size of each kind of item, and the index state with a live probe of the embedding service; nothing about a model, since there is none); the last reindex is kept in memory by `Indexer.last_run`, so it is empty after a restart.
- `src/vrum/workflow.py`: what an agent does in a day's work, built on the owners above and not repeating them: `next_work` (pick, claim and brief in one transaction, with the context cut to a size: requirements, `active_decisions`, `project_wide_decisions`, `facts` and `past_decisions`, each with its confirmation, plus handoff notes and similar items), `finish_work`, `create_plan` (check a whole plan, then create it in one transaction), `update_nodes`, `changes_since` (a feed that never skips a late event; with `newest` it reads the newest events backwards and `before_event_id` goes further back, since events are ordered by `(xid, id)` and not by id), and `create_node`'s check for similar items.
- `src/vrum/server.py`: the MCP tools (53 of them, thin: they call `Graph` and the other owners), the server instructions (`INSTRUCTIONS`, which the agent guide in `docs/agents.md` repeats word for word), the background reindex task, and the health route. Which tools only read is the server's own `read_only_hint` annotation (`_READS`).
- `src/vrum/exchange.py`: moving the whole graph as data: `export_graph`'s pages (everything in id order, as plain text and numbers: nodes, links, rules, decisions, facts and events) and `import_graph` (a file is read and checked, every problem listed at once, then loaded into an empty database in one step with its ids; the endings of replaced and withdrawn records are applied last so that the database's own rules are never bypassed). Facts and decisions carry their confirmation, lifecycle and links. `src/vrum/markdown.py`: `render`, a pure function from an export to the files of the read-only Markdown copy.
- `src/vrum/guard.py`: `GuardedServer`, the MCP server every tool call goes through: it refuses a secret in any argument before anything else, decides the project of the call (from the agent key in the call's own request headers, looked up again on every call so a revoked key stops at once, even on an open connection; a call the board makes in-process is for the project the board has already shown the person owns), runs the tool `working_for` that project, turns the SDK's validation errors into plain messages that do not repeat what was sent, and logs one line per call (with the project number). `src/vrum/access.py`: the `AccessGuard` around the whole web app: an agent key (valid and not revoked) on everything under `/mcp`, the board's page files and `GET /health` open, the board's `/board/api` calls handed on to the board (they carry a session cookie, checked there), and the request size limit, answering with plain JSON-RPC errors. `src/vrum/logs.py`: the JSON log format and the scrub that removes passwords, keys, sessions and secret formats (`vrk_…` agent keys and `vrs_…` sessions are formats too, so they are also refused in any text an agent writes) from every line.
- `src/vrum/board/`: the board. `__init__.py` is its server side (`add_board`): the page files under `/board` (open, since they hold no data; every response carries the content security policy; `/board/p/<id>` serves the same page), the accounts routes (`POST /board/api/accounts` to register, `POST`/`GET`/`DELETE /board/api/session` to sign in, ask who is signed in and sign out, `GET`/`POST /board/api/projects` and `GET /board/api/projects/<id>`, and `GET`/`POST /board/api/projects/<id>/keys` with `DELETE …/keys/<key>`), and, for a project the signed-in person owns (checked on every request, never in the browser), `POST /board/api/projects/<id>/tool/<name>` (calls the MCP tool of that name on the same server for that project, so every board action is the same operation as the matching tool, with the same refusals; only the tools in `READ_TOOLS` and `WRITE_TOOLS` may be called, and a test checks they exist and that `reindex` is not among them), `GET …/index` (how many items wait to be indexed) and `POST …/try/<name>`; `GET /board/api/info` and `GET /board/api/tools` need a session only. `board/session.py` is how the board knows who is asking: the cookie `vrum_session` (HttpOnly, SameSite=Strict, Path=/board, Secure on https), the check of a session's CSRF secret in the `X-Vrum-CSRF` header and of the `Origin` on everything that changes something, and the same-site JSON check on sign-in and registration. `board/tools.py` is the map from every MCP tool to where it is on the board (`OnTheBoard`: a view, a drawer or a settings page, and where on it) or why it is for agents only (`AgentsOnly`: `next_work`, `finish_work`, `create_plan`, `reindex` and `import_graph`); `tests/test_board.py` fails when a tool the server has is in neither, or the map names one it does not (set `VRUM_TEST_DROP_FROM_MAP=<tool>` to see it fail once). A new tool needs a `read_only_hint` annotation if it only reads (the board's try route refuses any tool the live server does not mark read only), an entry in the map, and a place in `READ_TOOLS` or `WRITE_TOOLS` if a page calls it.
- `src/vrum/board/static/`: the pages: plain HTML, CSS and ES-module JavaScript with no build step and no library. Text is only ever put on a page as text (`dom.js` builds elements; a test fails on `innerHTML` and the like), and there is no inline script or style (`h` has a `css` property that sets `element.style`, and a test fails on a `style:` attribute). `dom.js`'s `put(el, ...children)` replaces what an element holds and leaves out empty children: a bare `append` or `replaceChildren` with `null` or an array writes "null" or "[object HTMLElement]" on the page. A page script may not name a tool in quotes that is not in `READ_TOOLS` or `WRITE_TOOLS`, so keep tool names out of the words a page shows. A view exports `mount`, `unmount`, `update(params)` and `refresh(events)`. The files, by what they do:
    - The shell: `index.html` (the one page: `theme.js` first in the head, then the stylesheets, the sidebar, the top bar, a drawer column, the page, the detail panel and one module script), `app.js` (the registry of pages, `board`, `graph`, `roadmap`, `access`, `tools` and `status`, with the Board the default; the address; the clock; the connection banner and the name the changes are recorded with; switching project is a whole page load), `sidebar.js` (the sidebar `#main-nav` of an open project: the project switcher, the three views with real counts, the epics, and at the foot Activity, the Settings menu, the appearance control and the account; below 1100 px it is off to the left and opens over the page from `#sidebar-toggle`, so a test on a narrow window opens it first), `topbar.js` (the top bar `#top`: the way back, the search box, the quick switcher button and what the server and the index are doing; before a project is open, the brand, the account and the appearance control), `shell.js` (what CSS cannot do for the layout: the height the bar takes, and closing a sheet on a click on the dimmed page or on Escape), `page.js` (`pageHeader`, the title line the settings pages share), `brand.js` (the wordmark drawn inline so it follows the theme), `appearance.js` (the Light / Dark / System radio group) and `ctx.js` (what the pages share: who is using the board, the address helpers `addressOf` and `hrefTo`, which keys of an address a plain click keeps between views (the drawer, and between the three views the selected record, the work filter and the epic), `viewLink`, `recordLink`, `notify`), `entry.js` (sign-in, registration and the project list), `api.js` (talks to the server: the session's CSRF secret, the project's number in every path, and an answer that arrives after the project was left is dropped as `Stale`), `store.js` (the copy of the work, and of requirements, decisions and facts once a page asks for them, and the poll of `changes_since`), `dom.js`, `labels.js` (the words and icons for status, kind, priority and link type, so that colour is never the only clue), `icons.js` (the one icon set: inline SVG drawn by `icon(name, {size, label, className})`; no font glyph is ever used as an icon, so add a shape here), `dates.js` (UTC day arithmetic, the same day the database uses) and `switcher.js` (the Ctrl+K / ⌘K "Jump to" box, which only navigates).
    - The three views: `kanban.js` (the Board: columns, epic lanes, the "Needs attention" strip `#attention` whose numbers are `list_nodes` counts and `coverage_report`, the work filter and the cards), `graph.js` (the Graph page: the Work, Context and Everything presets and the Map and List presentations, scope, reach, colour, the map's SVG and its keyboard use), `graph-nodes.js` (what a node of the map looks like: its size from its words, and the SVG; a graph too big for that draws small icon tiles), `layered.js` (the rows layout for a scope of at most 60 dots and 12 in a row: epics on top, then stories, tasks and the context below, with the lines routed in lanes; a bigger scope uses the force layout), `graph-data.js` (what the preset, the switches and the scope show: the same dots, lines and rows for the map and the list, and the 1,000-dot limit), `layout.js` (the force layout for a big scope), `work-list.js` (the Graph's list of work: the tree of epics, stories and tasks), `context-list.js` (the Graph's list of context: requirements, decisions and facts, with their filters and actions), `requirements.js` (its requirements section: grouped by story, the unplaced ones first, the coverage report, writing, placing and moving), `list-parts.js` (what the context list's sections share: the frame, the filters, the connections of a row) and `roadmap.js` (bars from `span_start` to `span_end`; every drag, key and tray drop is `update_node` or `update_nodes`, never clamped, so the server refuses a start after the target). `filterbar.js` is the work filter box the Board, the Roadmap and the Graph share, and `loadRows`: an empty filter reads the store, anything else asks `list_nodes` with `query`.
    - The drawers: `drawer.js` (the column left of the page where Search and Activity open on every view; which one is in `drawer=` of the address, only one at a time, and it stays mounted while the rest of the address changes, so that opening it never discards a draft), `search.js` (the search drawer: the server's `search` read to the end with `callPaged`, the counts by type, status and epic worked out in the browser over the whole list, and the waiting count the shell shows), `duplicates.js` (Possible duplicates, the second tab of the same drawer, over `find_overlaps`; `Mark as…` is `add_link`, one click one link), `activity.js` (the Activity drawer: the feed over `changes_since`, newest first, and "Who is working on what" over `who_is_working`, `claim_node`, `renew_claim` and `release_claim`, with a one second countdown; its filters are `act_…` in the address) and `events.js` (`describe`, every action in plain words, including the fact and decision actions, and `eventRow`, which shows a handoff note in full).
    - The shared detail panel: `panel.js` (mounted once; what it shows is `sel=node:12`, `sel=rule:3`, `sel=decision:7` or `sel=fact:5`, or `panel=coverage`, so a link opens it on any view, and it keeps its draft while a view or a drawer changes), `card.js` (the epic, story or task: its details and changes at the version the person saw, links, requirements, the facts and decisions that concern it, mentions, what the index thinks it may duplicate and its history), `records.js` (a requirement, decision or fact drawn in full, and the operations the other pages import: `openRecord`, `recordFactDialog`, `recordDecisionDialog`, `linkDialog`, `supersedeDialog`, `withdrawDialog`, `confirmationControl` (the Unconfirmed / Confirmed dropdown), `recordRow`, `requirementDialog`, `placeRequirementDialog`), `record-forms.js` (every dialog: record, replace, withdraw, what it concerns, confirm and un-confirm, write or place a requirement), `entries.js` (how a fact or a decision is shown: confirmation and lifecycle always said from the record's own fields), `recall.js` (the very `recall` call an agent makes, drawn in its sections with its reasons), `coverage.js`, `create.js` (a new epic, story or task, and the parents to choose from) and `forms.js` (dialogs, labelled fields and the picker for what a record concerns; no field is `required`, so a blank is sent and the server's refusal is what a person reads).

## Working rules

- One milestone per iteration: the first unchecked one in `PROGRESS.md`. Never start the next one.
- A milestone is finished only when its "Proof" in `SPEC.md` passes against the real containers and a real MCP client, with every earlier proof still passing (except where `SPEC.md` marks one "Replaced by M16": a proof of something M16 removed is not kept).
- Product decisions that `SPEC.md` does not answer go in `BLOCKED.md` (question, 2 to 3 options, a recommendation, the default you would take). Do not invent answers.
- Defaults the owner may veto are recorded in `DECISIONS.md` and listed under "Defaults taken" in `PROGRESS.md`.
- **No migrations.** Vrum is a prototype with no customer data. The whole database is `src/vrum/schema.sql`. To change the schema, edit that file, tidying it as if it had always been this way, then rebuild the database from scratch: `docker compose down --volumes`, then `docker compose up -d --build --wait` (`./check.sh` already builds a fresh one every run). Do not write migration files, `ALTER TABLE` patches or data-preserving upgrade steps. Reconsider only when a database holds data someone cares about. (Owner's decision, see `DECISIONS.md`.)
- **Prototype stance.** Do not carry production habits that protect data or users that do not exist yet: no backward compatibility, deprecation paths or upgrade steps. When a design changes, change it everywhere and rebuild. Anything `SPEC.md` asks for is still built as written.
- Never commit a secret. Configuration comes from the environment.
- Never touch any Deelio repository or the Taiga project.
- No placeholder or shell code, and no abstraction without a consumer.
- Keep every change small and reviewable. Plain English in every message a person or agent reads.
- The MCP SDK is v2 (`from mcp.server import MCPServer`, `from mcp import Client`); its documentation is at https://py.sdk.modelcontextprotocol.io/. Check it before using an SDK feature.
